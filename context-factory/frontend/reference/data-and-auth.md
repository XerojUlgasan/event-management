# Client data and authentication

- `apps/web/src/components/app/data.ts` retains unrelated demo/navigation data. Package cards and admin catalog editing use `src/lib/api.ts` and `/v1/packages`; the standalone admin Venues screen uses the versioned draft/publish/archive venue catalog API. Published venues appear in the public Venues catalog only, with no home preview. Customer and admin messages use `/v1/messages` and `/v1/admin/conversations`. Package booking requests use `/v1/booking-requests` and appear in customer My events and the manager request queue; their preferred location is independent of the venue catalog. Quotes, payments, confirmed bookings, and event delivery are not persisted workflows yet. Confirm the actual API boundary before claiming a workflow is end to end.
- `src/lib/api.ts` owns the current HTTP wrapper and endpoint calls. It sends cookies with `credentials: "include"` and accepts a Firebase token only for relevant identity exchanges. Match request/response changes to the API's `createRoute` schemas and `profile.ts` mapping. Package and service catalog calls use typed DTOs here; the public list calls accept optional `limit` and `offset` and return `nextOffset`. Package responses include included and optional service assignments. Service previews load `GET /v1/services/:id/packages` to find current published packages with an included assignment to that service. Service images may be HTTPS URLs or uploaded assets resolved against the API origin.
- `src/lib/auth.tsx` owns `AuthProvider`, session restoration through `GET /me`, and sign-in/sign-out state. `src/lib/firebase.ts` configures optional Firebase browser sign-in with in-memory persistence. Read `AuthPage.tsx` and `SignInMethods.tsx` when changing login or linking UI.
- The database profile and role returned by the API determine whether the app shows the System Administrator, staff, or customer area. UI state is not authorization; protected API operations must check access server-side.
- `PUBLIC_API_URL` and optional Firebase browser variables are described in `apps/web/.env.example`. Keep secret service-account values on the API side.

For auth changes, trace the user action through UI, client request, API route, session, and restored page state. Test failure paths as well as the successful path.
