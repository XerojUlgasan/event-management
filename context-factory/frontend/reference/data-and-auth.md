# Client data and authentication

Screens reach `/v1` through the functions in [client layers](client-layers.md). This page records which flows are persisted and how the session is restored.

- `apps/web/src/demo/` holds sample photos and bookings; admin navigation lives in `components/workspaces/admin/navigation.ts`. Package, service, and venue catalog reads and admin saves use `src/lib/data/` and their `/v1` routes. Create saves a complete flat record directly as public and active; full-content updates use `expectedUpdatedAt`; archive hides the record from public reads. Each entity owns one canvas page. Service saves require a positive hourly rate and a canvas photo; venue saves require a positive maximum guest count, while photos are optional. Migrated null rates/guest limits can still be returned by reads. Published venues appear on `/`, `/venues`, and `/venues/{slug}`. Customer and admin messages use `/v1/messages` and `/v1/admin/conversations`. Package booking requests use `/v1/booking-requests` and appear in customer My events and admin Bookings. New requests send `durationMode`, `requestedDays` date entries, and `timeZone`; `preferredDate` remains the earliest date for compatibility, while the list is authoritative. The response derives `durationMode` and requested-day count, returns each day’s nullable start/end instants and `operationalSchedule` summary, and keeps legacy `estimatedDuration` values readable. Owners save paired times for an unscheduled day through `PATCH /v1/booking-requests/{id}/requested-days/{date}/times` with `expectedUpdatedAt`; the API updates only that day, rejects stale writes, and does not create an event day. Admin Bookings filters by `preferredDate` across all selected dates, has matching per-date counts and status filters, and pages unique requests with a cursor. Legacy rows with SQL `NULL` requested days fall back to their recorded preferred date and estimate; no missing dates are invented. Staff queue access remains separate from staff event-day views, which only show operational schedules. Staff Event days and Assigned to me use `/v1/staff/event-days` and `/v1/staff/assignments`; per-day responses persist through the availability endpoint. System Administrators open request details at `/app/bookings/{id}` and select a requested or operational date in the Event days section. For accepted requests, the administrator selects one shared 1–4-calendar-day response deadline and applies it. The selected-day workspace previews the cutoff in the booking timezone. `POST /v1/admin/event-days/apply-response-deadlines` atomically creates and links operational days for requested dates with saved customer times and recalculates deadlines for current scheduled operational dates, including replacements. Each deadline closes at 23:59:59.999 on the calculated date in the booking timezone. Closed staffing remains closed, expired open staffing remains closed, moved/cancelled history is unchanged, and requested dates still waiting for times are skipped until the administrator applies the choice again. The choice is not persisted as a future policy. Acceptance and time saving alone create no day. `POST /v1/admin/event-days` remains for legacy requests with SQL `NULL` requested days; legacy open creation, movement, and reopening take the same bounded `daysBefore` choice. Existing operational schedules and teams use the admin event-day routes. Staffing is separate from booking confirmation. Private package proposals and quotations persist through their booking-scoped APIs; the booking’s Checklist tab selects an operational day and manages its persisted checklist through the event-day APIs; payments, confirmed bookings and external workforce notifications remain unimplemented. Confirm the actual API boundary before claiming a workflow is end to end.
- Match request and response changes to the API's `createRoute` schemas and `profile.ts` mapping. [Client layers](client-layers.md) places the fetch wrapper, domain calls, catalog upload-then-save, the signed-out booking draft, and message-thread merge. Admin conversations use a 15-row cursor page with `nextCursor`; the admin Messages sidebar loads more pages on scroll and refreshes the first page for recent activity. Both message lists show event type for linked requests and last update. Linked package and event fields derive from the booking request; general threads have no editable event context. Conversations have no automatic expiry or `expiresAt` response field; age and event end times do not close a thread. Existing closed linked threads remain read-only; a customer message can reopen a general thread. Bookingless-chat expiry is deferred. Customers fetch their own request from a linked conversation and keep the `BookingDetails` modal for eligible per-day time edits. System Administrator links navigate to `/app/bookings/{id}`, whose page fetches the admin request and shows status controls plus `AdminEventDays`; its selected-day workspace uses the existing event-day APIs. The app route is restricted to System Administrators, and protected API operations still enforce authorization. AI replies and guest chat are deferred. Package DTOs use the `CatalogPackage` and `PackageContent` contracts, including a stored `description` edited in Package details and displayed on admin/public cards independently of canvas Markdown; public lists accept optional `limit` and `offset` and return `nextOffset`. `POST /v1/admin/packages` creates and publishes; `PATCH /v1/admin/packages/{id}` saves edits with `expectedUpdatedAt`. Package responses do not include a version ID; package service assignments are ordered included/optional links. Services and venues are flat DTOs containing current content and timestamps (`id`, `archivedAt`, `createdAt`, `updatedAt`, and `publishedAt`); service DTOs also include the first canvas photo as derived `imageUrl`. Their direct create and full-content update routes save public active records; updates use `expectedUpdatedAt`, while archive hides the record. No service/venue draft, publish, history, or version-ID endpoints exist. Each has one catalog page; omitted `sections` preserve saved content. Public service `imageUrl` selects the first canvas photo. Package canvas uploads use multipart FormData at `/v1/admin/catalog-media`; pending uploaded assets are attached by a later catalog save, while saved uploads are served from `/v1/catalog-media/{id}`. Photo and video widgets are upload-only; external URLs and hosted-player embeds are rejected. Built-in sample photos remain supported for seeded packages. Packages support ordered included/optional service assignments; venues remain independent.
- Shared catalog media widgets keep their canvas body to a photo/video preview. Empty Add a photo/Add a video buttons open the appropriate file chooser directly and reuse the editor validation and local preview; the three-dot settings remain available. `components/catalog/PackageMediaSettings.tsx` provides the native modal opened by a three-dot widget button; it owns file selection hints, image description, caption, and video autoplay controls. These edits remain local until the owning catalog Save action. The shared editor receives entity-specific metadata, validation, persistence, and preview callbacks. `components/catalog/CatalogContent.tsx` composes package, service, and venue views for editor customer previews, saved catalog overlays, booking package proposals, and public SSR. Generic canvas, section, widget, and sanitized Markdown rendering comes from `@event-management/ui`; media URL resolution remains in the app. The editor and customer views show the same saved captions and uncropped media. Editor mode suppresses autoplay; customer views honor opt-in muted inline video autoplay with native controls. Rendered widgets clip overflow without internal scrollbars. Markdown authoring opens in a separate native dialog; its edits remain local until the catalog Save action.
- `src/lib/auth/AuthProvider.tsx` owns `AuthProvider`, initial session restoration through `GET /me`, and sign-in/sign-out state. It revalidates `/me` when the document regains focus or visibility and when `http/request.ts` reports a `401` from a non-authentication, non-`/me` request. After a signed-in account-method operation returns `401`, `AuthProvider` also checks `/me` once that operation settles; this distinguishes an expired API session from invalid credential proof without ending a valid session. A successful check refreshes the profile; a `401` clears the profile and marks the user signed out. `App.tsx` then sends a protected workspace path to `/login`, preserving the local path, query, and hash for a later return. Other revalidation failures keep the current profile and show one error notice until a successful check. `navigation/workspace-navigation.ts` handles same-origin `/app` URLs with `pushState`/`replaceState` and listens for browser history changes, so ordinary workspace navigation does not remount `AuthProvider` or show the initial auth-loading state. Public and login destinations remain document navigations. When sign-in follows a workspace path, `workspaceReturnPath` accepts only local `/app` destinations allowed for the signed-in role. `src/lib/auth/firebase.ts` configures optional Firebase browser sign-in with in-memory persistence. Read `AuthPage.tsx` and `SignInMethods.tsx` when changing login or linking UI.
- Browser forms may mirror shared field and photo-count constraints for timely feedback, but the API route schemas enforce accepted values. Use `@event-management/contracts/limits/*` for mirrored constants and keep HTTP request-body caps server-side; see the [shared limits guidance](../../limits/SKILL.md).
- The database profile and role returned by the API determine whether the app shows the System Administrator, staff, or customer area. UI state is not authorization; protected API operations must check access server-side.
- `PUBLIC_API_URL` and optional Firebase browser variables are described in `apps/web/.env.example`. Keep secret service-account values on the API side. `pnpm dev` sets `PUBLIC_API_URL` to the same-origin path `/v1`; the Astro dev server proxies it to the Supabase gateway because that gateway's wildcard CORS header cannot be used with the session cookie. A relative `PUBLIC_API_URL` is resolved against the page origin in the browser.

For auth changes, trace the user action through UI, client request, API route, session, and restored page state. Test failure paths as well as the successful path.
