# Client data and authentication

- `apps/web/src/components/app/data.ts` retains unrelated demo/navigation data. Package, service, and venue catalog reads and admin saves use `src/lib/api.ts` and their `/v1` routes. Create saves a complete flat record directly as public and active; full-content updates use `expectedUpdatedAt`; archive hides the record from public reads. Each entity owns one canvas page. Service saves require a positive hourly rate and a canvas photo; venue saves require a positive maximum guest count, while photos are optional. Migrated null rates/guest limits can still be returned by reads. Published venues appear on `/` and its View more overlay. Customer and admin messages use `/v1/messages` and `/v1/admin/conversations`. Package booking requests use `/v1/booking-requests` and appear in customer My events and the manager request queue. Requests send `packageId`, optional `packageUpdatedAt`, optional guest count, and optional free-text preferred venue; the database snapshots package name, price, guest maximum, and ordered package inclusions. The initial request records a preferred date and estimated event length; exact times remain nullable and preferred location is independent of the venue catalog. Each response also includes the mutable `arrangement`, its `customizationRequests`, and a `pendingCustomizationRequests` count. Arrangement edits use `/v1/admin/booking-requests/{id}/arrangement` with `expectedUpdatedAt`; customers create requests through `/v1/booking-requests/{id}/customization-requests`, withdraw pending requests through `/v1/customization-requests/{id}/withdraw`, and administrators decide and list them through `/v1/admin/customization-requests`. The customer dialog keeps booking fields read-only but lets customers submit and withdraw their own customization requests; staff can read arrangements and requests but cannot edit or decide them. The manager queue uses status and preferred-date filters, a monthly count calendar, and cursor-paged requests in batches of 50; staff see the same queue without status editing. Quotes, payments, confirmed bookings, and event delivery are not persisted workflows yet. Confirm the actual API boundary before claiming a workflow is end to end.
- `src/lib/api.ts` owns the current HTTP wrapper and endpoint calls. It sends cookies with `credentials: "include"` and accepts a Firebase token only for relevant identity exchanges. Match request/response changes to the API's `createRoute` schemas and `profile.ts` mapping. Admin conversations use a 15-row cursor page with `nextCursor`; the admin Messages sidebar loads more pages on scroll and refreshes the first page for recent activity. Both message lists show event type for linked requests and last update. Linked package and event fields derive from the current booking arrangement; general threads have no editable event context. Request-linked threads stay open while the booking is active, close 24 hours after a known event end, and stay open while a customization request is pending; `expiresAt` is null while no automatic expiry applies. Expired linked threads remain closed. Booking-linked threads fetch the full request through a role-authorized detail route and reuse `BookingDetails`; the customer view is read-only. AI replies and guest chat are deferred. Package DTOs use the `CatalogPackage` and `PackageContent` contracts, including a stored `description` edited in Package details and displayed on admin/public cards independently of canvas Markdown, plus ordered service assignments (`serviceId`, `name`, `role`, `sortOrder`, `archivedAt`). Admin reads include archived services; public reads omit them. Public lists accept optional `limit` and `offset` and return `nextOffset`. `POST /v1/admin/packages` creates and publishes; `PATCH /v1/admin/packages/{id}` saves edits with `expectedUpdatedAt`. Package responses do not include a version ID. Services and venues are flat DTOs containing current content and timestamps (`id`, `archivedAt`, `createdAt`, `updatedAt`, and `publishedAt`); service DTOs also include the first canvas photo as derived `imageUrl`. Their direct create and full-content update routes save public active records; updates use `expectedUpdatedAt`, while archive hides the record. No service/venue draft, publish, history, or version-ID endpoints exist. Each has one catalog page; omitted `sections` preserve saved content. Public service `imageUrl` selects the first canvas photo. Package canvas uploads use multipart FormData at `/v1/admin/catalog-media`; pending uploaded assets are attached by a later catalog save, while saved uploads are served from `/v1/catalog-media/{id}`. Photo and video widgets are upload-only; external URLs and hosted-player embeds are rejected. Built-in sample photos remain supported for seeded packages. Services carry no package list in their own DTO; assignment is read from the package side.
- Shared catalog media widgets keep their canvas body to a photo/video preview. Empty Add a photo/Add a video buttons open the appropriate file chooser directly and reuse the editor validation and local preview; the three-dot settings remain available. `pages/PackageMediaSettings.tsx` provides the native modal opened by a three-dot widget button; it owns file selection hints, image description, caption, and video autoplay controls. These edits remain local until the owning catalog Save action. The shared editor receives entity-specific metadata, validation, persistence, and preview callbacks; public and admin details reuse `CatalogSections.tsx` and the service/venue canvases in `CatalogPreview.tsx`. `PackagePreview.tsx` suppresses captions/autoplay in editing mode; customer rendering honors saved video autoplay using muted inline video with native controls.
- `src/lib/auth.tsx` owns `AuthProvider`, session restoration through `GET /me`, and sign-in/sign-out state. `src/lib/firebase.ts` configures optional Firebase browser sign-in with in-memory persistence. Read `AuthPage.tsx` and `SignInMethods.tsx` when changing login or linking UI.
- Browser forms may mirror shared field and photo-count constraints for timely feedback, but the API route schemas enforce accepted values. Use `@event-management/contracts/limits/*` for mirrored constants and keep HTTP request-body caps server-side; see the [shared limits guidance](../../limits/SKILL.md).
- The database profile and role returned by the API determine whether the app shows the System Administrator, staff, or customer area. UI state is not authorization; protected API operations must check access server-side.
- `PUBLIC_API_URL` and optional Firebase browser variables are described in `apps/web/.env.example`. Keep secret service-account values on the API side.

For auth changes, trace the user action through UI, client request, API route, session, and restored page state. Test failure paths as well as the successful path.
