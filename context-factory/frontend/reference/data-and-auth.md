# Client data and authentication

- `apps/web/src/components/app/data.ts` retains unrelated demo/navigation data. Package, service, and venue catalog reads and admin saves use `src/lib/api.ts` and their `/v1` routes. Create saves a complete flat record directly as public and active; full-content updates use `expectedUpdatedAt`; archive hides the record from public reads. Each entity owns one canvas page. Service saves require a positive hourly rate and a canvas photo; venue saves require a positive maximum guest count, while photos are optional. Migrated null rates/guest limits can still be returned by reads. Published venues appear on `/` and its View more overlay. Customer and admin messages use `/v1/messages` and `/v1/admin/conversations`. Package booking requests use `/v1/booking-requests` and appear in customer My events and the manager request queue. Creation submits `packageId`, optional `packageUpdatedAt`, event type, preferred date, estimated duration, optional guest count and preferred venue, contact details, and optional `specialRequests`; it does not submit a time-zone field or exact event times. The API rejects a preferred date before today in Asia/Manila. A System Administrator can create and edit one private custom package from the booking using the shared package canvas; the owning customer can preview it and open its conversation. Booking responses join package name, price, maximum guests, and ordered service inclusions from the current linked package, so catalog edits affect existing requests. Event details and internal notes live directly on the request. System Administrators edit them through `PATCH /v1/admin/booking-requests/{id}/details` with required `expectedUpdatedAt`; staff and customers read event details, while only System Administrators receive non-null notes. Exact timestamps are edited and displayed in Asia/Manila. Customers discuss changes in the existing request-linked conversation; no structured customization routes or pending queue remain. Conversation context comes from `booking_requests` and the current package, and pending chat changes do not extend expiry. Quotation persistence, API behavior, and the admin builder are implemented. New quote bases use the current package price, with totals calculated from the base plus additions minus deductions. A changed package, assigned service, or delivery basis blocks sending or accepting an outdated quotation; a revision carries adjustments for explicit review before sending. Sending a quote posts it to the booking conversation, where the owner can accept it or request a revision; the customer decisions also appear as messages. Payments, confirmed bookings, and event delivery are not persisted workflows. Confirm the actual API boundary before claiming a workflow is end to end.
- `src/lib/api.ts` owns the current HTTP wrapper and endpoint calls. It sends cookies with `credentials: "include"` and accepts a Firebase token only for relevant identity exchanges. Match request/response changes to the API's `createRoute` schemas and `profile.ts` mapping. Admin conversations use a 15-row cursor page with `nextCursor`; the admin Messages sidebar loads more pages on scroll and refreshes the first page for recent activity. Both message lists show event type for linked requests and last update. Linked event fields derive from `booking_requests` and package names from the current linked package; general threads have no editable event context. Active request threads stay open without a known event end, then expire 24 hours after a known end. Declined or cancelled requests expire 24 hours after the event end, or after creation when no end is known. Pending chat changes do not extend expiry; `expiresAt` is null while an active request has no known end. Expired linked threads remain closed. Booking-linked threads fetch the full request through a role-authorized detail route and reuse `BookingDetails`; the customer view is read-only. AI replies and guest chat are deferred. Booking package reads use `GET /v1/admin/booking-requests/{id}/package` or the owning customer route; the admin POST/PUT custom-package save includes both booking and package timestamps and returns the updated booking and package. A `409` offers a refresh after confirmation. The shared editor also confirms discard, and dismissing either confirmation keeps the unsaved edits. Package DTOs use the `CatalogPackage` and `PackageContent` contracts, including `packageType`, private ownership, and a stored `description` edited in Package details and displayed on admin/public cards independently of canvas Markdown, plus ordered service assignments (`serviceId`, `name`, `role`, `sortOrder`, `archivedAt`). Admin reads include archived services; public reads omit them. Public lists accept optional `limit` and `offset` and return `nextOffset`. `POST /v1/admin/packages` creates and publishes; `PATCH /v1/admin/packages/{id}` saves edits with `expectedUpdatedAt`. Package responses do not include a version ID. Services and venues are flat DTOs containing current content and timestamps (`id`, `archivedAt`, `createdAt`, `updatedAt`, and `publishedAt`); service DTOs also include the first canvas photo as derived `imageUrl`. Their direct create and full-content update routes save public active records; updates use `expectedUpdatedAt`, while archive hides the record. No service/venue draft, publish, history, or version-ID endpoints exist. Each has one catalog page; omitted `sections` preserve saved content. Public service `imageUrl` selects the first canvas photo. Package canvas uploads use multipart FormData at `/v1/admin/catalog-media`; pending uploaded assets are attached by a later catalog save, while saved uploads are served from `/v1/catalog-media/{id}`. Photo and video widgets are upload-only; external URLs and hosted-player embeds are rejected. Built-in sample photos remain supported for seeded packages. Services carry no package list in their own DTO; assignment is read from the package side.
- Shared catalog media widgets keep their canvas body to a photo/video preview. Empty Add a photo/Add a video buttons open the appropriate file chooser directly and reuse the editor validation and local preview; the three-dot settings remain available. `pages/PackageMediaSettings.tsx` provides the native modal opened by a three-dot widget button; it owns file selection hints, image description, caption, and video autoplay controls. These edits remain local until the owning catalog Save action. The shared editor receives entity-specific metadata, validation, persistence, and preview callbacks; public and admin details reuse `CatalogSections.tsx` and the service/venue canvases in `CatalogPreview.tsx`. `PackagePreview.tsx` suppresses captions/autoplay in editing mode; customer rendering honors saved video autoplay using muted inline video with native controls.
- `src/lib/auth.tsx` owns `AuthProvider`, session restoration through `GET /me`, and sign-in/sign-out state. `src/lib/firebase.ts` configures optional Firebase browser sign-in with in-memory persistence. Read `AuthPage.tsx` and `SignInMethods.tsx` when changing login or linking UI.
- Browser forms may mirror shared field and photo-count constraints for timely feedback, but the API route schemas enforce accepted values. Use `@event-management/contracts/limits/*` for mirrored constants and keep HTTP request-body caps server-side; see the [shared limits guidance](../../limits/SKILL.md).
- The database profile and role returned by the API determine whether the app shows the System Administrator, staff, or customer area. UI state is not authorization; protected API operations must check access server-side.
- `PUBLIC_API_URL` and optional Firebase browser variables are described in `apps/web/.env.example`. Keep secret service-account values on the API side.

For auth changes, trace the user action through UI, client request, API route, session, and restored page state. Test failure paths as well as the successful path.
