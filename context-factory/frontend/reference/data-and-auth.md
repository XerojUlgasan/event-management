# Client data and authentication

- `apps/web/src/components/app/data.ts` retains unrelated demo/navigation data. Package cards and admin catalog editing use `src/lib/api.ts` and `/v1/packages`; the standalone admin Venues screen uses the versioned draft/publish/archive venue catalog API. Published venues appear on the public `/` page and in its View more overlay. Customer and admin messages use `/v1/messages` and `/v1/admin/conversations`. Package booking requests use `/v1/booking-requests` and appear in customer My events and the manager request queue. The initial request records a preferred date and estimated event length; exact times and preferred location may be null. The manager queue uses status and preferred-date filters, a monthly count calendar, and cursor-paged requests in batches of 50; staff see the same queue without status editing. Preferred location is independent of the venue catalog. Quotes, payments, confirmed bookings, and event delivery are not persisted workflows yet. Confirm the actual API boundary before claiming a workflow is end to end.
- `src/lib/api.ts` owns the current HTTP wrapper and endpoint calls. It sends cookies with `credentials: "include"` and accepts a Firebase token only for relevant identity exchanges. Match request/response changes to the API's `createRoute` schemas and `profile.ts` mapping. Package and service catalog calls use typed DTOs here; the public list calls accept optional `limit` and `offset` and return `nextOffset`. Package responses include included and optional service assignments. Service previews load `GET /v1/services/:id/packages` to find current published packages with an included assignment to that service. Service images use external HTTPS URLs.
- `src/lib/auth.tsx` owns `AuthProvider`, session restoration through `GET /me`, and sign-in/sign-out state. `src/lib/firebase.ts` configures optional Firebase browser sign-in with in-memory persistence. Read `AuthPage.tsx` and `SignInMethods.tsx` when changing login or linking UI.
- Browser forms may mirror shared field and photo-count constraints for timely feedback, but the API route schemas enforce accepted values. Use `@event-management/contracts/limits/*` for mirrored constants and keep HTTP request-body caps server-side; see the [shared limits guidance](../../limits/SKILL.md).
- The database profile and role returned by the API determine whether the app shows the System Administrator, staff, or customer area. UI state is not authorization; protected API operations must check access server-side.
- `PUBLIC_API_URL` and optional Firebase browser variables are described in `apps/web/.env.example`. Keep secret service-account values on the API side.

For auth changes, trace the user action through UI, client request, API route, session, and restored page state. Test failure paths as well as the successful path.
