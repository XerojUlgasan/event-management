# Pages and application structure

- Astro runs with `output: "server"` and the Node adapter. Public pages in `apps/web/src/pages` render catalog HTML on each request and load CSS only. `/login` and `pages/app/` mount `components/app/App.tsx` with `client:only="react"`. React owns authentication and the workspaces. Check package scripts, configuration, and those entries together before changing architecture claims.
- Public catalog pages are `/`, `/about`, `/packages`, `/services`, `/venues`, and `/{slug}` detail pages. The separate `/catalog` route and old 3D `/landing` page have been removed.
- `components/app/App.tsx` wires auth for `/login` and `/app`. `GET /me` selects the admin, staff, or customer shell, and an unmatched role path redirects to that shell's home. `AppShell.tsx`, `Sidebar.tsx`, `pages/`, `staff/StaffWorkspaceShell.tsx`, and `customer/CustomerDashboard.tsx` contain the workspace UI. Catalog overlays stay inside `/app`.
- The System Administrator sidebar includes a combined Staff & Customers directory backed by `/v1/admin/users`, with read-only detail drawers. Staff profiles use `staff/StaffWorkspaceShell.tsx`: Event days at `/app/events` combines a calendar with a searchable table and All/Open/Responded filters; Assigned to me at `/app/assignments` shows persisted assignment cards, including cancelled history. Both use `lib/data/event-days.ts` and a shared `Drawer` composition for schedules, responses, own assignment, and confirmed team. Availability writes use the returned event-day DTO; reads refresh on focus and every minute, while a timer closes controls at the deadline. The old sample events, checklist, and staff mock data were removed. Accepted admin booking details compose `staff/AdminEventDays.tsx` for day creation, staffing responses, team selection, cancellation, and movement. `MonthCalendar` from `@event-management/ui` supplies both the staff date grid and admin booking calendar; admin counts use every requested date once per request (legacy requests fall back to the recorded preferred date), while staff counts use operational event-day dates. Each caller owns date selection, filters, and API requests. Staff navigation and layout stay app-specific in `staff-workspace.css`. Staff can read booking requests through the API and public catalog endpoints expose published records, but this workspace does not currently render those views.
- The admin Packages page creates and edits complete, directly published package records in a canvas editor. Package details include an editable catalog description used by both admin and public cards, maximum guests, fixed price, and sections with photo, Markdown, and video widgets; Save creates or updates the current record. There is no package draft or publish workflow. Services and Venues reuse `pages/CatalogEditor.tsx` for sections with draggable/resizable photo, Markdown, and video widgets, media settings, and customer-page/admin-card previews. They are flat records: Save creates a public active record, and edits replace its full content using `expectedUpdatedAt`; archive hides it. Service details require a catalog description, positive whole-peso hourly rate, and a canvas photo. Venue details require name, location, description, and a positive maximum guest count; photos are optional. Migrated service rates and venue guest limits may be null for reads but must satisfy current save validation. The flat-catalog migration preserves current published content or archives latest content when none was published; existing archives remain hidden. Back up before deployment if service/venue history matters. Google Maps pinning is deferred until an API key is available.
- On the public `/` page, featured packages, services, and venues appear in that order. View more links to the matching list page, and each card links to `/packages/{slug}`, `/services/{slug}`, or `/venues/{slug}`. The slug comes from the title. Titles are unique, including archived records, so renaming a title changes its public URL. Service and package catalogs are independent; packages do not have structured service assignments.
- In the admin workspace, Packages, Services, and Venues share the `pages/CatalogCard.tsx` card layout and compact footer actions, active/Archives tabs, search, and responsive card grid. Services show hourly rate; venues show location and capacity. Preview, archive, and eligible delete actions live in the three-dot menu, with Edit beside it. The active tabs omit archived records; the Archives tabs show them from the admin catalog responses. These tabs do not appear in the customer workspace.
- Both signed-in workspaces open Account settings from the user menu. The customer Messages tab and the admin Messages workspace share PostgreSQL-backed human conversations through `/v1/messages` and `/v1/admin/conversations`. Both poll every five seconds, show unread counts and last-update times, and mark the other side's messages read when a thread is opened. A booking-linked conversation shows an info icon that opens the same requested-date and per-day details used in My events and Bookings; the customer can enter times for eligible unscheduled days, while admin status controls stay separate.
- The public package page places Book now directly under the price and guest count. That link goes to `/login?book={slug}` and does not render the booking form in the public HTML. After sign-in, the form in `/app` collects event type, one requested date or a Multi-day list, contact person, phone, and optional notes. Multi-day needs at least two distinct dates; dates may be nonconsecutive and are submitted chronologically. The current-tab draft preserves mode, date rows, other fields, and timezone through sign-in, then requires explicit review. Exact times are entered later by the owner from My events or linked-conversation details; the form reports “Time to be confirmed” until both times are saved. Dates and local times use the booking timezone, and an overnight end can be on the next date. Legacy requests continue to show only their recorded preferred date and estimate when the full date list is unknown. Admin Bookings counts each requested date once per request, applies the same status filter to counts and results, and filters a request once when any requested date matches; the table shows a compact summary and details show per-day times and operational schedule state. In accepted booking details, requested-date rows appear automatically, including rows waiting for customer times. The administrator selects one shared 1–4-calendar-day deadline choice and previews the end-of-calculated-date cutoff in the booking timezone for each requested or current scheduled date, then applies it for the request. The API creates and links each ready operational day using the requested date and exact saved times, while updating current scheduled-day deadlines atomically. Closed windows stay closed, expired openings remain closed, and moved/cancelled history stays intact. Dates still waiting for times are skipped and require applying the choice again once saved; no future policy is stored. Acceptance and time saving alone do not create a day; new requests expose no manual day, date, or schedule-time entry. The manual schedule form is reserved for legacy requests with no requested-day list; legacy opening, movement, and reopening use the same 1–4-day choice. These steps do not reserve a date or confirm a booking; staff views contain operational event days, never unscheduled requested dates.
- Keep page-specific composition and content in `apps/web` while reusing presentation from `@event-management/ui`. Every UI change must follow the [package reuse workflow](../../shared/shared-packages.md#required-workflow-for-every-ui-change) and load the [packages skill](../../packages/SKILL.md), including when no package file changes.
