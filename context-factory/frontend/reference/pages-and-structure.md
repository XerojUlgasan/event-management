# Pages and application structure

- Astro serves the HTML shell through `apps/web/src/pages/index.astro`, imports `styles/app.css`, and mounts `components/app/App.tsx` with `client:only="react"`. React owns the application screens, authentication state, and in-page view switching. Check package scripts, configuration, and that entry point together before changing architecture claims.
- The public catalog lives in sections and View more overlays on `/`. The separate `/catalog` route and old 3D `/landing` page have been removed.
- `components/app/App.tsx` wires auth and selects public, sign-in, admin, or customer views. `AppShell.tsx`, `Sidebar.tsx`, `pages/`, and `customer/CustomerDashboard.tsx` contain the corresponding workspace UI.
- The System Administrator sidebar includes a combined Staff & Customers directory backed by `/v1/admin/users`, with read-only detail drawers. Staff have a separate read-only workspace for booking requests and published packages and services.
- The admin Packages page creates and edits complete, directly published package records in a canvas editor. Package details include an editable catalog description used by both admin and public cards, maximum guests, fixed price, ordered service assignments marked included or optional, and sections with photo, Markdown, and video widgets; Save creates or updates the current record. There is no package draft or publish workflow. Services and Venues reuse `pages/CatalogEditor.tsx` for sections with draggable/resizable photo, Markdown, and video widgets, media settings, and customer-page/admin-card previews. They are flat records: Save creates a public active record, and edits replace its full content using `expectedUpdatedAt`; archive hides it. Service details require a catalog description, positive whole-peso hourly rate, and a canvas photo. Venue details require name, location, description, and a positive maximum guest count; photos are optional. Migrated service rates and venue guest limits may be null for reads but must satisfy current save validation. The flat-catalog migration preserves current published content or archives latest content when none was published; existing archives remain hidden. Back up before deployment if service/venue history matters. Google Maps pinning is deferred until an API key is available.
- On the public `/` page, featured packages, services, and venues appear in that order. Each View more control opens an overlay with the full paged catalog. Cards open full-screen detail previews, and closing a detail returns to the catalog overlay. Package catalogs can attach catalog services as included or optional; the public package detail lists them. Service and venue catalogs remain independent of each other.
- In the admin workspace, Packages, Services, and Venues share the `pages/CatalogCard.tsx` card layout and compact footer actions, active/Archives tabs, search, and responsive card grid. Services show hourly rate; venues show location and capacity. Preview, archive, and eligible delete actions live in the three-dot menu, with Edit beside it. The active tabs omit archived records; the Archives tabs show them from the admin catalog responses. These tabs do not appear in the customer workspace.
- Both signed-in workspaces open Account settings from the user menu. The customer Messages tab and the admin Messages workspace share PostgreSQL-backed human conversations through `/v1/messages` and `/v1/admin/conversations`. Both poll every five seconds, show unread counts and last-update times, and mark the other side's messages read when a thread is opened. A booking-linked conversation shows an info icon that opens the existing booking details dialog.
- The shared published package preview offers Book now on the public page, catalog overlay, and customer surfaces. Signed-in customers submit the short inquiry directly; a signed-out visitor keeps a draft in the current browser tab through sign-in and explicitly reviews it before submission. The form collects an event type (Birthday, Wedding, Corporate, or a custom description), preferred date, approximate event length, contact person, and phone. More than one week requires an exact day count; length may be unspecified. Contact person is always editable and prefills from the profile when available. Guest count is deferred to staff follow-up. Customer My events and manager Bookings list the same persisted booking requests; they do not represent confirmed events.
- Keep page-specific components and content in `apps/web`. Use `@event-management/ui` for reusable presentational components; consult the packages skill before changing that package.
- Check the root README's [product scope](../../../README.md#product-scope) and [current implementation](../../../README.md#current-implementation) before implementing business workflows. Intended scope, mock screens, and demo data are not proof of backend implementation.
