# API verification

- `pnpm --filter @event-management/api test:quotations` runs the quotation API against a disposable migrated database. It covers JSONB items/server arithmetic, base-only offers, permissions, revision tokens, financial history across package/event edits, explicit admin repricing revisions, adjustment review and atomic linked-conversation delivery. Customer acceptance/revision endpoints must be unavailable without writing quotation or audit rows. Customer chat feedback must leave quotation and booking/scheduling state unchanged; historical accepted offers must remain readable and revisable by an admin. Injected transaction failures check rollback; ordinary passing responses do not establish rollback by themselves.
- `pnpm --filter @event-management/api test:proposal-migration` migrates a populated current baseline and checks retained catalog/inquiry/scheduling/conversation data, private ownership constraints, JSONB arithmetic/order, message booking linkage and new-table RLS/grants. It does not apply the migration to the configured application database.

- `pnpm --filter @event-management/api test:event-days` exercises staffing routes against a UUID-named disposable local PostgreSQL database. It covers role permissions, accepted requests, timezone/overnight schedules, response deadlines, separate availability/assignment records, coordinator and overlap protection, cancellation/movement history, and requested-day staffing. For new requests it checks the shared 1–4-day batch choice, booking-timezone end-of-calculated-date cutoffs (including year boundaries), automatic creation from exact saved times, atomic linking/deadline updates, missing-times reapplication, preservation of closed windows and moved/cancelled history, and stale/duplicate/concurrent-write rejection. It also covers legacy manual creation and day-level opening/movement/reopening with `daysBefore`; unscheduled dates never appear as staff openings or assignments. It does not establish browser or hosted-provider behavior.

- `pnpm --filter @event-management/api check` runs TypeScript without emitting files; `pnpm db:validate` checks Prisma schema configuration.
- The closest behavior suite for auth is `pnpm --filter @event-management/api test:auth`. Its source is `apps/api/tests/auth.test.ts`: it runs route requests against a disposable local PostgreSQL database and Firebase Auth emulator. It requires Firebase CLI on `PATH`, local PostgreSQL, and permission to create a test database. Read the setup and teardown before changing it or running it with unusual database settings.
- Keep new assertions about observable route behavior: status, body, cookie/session result, database result, and OpenAPI contract where relevant. Extend the existing suite for auth changes. For a new feature area, add a focused behavioral test matching its actual dependencies.
- `pnpm --filter @event-management/api test:booking-requests` creates a UUID-named disposable local PostgreSQL database, applies migrations, and drops only that test database. It covers date/mode validation, atomic request creation, per-day time validation and saving, owner/status permissions, stale and concurrent writes, timezone/overnight and repeated daylight-saving times, calendar counts/status filters, duplicate-free later-date pagination, and migration preservation of legacy requests and related operational records.
- `pnpm --filter @event-management/api test:packages`, `test:messages`, and `exec tsx --test tests/seed.test.ts` create UUID-named disposable local PostgreSQL databases, apply migrations, and drop only those test databases. The package suite uses a local fake Storage API for media paths; it does not verify a configured Supabase Storage bucket. Read test setup and teardown before running these suites.
- A type check does not establish that a route works with PostgreSQL, the emulator, or a browser. Report which boundaries were actually exercised.

- `pnpm --filter @event-management/api exec tsx --test tests/flat-catalog-migration.test.ts` applies migrations to a disposable database and checks published-content selection, draft-only archives, selected canvas/media retention, owner constraints, and removal of service/venue version tables.

- `pnpm --filter @event-management/api exec tsx --test tests/catalog-cleanup-migration.test.ts` proves the catalog-field cleanup preserves retained records, guest limits, snapshots, messages, and canvas media while removing obsolete columns.

- `pnpm --filter @event-management/api test:rls` applies migrations to a disposable local database and checks RLS coverage, retained data, server access, and removal of `PUBLIC` table grants. When `anon` and `authenticated` exist, it also proves read and `TRUNCATE` denial for both roles. Those subtests explicitly skip on ordinary Compose databases without Supabase roles; run against the local Supabase connection to cover them. The suite does not alter the configured application database or create shared roles.

The event-day suite also covers private checklist drafts, immediate send/read/edit, all task fields and ordering, server completion times/reopening, deleting the last task, unauthorized callers, immutable metadata, unavailable acceptance routes, stale/concurrent saves/sends, JSONB constraints and field/count limits, Unicode transport size, coordinator renewal/demotion/cancellation/replacement, day movement/cancellation, both parent-cancellation paths, injected rollback and an edit/reassignment race. It checks new-table RLS/grants, OpenAPI registration, populated-baseline migration preservation, and the Edge route-family dispatcher with the same operations/body caps (in-process JavaScript, not hosted Deno runtime). These are disposable database/API checks, not browser or hosted evidence.
