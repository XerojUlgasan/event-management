# API structure and routes

## Event-day staffing

`controllers/event-days/`, `services/event-days/`, and `data/event-days/` own day staffing. Node and Edge mount the same routes. System Administrators list through `/v1/admin/event-days`; legacy manual creation uses that route, while requested-date day creation and deadline updates use `POST /v1/admin/event-days/apply-response-deadlines`. They open/close responses through `/{id}/staffing`, confirm/cancel staff through `/{id}/assignments/{staffId}`, and cancel/move days through `/{id}/cancel` and `/{id}/move`. Staff list openings at `/v1/staff/event-days`, list their assignments at `/v1/staff/assignments`, and put their response at `/v1/staff/event-days/{id}/availability`.

Writes lock current state; creating/opening staffing, responding, confirming assignments, and moving days require an accepted booking request. Cancellation remains available to clean up existing staffing after a request leaves accepted status. Cancelling a booking request cancels its scheduled days and confirmed assignments in the same transaction. Opening requires a future response deadline; expired openings are returned as closed and reject responses. Event-day dates must match the start in the booking timezone; full timestamp ranges support overnight schedules. Staff eligibility uses database role `staff`. Confirming requires a closed response window and an available response, checks full-range overlaps under a staff lock, and permits only one confirmed coordinator per day. A staff member already confirmed on the same day record cannot respond available until that assignment is cancelled. Day cancellation/movement cancels assignments transactionally and preserves history; movement links a fresh replacement under the same booking. None of these actions confirms a booking. Deadline inputs for opening, moving, and reopening are `daysBefore` choices of 1–4 calendar days, not raw timestamp values; schedule and response-window writes advance the booking revision.

For requests with non-NULL `requested_days`, `POST /v1/admin/event-days/apply-response-deadlines` accepts the strict JSON body `{ bookingRequestId, daysBefore, expectedUpdatedAt }`; `daysBefore` is 1, 2, 3, or 4. Under the parent booking lock and expected revision, the API atomically creates, links, and opens operational days for every unlinked requested date with saved times, and recalculates deadlines for current `scheduled` operational days using their current dates (including replacement dates). Each deadline is 23:59:59.999 at the end of the date that many calendar days before the event date, interpreted in the booking timezone. Thus one choice applies consistently across the request, including dates across a month or year boundary. The response is `{ eventDays }`. Any invalid/past deadline needed for a newly opened or currently open day rejects the whole transaction; stale revisions also return `409`. Dates without both saved times are skipped; administrators must apply the choice again after times arrive. The choice is not persisted as a policy for future dates. Closed staffing stays closed when its deadline is updated, and an expired open window remains closed; cancelled or moved history rows are not rewritten. New requested-date days always use the saved customer date, exact saved instants, and booking timezone; acceptance and time saving alone do not create an operational day. For requests with SQL `NULL` `requested_days`, `POST /v1/admin/event-days` retains legacy manual scheduling; it rejects new requests with requested-day data. Legacy open creation, movement, and reopening use `daysBefore` too. Customer dates and times stay locked after scheduling. Moving or cancelling a day preserves the association and existing event-day history; the booking DTO exposes the current `operationalSchedule` for that date, following replacement links and reflecting cancellation. Requested dates alone never appear as staff openings or assignments; staff routes read operational `events_day` records.

## Existing domains

Catalog widgets expose `autoplay` as a boolean defaulting to false. Only video widgets can set it true; request validation and the `catalog_widgets_video_autoplay` database constraint enforce this. Package section reads and direct saves include the field.

- `apps/api/src/index.ts` starts the Node server. `src/app.ts` builds the `OpenAPIHono<HonoEnv>` app, configures CORS and request guards, injects `db`, mounts controller groups at `/v1`, and serves `/openapi.json`.
- `src/controllers/<domain>/index.ts` registers routes and middleware. Each operation has a kebab-case verb–entity file exporting `<operation>Route` and `<operation>RouteHandler`; the route defines method, path, request and response schemas, while the handler maps validated input and service outcomes to HTTP responses. The active domains are `auth/`, `packages/`, `catalog-media/`, `services/`, `messages/`, `booking-requests/`, `venues/`, `users/`, and `health/`.
- `src/services/<domain>/<verb>-<entity>.ts` owns business rules and coordinates transactions and data calls. Exports use the `<operation>Service` suffix. A service is optional for an operation with no business work, such as health.
- `src/data/<domain>/<verb>-<entity>.ts` owns focused Kysely queries and accepts a database client or transaction. Exports use the `<operation>Data` suffix. `src/db/` remains the shared connection, generated types, and database setup area.
- `src/utils/` holds reusable primitives; auth-specific and package-specific helpers can use `utils/auth/` and `utils/packages/`. `src/constants/http.ts` holds API-only HTTP body caps; shared domain limits live in `packages/contracts/src/limits/`. `src/middleware/` holds shared request authentication middleware; `src/types/hono.ts` defines typed context variables.
- Packages, services, and venues are flat, directly saved records whose canvas uses the reusable catalog-page, section, widget, and media tables. Each service or venue has one page. Photo/video widgets accept Supabase Storage uploads only, plus the built-in seeded sample photos.
- Files and folders use kebab-case; functions, variables, and Zod schemas use camelCase; types and classes use PascalCase; PostgreSQL tables and columns use snake_case. Keep the current API JSON contract aligned with its consumers when changing response fields.

- Package catalog controllers include `/v1/packages` and `/v1/admin/packages`. `POST /v1/admin/packages` creates and publishes complete content immediately; `PATCH /v1/admin/packages/{id}` saves the complete content using `expectedUpdatedAt` and returns `409` for stale edits. Packages have no draft, publish, or version-history endpoints. They store an editable catalog `description` (up to 4,000 characters) independently from canvas Markdown; public/admin reads return it and omitted description on legacy edits preserves the saved value. They store positive `max_guests` and a required fixed price as whole pesos; the API represents price in centavos as `{ kind: "fixed", currency: "PHP", amountMinor }` and requires `amountMinor` divisible by 100. `POST /v1/admin/packages/{id}/archive` hides a package from public reads; deletion returns `409` if a booking request references it.
- Catalog-media routes let a System Administrator upload a pending file at `POST /v1/admin/catalog-media` and discard an unreferenced upload at `DELETE /v1/admin/catalog-media/{id}`. A successful package, service, or venue save attaches uploaded media IDs to catalog widgets; public reads stream only media referenced by published, nonarchived catalog content through `GET /v1/catalog-media/{id}`. External photo/video URLs are rejected by the catalog API and database constraints.
- Service catalog controllers include `/v1/services` and `/v1/admin/services`; venue routes use the matching `/v1/venues` and `/v1/admin/venues` paths. Public package and service lists accept optional `limit` (1–15) and `offset`, returning `nextOffset`; no `limit` retains the full-list response. Services and venues are flat records with one canvas page each. `POST /v1/admin/services` and `POST /v1/admin/venues` create public active records directly. `PATCH /v1/admin/services/{id}` and `/v1/admin/venues/{id}` replace full content and require `expectedUpdatedAt`; stale or archived edits return `409`. `POST /v1/admin/services/{id}/archive` and `/v1/admin/venues/{id}/archive` hide records from public reads. Eligible deletion uses `DELETE /v1/admin/services/{id}` or `DELETE /v1/admin/venues/{id}`. DTOs contain content and `id`, `archivedAt`, `createdAt`, `updatedAt`, and `publishedAt`; service DTOs also carry derived `imageUrl` from the first canvas photo. There are no service/venue draft, publish, history, or version-ID contracts. Service saves require name, description, positive whole-peso hourly rate, and a canvas photo. Venue saves require name, location, description, and a positive maximum guest count; photos are optional. Migrated nullable hourly rates and venue guest limits remain readable. Optional omitted `sections` preserve the existing canvas on update. Package-service assignments and the related-packages route are not part of the package contract.
- Messaging controllers cover customer `/v1/messages/conversation` and System Administrator `/v1/admin/conversations` paths. The admin list includes conversations without messages, returns up to 15 per page with `nextCursor`, and orders by `updated_at` then ID descending. Customers can have unbound conversations and conversations linked to booking requests; messages have `read_at`, and customer routes never accept another customer's conversation id. Messages have human `customer` or `admin` senders; AI replies, guest import, handoff, and takeover routes are deferred. Conversation status is `active` or `closed`. Linked package and event fields derive from the booking request; general threads have no context endpoint. Expiry uses the parent request's `ends_at` when known, or its creation time otherwise. Requested-day timestamps do not create a continuous parent interval or update `ends_at`, so a new request with no parent end expires from creation. Expired linked threads remain closed, while customer messages can reopen general threads.
- Booking request controllers cover customer `POST /v1/booking-requests`, `GET /v1/booking-requests/mine`, owner-only `GET /v1/booking-requests/{id}` and cancellation, plus staff-readable list and `GET /v1/admin/booking-requests/{id}` and System Administrator status updates under `/v1/admin/booking-requests`. Both detail routes include status history. Creation accepts `packageId`, optional `packageUpdatedAt`, `eventType`, `durationMode`, `requestedDays` date entries, `timeZone`, contact details, and optional notes. `one_day` requires exactly one date; `multi_day` requires at least two distinct dates. Nonconsecutive dates are allowed, validated as today or future in the booking timezone, and sorted before persistence. The API atomically stores the request, status history, conversation, and JSONB `requested_days` entries shaped as `{date, startsAt: null, endsAt: null}`. `preferred_date` remains the earliest selected date for compatibility; the JSON list is authoritative for new requests. Creation does not accept `packageVersionId`; a stale supplied package timestamp returns `409`. Requests continue to snapshot package name, fixed price, and guest maximum. New intake does not use legacy estimated-duration fields; the response retains them for old records. SQL `NULL` in `requested_days` identifies a legacy request: `requestedDays`, `durationMode`, and `requestedDayCount` remain `null`, recorded preferred date/estimate/timestamps remain readable, and the API does not fabricate dates. Guest count is optional and saved as null when omitted, with `outOfRange` false. Acceptance is for processing only; it is not a confirmed booking or date hold.
- An owner can save later times with `PATCH /v1/booking-requests/{id}/requested-days/{date}/times`. The body contains offset-bearing `startsAt` and `endsAt` instants plus the request's `expectedUpdatedAt` revision. Only the owning customer can edit; requests must be `under_review`, `needs_details`, or `accepted`, the date must belong to the request, and no operational schedule may already be linked. Start and end are required together, end must be later, start must fall on the requested date in the booking timezone, and end may fall on that date or the next date. Repeated daylight-saving local times are rejected. The API locks the parent request, updates only the target JSON entry, preserves all others, and advances the revision; it does not create an operational day or open staffing. Stale writes return `409`. Legacy requests with SQL `NULL` have no editable requested-day entry.
- The staff-readable booking request list accepts `status`, `preferredDate`, `limit` (1–50), and `cursor`; filtered or paged responses include `nextCursor`, while an unfiltered request retains the existing full list response. `preferredDate` matches any requested date for new requests and falls back to recorded `preferred_date` only for legacy rows. An `EXISTS` predicate keeps one row per request during filtering and pagination. `GET /v1/admin/booking-requests/calendar` takes `month` (`YYYY-MM`) and optional `status`, returns one count per request per requested date, and applies the same status filter as the list; legacy rows count against their recorded preferred date. Each returned `requestedDays` entry includes the stored date/times, optional `eventDayId`, and an `operationalSchedule` field with the current linked event-day date, instants, timezone, and status, or `null` when no schedule exists. `durationMode` and `requestedDayCount` are derived from the array length.
- Validate incoming fields through route schemas and read JSON with `c.req.valid("json")`. Keep OpenAPI responses consistent with actual handler status codes and bodies. `src/app.ts` applies an allowed-origin check to browser writes and server-side HTTP body caps: 16 KiB for auth, admin conversations, booking requests, and customer message paths; 3 MiB for admin package, service, and venue JSON; 25 MiB plus 64 KiB multipart overhead for catalog-media uploads. These request-body caps are API transport limits, separate from per-file and shared field constraints. See the [shared limits guidance](../../limits/SKILL.md).

For a new operation, use the matching domain folder in each layer. For example, `controllers/packages/create-package.ts` exports `createPackageRoute` and `createPackageRouteHandler`, `services/packages/create-package.ts` exports `createPackageService`, and `data/packages/create-package.ts` exports `createPackageData`. Register the route and handler in `controllers/packages/index.ts`. The flow is controller → service → data when business rules are involved; a simple controller can call data directly, and an operation with no database work need not have a data file. Keep existing JSON request and response field names unless the task explicitly changes the API contract and its consumers.

Check the affected route's OpenAPI output and behavior, especially if changing paths or response shapes consumed by `apps/web/src/lib/data/`.

- System Administrator access requires role `admin` and staff title `System Administrator`; role `staff` can read booking requests and published catalog, but cannot access administrative catalog, messages, directory, or writes.
- Venues are an independent flat catalog in `controllers/venues/`, `services/venues/`, and `data/venues/`, with direct create/update/archive operations. Public reads expose active, nonarchived records through the public Venues catalog. There is no package-to-venue link. Venue data includes name, location, description, maximum guest count and one photo/Markdown/video canvas page. Canvas media uses uploads. Saves allow zero photos but require a positive maximum guest count; migrated records may have null capacity and no photos for reads. Migration `20261102180000_flat_services_venues` retains current published content and metadata, or archives the latest content where no version was published; existing archives stay archived. It drops unselected version pages and both version tables, but does not delete uploaded media objects. Back up before deployment if history matters and inspect all pending migrations. Google Maps pinning is deferred until an API key is available. The cleanup migration drops package venue details and terms, including existing values. Booking-request preferred venue/location remains independent. A venue entry does not establish availability or a reservation.
