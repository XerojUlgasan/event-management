# API structure and routes

Catalog widgets expose `autoplay` as a boolean defaulting to false. Only video widgets can set it true; request validation and the `catalog_widgets_video_autoplay` database constraint enforce this. Package section reads and direct saves include the field.

- `apps/api/src/index.ts` starts the Node server. `src/app.ts` builds the `OpenAPIHono<HonoEnv>` app, configures CORS and request guards, injects `db`, mounts controller groups at `/v1`, and serves `/openapi.json`.
- `src/controllers/<domain>/index.ts` registers routes and middleware. Each operation has a kebab-case verb–entity file exporting `<operation>Route` and `<operation>RouteHandler`; the route defines method, path, request and response schemas, while the handler maps validated input and service outcomes to HTTP responses. The active domains are `auth/`, `packages/`, `catalog-media/`, `services/`, `messages/`, `booking-requests/`, `customization-requests/`, `venues/`, `users/`, and `health/`.
- `src/services/<domain>/<verb>-<entity>.ts` owns business rules and coordinates transactions and data calls. Exports use the `<operation>Service` suffix. A service is optional for an operation with no business work, such as health.
- `src/data/<domain>/<verb>-<entity>.ts` owns focused Kysely queries and accepts a database client or transaction. Exports use the `<operation>Data` suffix. `src/db/` remains the shared connection, generated types, and database setup area.
- `src/utils/` holds reusable primitives; auth-specific and package-specific helpers can use `utils/auth/` and `utils/packages/`. `src/constants/http.ts` holds API-only HTTP body caps; shared domain limits live in `packages/contracts/src/limits/`. `src/middleware/` holds shared request authentication middleware; `src/types/hono.ts` defines typed context variables.
- Packages, services, and venues are flat, directly saved records whose canvas uses the reusable catalog-page, section, widget, and media tables. Each service or venue has one page. Photo/video widgets accept R2 uploads only, plus the built-in seeded sample photos.
- Files and folders use kebab-case; functions, variables, and Zod schemas use camelCase; types and classes use PascalCase; PostgreSQL tables and columns use snake_case. Keep the current API JSON contract aligned with its consumers when changing response fields.

- Package catalog controllers include `/v1/packages` and `/v1/admin/packages`. `POST /v1/admin/packages` creates and publishes complete content immediately; `PATCH /v1/admin/packages/{id}` saves the complete content using `expectedUpdatedAt` and returns `409` for stale edits. Packages have no draft, publish, or version-history endpoints. They store an editable catalog `description` (up to 4,000 characters) independently from canvas Markdown; public/admin reads return it and omitted description on legacy edits preserves the saved value. They store positive `max_guests` and a required fixed price as whole pesos; the API represents price in centavos as `{ kind: "fixed", currency: "PHP", amountMinor }` and requires `amountMinor` divisible by 100. `POST /v1/admin/packages/{id}/archive` hides a package from public reads; deletion returns `409` if a booking request references it.
- Catalog-media routes let a System Administrator upload a pending file at `POST /v1/admin/catalog-media` and discard an unreferenced upload at `DELETE /v1/admin/catalog-media/{id}`. A successful package, service, or venue save attaches uploaded media IDs to catalog widgets; public reads stream only media referenced by published, nonarchived catalog content through `GET /v1/catalog-media/{id}`. External photo/video URLs are rejected by the catalog API and database constraints.
- Service catalog controllers include `/v1/services` and `/v1/admin/services`; venue routes use the matching `/v1/venues` and `/v1/admin/venues` paths. Public package and service lists accept optional `limit` (1–15) and `offset`, returning `nextOffset`; no `limit` retains the full-list response. Services and venues are flat records with one canvas page each. `POST /v1/admin/services` and `POST /v1/admin/venues` create public active records directly. `PATCH /v1/admin/services/{id}` and `/v1/admin/venues/{id}` replace full content and require `expectedUpdatedAt`; stale or archived edits return `409`. `POST /v1/admin/services/{id}/archive` and `/v1/admin/venues/{id}/archive` hide records from public reads. Eligible deletion uses `DELETE /v1/admin/services/{id}` or `DELETE /v1/admin/venues/{id}`. DTOs contain content and `id`, `archivedAt`, `createdAt`, `updatedAt`, and `publishedAt`; service DTOs also carry derived `imageUrl` from the first canvas photo. There are no service/venue draft, publish, history, or version-ID contracts. Service saves require name, description, positive whole-peso hourly rate, and a canvas photo. Venue saves require name, location, description, and a positive maximum guest count; photos are optional. Migrated nullable hourly rates and venue guest limits remain readable. Optional omitted `sections` preserve the existing canvas on update. Package create/update/read accepts `services` as an ordered array of `{ serviceId, role }`, where `role` is `included` or `optional`; responses add the service `name`, `sortOrder`, and `archivedAt`. Archived services cannot be newly attached, but an existing assignment may be saved. Public reads omit archived services; admin reads include them. There is no related-packages route.
- Messaging controllers cover customer `/v1/messages/conversation` and System Administrator `/v1/admin/conversations` paths. The admin list includes conversations without messages, returns up to 15 per page with `nextCursor`, and orders by `updated_at` then ID descending. Customers can have unbound conversations and conversations linked to booking requests; messages have `read_at`, and customer routes never accept another customer's conversation id. Messages have human `customer` or `admin` senders; AI replies, guest import, handoff, and takeover routes are deferred. Conversation status is `active` or `closed`. Linked package and event fields derive from the current booking arrangement; general conversations have no context endpoint. A request-linked conversation stays open while the booking is active, closes 24 hours after a known event end, and stays open while a customization request is pending. Declined or cancelled requests use the event end or creation time. Expired linked threads remain closed, while customer messages can reopen general threads. Conversation responses report a nullable `expiresAt`; null means no automatic expiry while the condition holds.
- Booking request controllers cover customer `POST /v1/booking-requests`, `GET /v1/booking-requests/mine`, owner-only `GET /v1/booking-requests/{id}` and cancellation, plus staff-readable list and `GET /v1/admin/booking-requests/{id}` and System Administrator status updates under `/v1/admin/booking-requests`. Both detail routes include status history. Creation takes a date-only preference and estimated duration rather than requiring exact times. It accepts `packageId`, optional `packageUpdatedAt`, optional positive `guestCount`, and bounded free-text `preferredVenueLocation`; it does not accept `packageVersionId` or a venue foreign key. A supplied stale package timestamp returns `409`. Each request snapshots package name, fixed price, guest maximum, and ordered package inclusions in JSON; later package or service edits do not alter those fields. `more_than_1_week` requires `estimatedDurationDays` of at least 8; `undecided` remains valid. Guest count is optional and saved as null when omitted, with `outOfRange` false; older requests retain recorded counts. Exact start/end timestamps remain nullable for new inquiries. An accepted request is only accepted for processing; it is not a confirmed booking or date hold.
- Each booking request has one mutable arrangement returned as `arrangement`, separate from the immutable request snapshot. It stores event type, preferred date, estimated duration, exact start/end times, time zone, guest count, preferred venue, internal notes, editor, and timestamps, and computes `outOfRange` against the snapshotted package maximum (advisory only; null guest count stays in range). `PATCH /v1/admin/booking-requests/{id}/arrangement` requires a System Administrator, accepts partial fields with optional `expectedUpdatedAt` (stale returns `409`), rejects closed requests, and records `arrangement.updated` audit events with before/after metadata. Staff may read arrangements through booking responses but cannot edit them.
- Customization requests live in the separate `customization-requests` domain. Customers submit `POST /v1/booking-requests/{id}/customization-requests` for the eight contract types, with a bounded description and optional `conversationId`/`messageId` that must belong to the same booking and customer. Owner-only `PATCH /v1/customization-requests/{id}/withdraw` withdraws a pending request. System Administrators decide with `PATCH /v1/admin/customization-requests/{id}` using `approved` or `rejected`; rejection requires a reason. Staff and customers can read `GET /v1/admin/customization-requests` with `status`, `limit` (1–50), and `cursor`; only System Administrators can decide. Statuses are `requested`, `approved`, `rejected`, and `withdrawn`. Every write records an `audit_events` row. Decisions do not change the package price, confirm a booking, or reserve a date.
- Quotations live in `controllers/quotations/`, `services/quotations/`, and `data/quotations/`. System Administrators create/edit/send draft quotations under `/v1/admin/booking-requests/{id}/quotations` and `/v1/admin/quotations/{id}`; customers read the latest active quote under `/v1/booking-requests/{id}/quotation`, accept it at `/v1/quotations/{id}/accept`, or request a revision at `/v1/quotations/{id}/revision`. Quotes use PHP minor units, server-computed totals, monotonic versions, and `draft`, `sent`, `accepted`, and `superseded` states. Sending supersedes the prior sent version; acceptance does not confirm a booking or reserve a date. The admin quotation builder UI and chat rendering remain later phases.
- The staff-readable booking request list accepts `status`, `preferredDate`, `limit` (1–50), and `cursor`; filtered or paged responses include `nextCursor`, while an unfiltered request retains the existing full list response. `GET /v1/admin/booking-requests/calendar` takes `month` (`YYYY-MM`) and optional `status`, and returns counts grouped by preferred date for the whole month.
- Validate incoming fields through route schemas and read JSON with `c.req.valid("json")`. Keep OpenAPI responses consistent with actual handler status codes and bodies. `src/app.ts` applies an allowed-origin check to browser writes and server-side HTTP body caps: 16 KiB for auth, admin conversations, booking requests, customization requests, and customer message paths; 3 MiB for admin package, service, and venue JSON; 25 MiB plus 64 KiB multipart overhead for catalog-media uploads. These request-body caps are API transport limits, separate from per-file and shared field constraints. See the [shared limits guidance](../../limits/SKILL.md).

For a new operation, use the matching domain folder in each layer. For example, `controllers/packages/create-package.ts` exports `createPackageRoute` and `createPackageRouteHandler`, `services/packages/create-package.ts` exports `createPackageService`, and `data/packages/create-package.ts` exports `createPackageData`. Register the route and handler in `controllers/packages/index.ts`. The flow is controller → service → data when business rules are involved; a simple controller can call data directly, and an operation with no database work need not have a data file. Keep existing JSON request and response field names unless the task explicitly changes the API contract and its consumers.

Check the affected route's OpenAPI output and behavior, especially if changing paths or response shapes consumed by `apps/web/src/lib/api.ts`.

- System Administrator access requires role `admin` and staff title `System Administrator`; role `staff` can read booking requests, their arrangements and customization requests, the customization-request queue, and published catalog, but cannot decide customization requests or access administrative catalog, messages, directory, or other writes.
- Venues are an independent flat catalog in `controllers/venues/`, `services/venues/`, and `data/venues/`, with direct create/update/archive operations. Public reads expose active, nonarchived records through the public Venues catalog. There is no package-to-venue link. Venue data includes name, location, description, maximum guest count and one photo/Markdown/video canvas page. Canvas media uses uploads. Saves allow zero photos but require a positive maximum guest count; migrated records may have null capacity and no photos for reads. Migration `20261102180000_flat_services_venues` retains current published content and metadata, or archives the latest content where no version was published; existing archives stay archived. It drops unselected version pages and both version tables, but does not delete uploaded media objects. Back up before deployment if history matters and inspect all pending migrations. Google Maps pinning is deferred until an API key is available. The cleanup migration drops package venue details and terms, including existing values. Booking-request preferred venue/location remains independent. A venue entry does not establish availability or a reservation.
