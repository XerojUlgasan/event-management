# API structure and routes

- `apps/api/src/index.ts` starts the Node server. `src/app.ts` builds the `OpenAPIHono<HonoEnv>` app, configures CORS and request guards, injects `db`, mounts controller groups at `/v1`, and serves `/openapi.json`.
- `src/controllers/<domain>/index.ts` registers routes and middleware. Each operation has a kebab-case verb–entity file exporting `<operation>Route` and `<operation>RouteHandler`; the route defines method, path, request and response schemas, while the handler maps validated input and service outcomes to HTTP responses. The active domains are `auth/`, `packages/`, `services/`, `messages/`, `booking-requests/`, `venues/`, `users/`, and `health/`.
- `src/services/<domain>/<verb>-<entity>.ts` owns business rules and coordinates transactions and data calls. Exports use the `<operation>Service` suffix. A service is optional for an operation with no business work, such as health.
- `src/data/<domain>/<verb>-<entity>.ts` owns focused Kysely queries and accepts a database client or transaction. Exports use the `<operation>Data` suffix. `src/db/` remains the shared connection, generated types, and database setup area.
- `src/utils/` holds reusable primitives; auth-specific and package-specific helpers can use `utils/auth/` and `utils/packages/`. `src/constants/http.ts` holds API-only HTTP body caps; shared domain limits live in `packages/contracts/src/limits/`. `src/middleware/` holds shared request authentication middleware; `src/types/hono.ts` defines typed context variables.
- Package and service versions keep optional external HTTPS image URLs; venue versions keep ordered HTTPS photo URLs. The API has no image upload or image retrieval routes.
- Files and folders use kebab-case; functions, variables, and Zod schemas use camelCase; types and classes use PascalCase; PostgreSQL tables and columns use snake_case. Keep the current API JSON contract aligned with its consumers when changing response fields.

- Package catalog controllers include `/v1/packages` and `/v1/admin/packages`. Versions may have an external HTTPS image URL.
- Service catalog controllers include `/v1/services`, `/v1/services/{id}/packages`, `/v1/admin/services`. Public package and service lists accept optional `limit` (1–15) and `offset`, returning `nextOffset`; no `limit` retains the full list. The related-packages route returns current published packages with an included assignment to the visible service, including an older service version. Service versions carry category tags and an optional external HTTPS image URL. Package versions may hold UUID-identified included service or priced add-on assignments. Public reads expose only current published, nonarchived service offers.
- Messaging controllers cover customer `/v1/messages/conversation` and System Administrator `/v1/admin/conversations` paths. The admin list includes conversations without messages, returns up to 15 per page with `nextCursor`, and orders by `updated_at` then ID descending. Customers can have unbound conversations and conversations linked to booking requests; messages have `read_at`, and customer routes never accept another customer's conversation id. Messages have human `customer` or `admin` senders; AI replies, guest import, handoff, and takeover routes are deferred. Conversation status is `active` or `closed`.
- Booking request controllers cover customer `POST /v1/booking-requests`, `GET /v1/booking-requests/mine`, owner-only `GET /v1/booking-requests/{id}` and cancellation, plus staff-readable list and `GET /v1/admin/booking-requests/{id}` and System Administrator status updates under `/v1/admin/booking-requests`. Both detail routes include status history. Creation takes a date-only preference and estimated duration rather than requiring exact times or a venue. Exact start/end timestamps and preferred location remain nullable for new inquiries; older requests retain their recorded values. Requests retain the selected published package version and an audit history. An accepted request is only accepted for processing; it is not a confirmed booking or date hold.
- The staff-readable booking request list accepts `status`, `preferredDate`, `limit` (1–50), and `cursor`; filtered or paged responses include `nextCursor`, while an unfiltered request retains the existing full list response. `GET /v1/admin/booking-requests/calendar` takes `month` (`YYYY-MM`) and optional `status`, and returns counts grouped by preferred date for the whole month.
- Validate incoming fields through route schemas and read JSON with `c.req.valid("json")`. Keep OpenAPI responses consistent with actual handler status codes and bodies. `src/app.ts` applies an allowed-origin check to browser writes and server-side HTTP body caps: 16 KiB for auth, admin conversations, booking requests, and customer message paths; and 64 KiB for admin catalog JSON. These request-body caps are API transport limits, separate from shared field and file constraints. See the [shared limits guidance](../../limits/SKILL.md).

For a new operation, use the matching domain folder in each layer. For example, `controllers/packages/create-package.ts` exports `createPackageRoute` and `createPackageRouteHandler`, `services/packages/create-package.ts` exports `createPackageService`, and `data/packages/create-package.ts` exports `createPackageData`. Register the route and handler in `controllers/packages/index.ts`. The flow is controller → service → data when business rules are involved; a simple controller can call data directly, and an operation with no database work need not have a data file. Keep existing JSON request and response field names unless the task explicitly changes the API contract and its consumers.

Check the affected route's OpenAPI output and behavior, especially if changing paths or response shapes consumed by `apps/web/src/lib/api.ts`.

- System Administrator access requires role `admin` and staff title `System Administrator`; role `staff` can read booking requests and published catalog, but cannot access administrative catalog, messages, directory, or writes.
- Venues are an independent versioned catalog in `controllers/venues/`, `services/venues/`, and `data/venues/`, with draft, publish, and archive operations. Public reads expose only published, nonarchived venue entries through the public Venues catalog. There is no home-page venue preview or package-to-venue link. Existing active venues migrate as visible published entries; archived venues remain hidden. Venue data includes title (`name` in the API), location, description, minimum and maximum capacity, optional editable categories, and up to 10 external HTTPS photo URLs. Publishing a new venue allows zero photos but requires positive minimum and maximum capacity; migrated published entries may retain null capacity and no photos. Google Maps pinning is deferred until an API key is available. Keep the legacy package venue-details database field for existing values but omit it from package DTOs, screens, and publication requirements. Booking-request preferred venue/location remains independent. A venue entry does not establish availability or a reservation.
