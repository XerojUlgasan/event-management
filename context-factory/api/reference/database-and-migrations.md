# Database and migrations

- `apps/api/prisma/schema.prisma` and `prisma/migrations/` define schema changes. `prisma.config.ts` takes its connection URL from `src/db/config.ts`.
- The local Supabase CLI project is `apps/supabase`. `pnpm dev` starts that stack, serves the edge function, and runs the website against it. See the root [local Supabase setup](../../../README.md#local-supabase). `pnpm build:edge` bundles the Hono routers into `apps/supabase/functions/api` and loads a route family on request. `pnpm all`, the Node API, Prisma, seeds, and integration tests still use Compose PostgreSQL from `apps/api/compose.yaml`.
- Runtime route queries use Kysely through `src/db/client.ts` and focused files in `src/data/<domain>/`. Controllers receive `c.get("db")` and pass it to services; data functions accept it or a transaction. Database setup and seed commands remain in `src/db/`. The checked-in `src/db/types.ts` is generated from the migrated PostgreSQL database by `pnpm db:generate`. The generator includes `public.*` application tables and excludes Prisma history; it does not export Supabase internal schemas. Do not hand-edit generated DB types.
- For a schema change, edit the Prisma schema, create and review a migration with `pnpm db:migrate`, regenerate Kysely types with `pnpm db:generate`, then update affected queries and run `pnpm check`. `pnpm db:deploy` applies committed migrations; it does not create one.
- Read existing migrations as well as the Prisma schema when changing constraints or data behavior. For example, the users migrations add email normalization/uniqueness behavior beyond the model declaration.
- Every new application table must enable RLS and remove unused `PUBLIC`, `anon`, and `authenticated` table grants in its migration. See `20261109140000_enable_application_rls`: direct clients use Clemora's API, so there are no client policies; the API database role must own the tables or have `BYPASSRLS`. Supabase roles are optional on Compose PostgreSQL. The migration protects existing tables, including Prisma history when present, but does not automatically protect future tables. SQL-only access changes do not require Prisma model or Kysely type regeneration.
- `src/db/seed.ts` and `seed-admin.ts` are data setup commands, not migrations. The seed inserts three directly published package samples, a reusable catalog-page content tree, local account fixtures, demo conversations, and venue samples. It does not create service assignments or booking requests. Do not run a seed against a database without checking its target and impact.

Database commands use local settings from `apps/api/.env`. Use `.env.example` for variable names and keep values out of chat, docs, and logs.

Packages, services, and venues are flat, directly saved catalog records. Migration `20261102170000_package_description` adds a stored package description and backfills existing first-Markdown card excerpts without changing canvas content. Their pages use `catalog_pages`, `catalog_sections`, `catalog_widgets`, and `media_assets`, with exactly one package, service, or venue owner per page. Migration `20261102180000_flat_services_venues` preserves service/venue IDs, timestamps, current published metadata, and the selected canvas, then drops `service_versions` and `venue_versions` and unselected version pages. If there is no current published version, it preserves the latest content and archives the flat record; existing archives remain archived. Uploaded media objects are not deleted by the migration. Back up before deployment if version history matters, and inspect all pending migrations because `20261102130000_package_canvas` has a separate destructive impact. Services require a positive hourly rate and a canvas photo. Venues require a positive maximum guest count; photos are optional. Migrated records may have null legacy values for reads. Read [catalog media and image migrations](external-image-urls.md) before changing media schema or migration behavior.

Migration `20261102130000_package_canvas` intentionally recreates package persistence. It drops package versions and service assignments, deletes existing package records and booking requests/status history, and removes conversations/messages linked to booking requests. General conversations and their messages survive. Inspect and back up affected records before applying this migration to a database with data; `pnpm db:deploy` applies this committed data change but does not make it reversible.

See the root README's [catalogs and media](../../../README.md#catalogs-and-media) and [migration impact](../../../README.md#migration-impact) for shared `maxGuests` / `max_guests` names, retained inquiry snapshots, and cleanup migration `20261102190000_cleanup_catalog_fields`.
