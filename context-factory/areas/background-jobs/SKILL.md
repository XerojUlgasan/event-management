# Background jobs

Use this guide with [API](../api/SKILL.md) and the selected task workflow. Inspect the current implementation and its callers before changes; source and package scripts are authoritative. Starting a worker can process queued jobs and make paid provider calls.

## Ownership

- `apps/api/src/data/background-jobs/` owns queue SQL and short state-transition transactions.
- `apps/api/src/services/background-jobs/job-definitions.ts` registers payload schemas, handlers, and retry and timeout policy, and owns worker settings. `enqueue-job.ts` validates jobs and schedules them within the caller's transaction. `run-worker.ts` owns polling and concurrency, and `run-one-background-job.ts` claims, executes, heartbeats, and finishes one job.
- Job handlers live under `apps/api/src/services/background-jobs/handlers/`; the embedding workflow owns catalog preparation and provider operations. Package and service photos are chunks of their owner's embedding job. `process-image-message.ts` handles private-image validation/interpretation and the eligible conversation-scoped assistant turn for image-containing messages; text-only customer/guest replies stay in the synchronous send flow. Message data owns image-job projection, atomic enqueue and reply identity.
- `apps/api/src/workers/background-jobs.ts` is the supervised Node entry point. The HTTP Edge function does not host persistent polling. The [README](../../../README.md#configuration) describes local and hosted setup; consult package scripts before running them.
- The same entry point runs the [event completion check](../../business/event-days.md#event-completion) once per minute and on startup. It scans for due bookings and writes readiness with in-app alerts under the booking lock. Completion uses current schedule data and needs no queue entry per booking.

## Queue behavior

Catalog saves reconcile chunks and enqueue the owner in the same transaction when eligible chunks exist, without waiting for an embedding provider. Media promotion and cleanup retain their existing after-commit lifecycle. The Knowledge Catalog's manual **Index pending** action discovers all eligible pending/stale/withdrawn owners in a read snapshot, then ensures they are scheduled sequentially in separate short transactions. Each transaction locks the owner before any queue lock, reassesses current eligibility/freshness, and uses the queue's ensure-scheduled operation: pending/running jobs are returned untouched; only an idle owner still needing indexing gets a new job. Expired running jobs remain with lease recovery, and terminal failures permit a new attempt. Automatic saves keep their refresh enqueue semantics, including successors for real edits and pending retry reset. Its strict empty-object request returns `202` newly submitted, skipped, and failed counts without waiting for indexing or calling the provider or Storage; partial failures and interrupted committed prefixes are retryable. Page navigation after acceptance does not cancel queued work. Coverage remains chunk freshness, not queue progress. The `catalog:embed` CLI remains a separate provider-calling reconciliation path. See the [specification](../../../docs/specs/knowledge-catalog-background-indexing.md).

The registry defines `embed_package` with strict `{ packageId: UUID }`, `embed_service` with strict `{ serviceId: UUID }`, and `process_image_message` with strict server-bound `{ messageId: UUID, conversationId: UUID, aiVersion: nonnegative integer | null, suppressReply?: true }`. It sets a 3-second poll interval, three concurrent jobs per worker process, a 60-second lease with a 20-second heartbeat, 120-second embedding timeouts and a 240-second image-message timeout. Retry delays are 10 seconds, 60 seconds and 5 minutes; initial execution plus three retries allows four attempts. Invalid images are terminal. Policies live in code and changes also apply to queued jobs.

Queue transitions use a short global advisory transaction lock; provider calls occur outside queue transactions. A lease token fences heartbeat and completion, and expired leases are recovered. Pending jobs deduplicate by type and owner, while a running job can have one pending successor. Live leased claims for the same type and owner are serialized; an expired invocation can overlap a later claim until it honors cancellation. If an older running job fails or expires while a successor is pending, the older job fails as superseded and the successor remains. Leases provide at-least-once execution, so handlers must tolerate replay. Failed embedding chunks make the owner job retryable. Unknown job types remain unclaimed; invalid payloads fail terminally. Keep errors and logs bounded and sanitized.

Image-message jobs deduplicate by saved message ID. Claims serialize image jobs within a conversation and wait through earlier image-job retry backoff. Terminal failures release later image jobs; pending observations remain unavailable in model context. Customer/guest image jobs request a reply only when the captured AI version allows it; admin image jobs interpret without requesting a reply. Text-only customer/guest turns never create a job: the synchronous send flow waits, with a five-second abortable bound, for earlier pending/running image jobs before calling the assistant. A wait timeout returns the saved message with `assistantError`, without queueing the text turn. This wait does not serialize concurrent text turns or later image messages. Admin text stays immediate. Captured AI versions preserve takeover and off/on invalidation, and guest image jobs retain their original restricted capability after claim.

Image-message reads derive queued, interpreting, replying, completed, failed and suppressed outcomes from the existing job status and saved observations/reply. The payload captures AI version (null for interpretation-only jobs), message and conversation IDs; original guest/customer scope is derived from the saved human message and current conversation claim links. No separate processing table, image-status column or duplicated identity fields are needed. Authorized image-processing retries reuse the original message, uploads and job; they do not consume another guest slot. Retrying an old failed image turn after a later image job starts, or after a later reply is saved, repairs observations without publishing an obsolete answer; an inline text turn still in flight is outside that guard. Replies and handoff acknowledgements share a database-enforced unique trigger. Fence domain writes with the current lease as well as queue completion; cancellation alone cannot stop a stale handler. Existing validated observations survive retries, while a crash before observation persistence may repeat a provider call.

## Add or change a job type

1. Trace the initiating transaction, domain operation, side effects, owner identity, and failure behavior. Define a strict payload containing only necessary identifiers, and choose a deduplication key and recovery semantics.
2. Add the handler and register its payload schema, deduplication key, handler, retry delays, and timeout in `job-definitions.ts`; enqueue through `enqueue-job.ts` in the transaction that commits the triggering change.
3. Make handlers honor `AbortSignal` before side effects and pass it to cancellable operations. Cancellation stops the runner waiting and heartbeating, but cannot terminate arbitrary JavaScript or undo external effects. Test atomic enqueue/rollback, duplicate and successor handling, concurrency, lease expiry and fencing, retry exhaustion, invalid payloads, and handler failures as applicable. Check cancellation and stale writes for external work.
4. Inspect scripts and test side effects, then run `pnpm --filter @event-management/api test:background-jobs` and the affected domain suite (`test:catalog-knowledge` for embeddings, `test:messages` plus `tests/ai/assistant-turn.test.ts` for message processing). Use isolated database fixtures and synthetic providers. Check guest quota/claim, image validation and audit, terminal failure/retry, causal history, and takeover as applicable. Report runtime, database, provider, and deployment evidence separately.
