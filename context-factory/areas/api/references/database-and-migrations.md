# Database and migrations

## Ownership and workflow

`apps/api/prisma/schema.prisma` and `prisma/migrations/` own schema changes; runtime queries use Kysely in `src/data/`. `src/db/types.ts` is generated from the migrated database by `pnpm db:generate`; never hand-edit it. Prisma configuration resolves its connection through `src/db/config.ts`.

For a schema change, inspect existing migrations and constraints, update the Prisma schema where applicable, create and review the migration with `pnpm db:migrate`, regenerate types from the migrated database, update consumers, and run relevant checks. `pnpm db:deploy` applies committed migrations; it does not create one. SQL-only access changes need no Prisma or Kysely regeneration. Inspect the target and impact before any migration, seed, or test; keep connection values private.

New application tables must enable RLS and remove unused `PUBLIC`, `anon`, and `authenticated` grants. API access relies on the server role owning tables or having `BYPASSRLS`; Supabase roles may be absent on Compose. Existing migrations do not automatically protect future tables. Use `test:rls` and note when role-specific checks are skipped.

## Environment and destructive history

The local Supabase stack and Edge function are separate from the Compose PostgreSQL used by the Node API, Prisma, seeds, and integration tests. Read [local setup](../../../../README.md#local-supabase), current scripts, and environment target before operating either stack. See [seed guidance](../../../../docs/SEED.md) for insert-only scenario behavior and fixtures.

Inspect every pending migration before deployment. Earlier migrations can remove package records and linked history; `20261114000000_drop_venues` removes the venue catalog and `20261114010000_drop_staff_tables` removes availability/assignment tables and event-day response fields. The additive `20261114151517_complete_catalog_staff_removal` migration converted non-designated admin and staff accounts to customers and revoked their sessions, removed the remaining role and coordinator/checklist-delivery fields, deleted ownerless catalog pages, and restored the temporary package/service page-owner constraint while retaining shared media assets. Follow-up migration `20261114154206_remove_event_checklists` drops the checklist table and validator, including existing task data. Migration `20261116072801_embed_catalog_canvas` later embeds remaining package/service canvases into JSONB columns and drops the page/section/widget tables. Run the existing `pnpm --filter @event-management/api media:cleanup` command to remove stale unreferenced media. Back up affected data when its history matters. The root [migration impact](../../../../README.md#migration-impact) and migration SQL own the details.

## Entity-owned catalog canvases

`packages.canvas` and `services.canvas` are JSONB arrays of ordered sections shaped as `{ id, title, widgets }`; each widget stores its content/layout fields and a `mediaId` where applicable. This is a plain sections array with no document-version or `schemaVersion` field. The package or service owns the full canvas save, and its existing `updated_at` / `expectedUpdatedAt` concurrency check remains the stale-write boundary. There are no separately stored/versioned section or widget rows. The runtime schemas in `@event-management/contracts/catalog-canvas` constrain section/widget shape, content, IDs, limits, and layout. The editor checks the whole document before uploading and saving; API routes, stored-document readers/writers, and seed writers use the same application rules. Media ownership and availability checks remain server-side.

Migration `20261116072801_embed_catalog_canvas` adds both owner columns, backfills section and widget IDs, display order, content/layout fields, and media IDs, then drops `catalog_widgets`, `catalog_sections`, and `catalog_pages`. It does not update owner timestamps or change `media_assets`, uploaded Storage objects, or relational `package_services`. Each owner canvas has a GIN index using `jsonb_path_ops`; media-reference and cleanup queries use JSONB containment against these indexes. Deploy the matching API and generated Kysely types with this migration; an API that still expects the dropped child tables cannot run against the new schema. The [catalog canvas decision](../../../history/decisions/2026-11-16_catalog-canvas-jsonb.md) records the accepted scope.

Follow-up migration `20261116090100_validate_catalog_canvas_in_app` removes the two canvas check constraints and `catalog_canvas_is_valid(jsonb)`. It preserves JSONB data, defaults, NOT NULL constraints, owner timestamps, and GIN indexes. Deploy the matching application validators with this migration; direct SQL writes no longer enforce document rules. The original migration remains unchanged as replay history.

For booking requests, private proposals, quotations, or media, inspect their migrations and current service invariants together. Inquiry package details come from the catalog record referenced by `package_id`; private proposals have separate ownership. Quotations retain financial history rather than package/media snapshots. See [catalog media](external-image-urls.md) before changing storage references or cleanup.
