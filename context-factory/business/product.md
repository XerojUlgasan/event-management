# Product scope and implementation

**Styled by AMAC** is the website's visible brand, replacing the previous Clemora identity. The supplied AMAC logo guides its charcoal, off-white, and taupe theme across public pages, login, and workspaces. This pnpm event-management workspace contains an Astro/React frontend, Hono OpenAPI backend, and shared UI, theme, and contract packages. PostgreSQL stores application records; Prisma owns schema changes and migrations, and Kysely handles runtime SQL. Original client research for **Prevail Events Management** is preserved in the interview records; the visual rebrand does not change product scope or establish a legal ownership change.

The supplied transparent logo is owned by `packages/ui/src/assets/`. Shared colors and typography live in `packages/theme/src/theme.css`. Existing package names, API routes, and browser storage keys retain their technical identifiers.

Use the [development guide](../workflows/implement/references/development.md) for setup. The [interview summary](../../docs/PREVAIL_INTERVIEW_SUMMARY.md) records client evidence and distinguishes it from later scope decisions.

## Product scope

Scope recorded on 2026-11-03, clarified on 2026-11-11, and updated for venue catalog, staff, and event-checklist removal on 2026-11-14:

| Area                         | Intended behavior                                                                                                                                                                                                                                                                                                                         |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Catalogs                     | Present packages and services with administrator-managed content. Physical event locations remain part of customer/admin discussions.                                                                                                                                                                                                     |
| Inquiries and quotations     | Let customers start from a package or describe requirements first. Admins communicate with customers, collect missing details, discuss custom packages and added services, prepare quotations, issue revisions, and retain quotation history. Customers discuss offers and request changes through chat; admins handle quotation changes. |
| Booking and event scheduling | Admins review and accept event requests, schedule requested days, and manage event changes. Date holds, exclusive periods, setup/cleanup buffers, and cancellation policy remain open decisions.                                                                                                                                          |
| Customer service             | Use AI for factual answers from approved information, inquiry collection, and human handoff. Admins retain quotation and commitment decisions.                                                                                                                                                                                            |
| Reports and past events      | Report on actual business records and maintain a managed past-events showcase with publication permissions.                                                                                                                                                                                                                               |
| Access and communication     | Use customer and designated System Administrator accounts. Automatically create a conversation for each submitted booking request so the customer and admin can communicate and create booking-related transactions. Give customers access to their own inquiries and conversations.                                                      |

The [identity reference](identity.md) defines these intended responsibilities. The only account roles are customer and admin; admin access is reserved for designated System Administrators.

The [messages reference](messages.md) describes intended booking-linked communication. Quotations are the implemented booking-related transaction; other transaction types remain undefined within the scope boundaries below.

A request does not reserve a date, establish a final price, or confirm a booking. Confirmation rules remain to be agreed and must not be inferred from payment.

**Outside scope:** all payment responsibilities, including gateways, proof uploads, verification, payment records/status, balances, fee calculation or crediting, and receipts; equipment/inventory management; and supplier management or coordination. Existing demo screens do not establish requirements.

**Later work:** menus, additional policy/term configuration, broader AI knowledge maintenance, and reports.

Before implementing dependent work, confirm intake fields and real catalog content/prices; any further quotation format or approval policy changes; confirmation, date holds, cancellation and event-change rules; assistant sources and any automatic handoff rules; and report/showcase definitions. Meta and other channel integrations require separate decisions.

## Current implementation

System Administrators edit **Business information** at `/app/business-information`. When the profile row is missing, the editor opens with empty fields. The first save creates the profile. Public pages show those details in their footer: business name, short introduction, phone, email, Facebook, Instagram, address, map link, service area, and opening hours. Hours use one plain-text field. Fields are optional; empty fields and sections stay hidden. There is no separate business-information page; `/about` redirects to the homepage footer. Saving updates footer details on the next page request; stale edits return 409, and unsaved form state survives workspace navigation. Previously saved details outside this basic set remain in the document and public API response but are omitted from the editor and footer; saving the basics preserves those values. A failed footer read does not block the page. Package details and booking workflows remain in their existing sections. AMAC AI can look up the same ten public fields for guests and signed-in customers.

Catalog embedding ingestion uses the server-only `catalog_knowledge` table from migration `20261116103220_add_catalog_knowledge`. Each non-archived catalog package or service produces one combined `text` entry containing listing facts, all original Markdown across sections in reading order, and linked-listing captions. Text is neither split by widget nor sliced by length; listing/section context is retained and linked listing details are not copied. Only photo widgets produce separate chunks with listing/section context, alt text, and captions. Uploaded and checked-in sample photos send their actual bytes with that context to `google/gemini-embedding-2`; WebP converts to PNG for embedding, and videos are skipped. Vectors have 768 dimensions and are normalized. Catalog saves reconcile derived rows and enqueue an owner embedding job in the same transaction when eligible chunks exist. A separate worker refreshes embeddings without delaying the save for provider calls. Unchanged inputs retain their vectors, and guarded writes reject results superseded by catalog edits. Admin semantic search is available in the Knowledge Catalog. Customer and guest assistant turns can use the separate public `searchPublicCatalog` tool with structured filters and optional semantic retrieval. Migration deployment is a separate operational step. See the [combined-text decision](../history/decisions/2026-11-19_combined-catalog-text.md), [ingestion decision](../history/decisions/2026-11-16_catalog-embedding-ingestion.md), and [storage decision](../history/decisions/2026-11-16_catalog-knowledge-storage.md).

Existing overview, per-widget Markdown, and linked-caption rows become withdrawn and are excluded from semantic search. **Index pending**, a catalog save, or the provider-backed `catalog:embed` command replaces them with the combined text entry; unchanged photo embeddings are retained. This source-format change needs no schema migration. The application preserves and submits the full combined text, but Gemini Embedding 2 has an [8,192-token input limit](https://deepmind.google/models/gemini/embedding/); preparation does not guarantee that an oversized listing is fully represented by the provider.

Customers browse **Catalogs** at `/app/catalogs`, with Packages and Services tabs. Older customer `/app/packages` links open the same catalog. Filters start collapsed and open from the filter icon beside the results count; closing the panel preserves entered values and active filters. Package filters use inclusive total-price ranges in whole PHP pesos and a guest count. Service filters select fixed-price or hourly-only listings, then apply inclusive ranges to the fixed base price or hourly rate, respectively; excess-hour charges are not part of the fixed-price range. An hourly-only price range excludes services without a known rate. Package guest counts match listings with enough capacity. Applying or clearing filters starts at page 1, and Next/Previous returns focus and scroll to the catalog top. Browsing and package inquiries do not confirm a booking or final price.

The public `/packages` and `/services` pages use the same filter fields. Apply and Clear return to the first page, and page links carry the applied filters. The URL can be shared or reloaded to restore the filtered results.

### Admin agent settings

System Administrators open **AI → Agent** at `/app/ai/agent` to edit the assistant name, public chat greeting, personality, and additional guidance. The business information switch controls its lookup, and the public catalog switch controls catalog lookups and attachments. Publishing saves the single `ai_agent_settings` row and applies the settings to subsequent assistant turns. The three personalities share the same booking consent and handoff rules. A publish from an older revision requires reviewing the latest settings before trying again.

**Test chat** uses the editor's current values and sample facts. It has no access to customer conversations or actions. Rooms without a configured text model show simulated replies. Migration `20261122153000_ai_agent_settings` creates the default profile with both lookups enabled.

### Admin knowledge catalog

System Administrators open **AI → Knowledge Catalog** at `/app/ai/knowledge`. The dashboard shows separate package and service indexing coverage, listings needing attention, and searchable, cursor-paged listings. Coverage uses all eligible non-archived catalog packages and services, including unpublished listings and owners with no knowledge rows. A listing counts as indexed only when every expected chunk matches its current source identity, pipeline, model, and recorded input digest, with no withdrawn rows remaining. Empty eligibility shows no percentage. Table filters do not change the global coverage totals.

The admin-only `GET /admin/ai/knowledge` and `GET /admin/ai/knowledge/{kind}/{id}` read a consistent database snapshot without reconciling rows or calling an embedding provider. The detail drawer previews stored text and authorized photos; missing rows show expected pending content, and withdrawn chunks are labeled and excluded from coverage. **Open listing** opens the exact package/service preview. Pending does not distinguish failed work from work awaiting execution. Photo freshness assumes immutable upload identity; these reads do not download image bytes again or verify current Storage availability. **Refresh** reloads dashboard data and does not retry embeddings. Customer assistant retrieval uses a separate public adapter described below.

The detail drawer resolves included-service names for saved and pending package text. Archived or missing services show **Service details unavailable**. The names are applied when reading the drawer and require no reindexing.

Select the flask icon beside **Refresh** to open the **Search knowledge** dialog. It embeds an explicitly submitted query with the configured `google/gemini-embedding-2` model and returns up to five unique listings ordered by their best matching chunk's cosine similarity. The admin-only `POST /admin/ai/knowledge/search` accepts `{ query }` (1–500 characters after trimming). It searches current indexed chunks from non-archived services and packages of type `catalog`, including unpublished listings; custom packages, pending, incompatible, stale, and withdrawn chunks are excluded. Matches are grouped by listing kind and package/service ID before the five-result limit, retaining the highest-scoring eligible text or photo chunk for each listing. Results appear in the dialog as compact rows with the source package/service title and an optional left thumbnail. Selecting a row opens that listing's preview immediately, with loading and retry states. Closing the preview returns to the search results. The API retains similarity scores; there is no relevance cutoff. Provider/configuration failures return a sanitized 503. Search makes one embedding request per submission without changing knowledge rows. This admin endpoint remains separate from the customer assistant tool. The existing table search continues to filter listing names.

**Index pending** discovers all eligible listings with missing, pending, outdated, or withdrawn knowledge, independent of table filters, then ensures each package or service is scheduled through the existing background queue. The admin-only `POST /admin/ai/knowledge/index` accepts `{}` and returns `202` with `pendingListings`, `submittedListings`, `skippedListings`, and `failedListings`. Submitted counts include only newly inserted jobs; skipped listings already have pending/running work or became up to date or ineligible after discovery. For each listing, a short transaction locks the owner, rechecks current freshness, and atomically checks active jobs before inserting. Existing jobs, payloads, leases, retry attempts and backoff remain untouched by manual clicks. One listing job covers its text and photos. Actual catalog saves retain their separate enqueue behavior, including a follow-up for edits made while indexing runs. The request does not wait for indexing or call the embedding provider or Storage. After submission, the page reloads coverage once and you can leave it; **Refresh** checks actual coverage later. Partial enqueue failures and interrupted committed prefixes remain retryable. A listing whose earlier job exhausted retries can be submitted again if it still needs indexing; expired running jobs stay with worker lease recovery. Submission retains a 75-second request budget and bounded database waits. The worker must be running to process accepted jobs and can incur provider usage charges. The CLI backfill remains available for full reconciliation, including image-byte changes that metadata-only discovery cannot detect.

See the [background indexing specification](../../docs/specs/knowledge-catalog-background-indexing.md) for the submission contract, recovery behavior, and verification boundaries.

### Admin supporting documents

System Administrators open **AI → Supporting Documents** at `/app/ai/documents` to upload a PDF with selectable text, up to 25 MiB and 200 pages. The admin view shows the filename, page count, processing progress, and any unreadable page numbers. A document is ready after all its chunks have saved embeddings. When a temporary failure exhausts its retries, **Retry** resubmits the failed work for that file.

Use the flask icon beside **Refresh** to test a search across indexed PDF passages. The test returns up to five ranked matches. Select a passage to inspect its text, source, page range, and embedding metadata. The row's trash icon permanently removes the PDF, document record, and its embeddings after confirmation.

AMAC can search the entire supporting-document collection, including previously uploaded PDFs, in guest and signed-in chats. Each semantic search returns up to five indexed passages with their filenames, headings, and pages. AMAC uses a passage when it helps answer the question and can combine it with the business profile, catalog, or the signed-in customer's booking and quotation records.

Original PDFs are stored in the private Cloudflare R2 bucket set by `R2_SUPPORTING_DOCUMENTS_BUCKET_NAME`. The Node worker extracts text in page order, saves page and heading information with each chunk, and queues one `embed_document_chunk` job per chunk in the same transaction. See [storage setup](../workflows/implement/references/development.md#cloudflare-r2-storage) for API and worker settings.

### Booking requests and messages

Signed-in customer **Home** (`/app/home`) offers one **Your next step** action below the welcome and catalog links. It first checks whether the latest open request needs details, then looks for a current unread quotation on an open request. Otherwise it offers to resume the latest unfinished chat draft, open the latest open request, view closed requests, or start planning in Messages. Quotation selection rechecks the current offer and opens the exact sent version from its alert. The draft summary is available only to its signed-in customer and stays out of My events until submission.

Customers can ask AMAC AI to prepare a booking in chat. Each conversation keeps one booking request with an empty `submitted_at` while the customer supplies the event type, duration, dates, timezone, contact and phone. Guest count, venue, budget, package, service hours and other preferences are optional. Guests can claim the same draft after signing in. AMAC follows the customer’s language and tone, saves every detail they volunteer, and asks for one missing detail at a time. Once the draft is complete, AMAC shows the saved details and asks whether to send them to the team. A signed-in customer can approve in their own words. A correction produces a fresh summary for approval. AMAC AI saves package choices and requested extras while its draft is open. The submission receipt shows the reference and directs the customer to message staff in the same chat for changes. If the customer asks for a change after submission, AMAC AI hands the chat to staff for review. The admin sees the requested extras and decides pricing and scheduling. [Conversational booking specification](../../docs/specs/amac-conversational-booking.md)

Admins can change a request’s status beside its badge on the **Details** tab. The editor identifies customer-visible reasons and explains the effect of cancellation on scheduled event days. Saving opens the status history at the latest change. **Load older changes** appends earlier entries.

Customers follow their requests at **My events** (`/app/events`) in a timeline grouped into Today, Upcoming, Dates to arrange, Past dates, and Closed requests. Empty groups stay hidden except Upcoming. Grouping uses requested dates in each request’s timezone; a multi-day request uses its next requested date, or its most recent date once all have passed. These groups do not describe operational progress or confirm bookings. Cards show status, requested dates and times, and details/chat actions. Details retain time editing, operational schedules, status history, and cancellation. Earlier requests load into the same timeline; while more pages remain, counts describe loaded requests, and additional upcoming dates may still be on an earlier page.

Submitting through the booking form also requires a customer session and allows an optional published catalog package. In an active general conversation, **Create booking request** lets the customer search published packages by name or description, choose a package or discuss a custom package, then submit into that same thread. It collects event type (Birthday, Wedding, Corporate, or a custom choice), one date or Multi-day dates, contact name and phone, and optional notes. Multi-day requests need at least two distinct dates; dates may be nonconsecutive and are saved chronologically. The booking timezone comes from the browser and determines whether a date is today or in the future. A signed-out visitor's catalog draft retains the duration mode, date rows, other fields, and timezone through sign-in, then requires explicit review before submission.

The manual booking form lets customers review optional add-on services before submitting. Customers can request whole excess hours beyond a fixed-price service's coverage or enter the total hours for an hourly-only service. Sign-in preserves the selections. The submitted request records the hours and the public catalog terms shown at review for both the customer and the admin. The admin decides which services to add to the private package and sets billable hours in the quotation.

New requests store the complete date list in `requested_days`; `preferred_date` remains the earliest selected date for compatibility. Each requested-day entry starts with no times. Customers can later save start and end times for each unscheduled day from My events or the booking-details modal opened from a linked customer conversation. Both times are required, interpreted in the booking timezone, and may end on the following date for an overnight event. The chosen dates stay fixed. Customers can edit times while a request is `under_review`, `needs_details`, or `accepted`, until an operational schedule is created for that day. Declined and cancelled requests, and already scheduled days, are read-only. Views show “Time to be confirmed” until both times are saved.

The admin Bookings calendar counts a request once on every requested date and applies the same status filter as its results. Selecting any requested date finds the request once in the cursor-paged table; the `preferredDate` API filter matches any requested day for new requests. Legacy rows with SQL `NULL` in `requested_days` keep their recorded preferred date and estimate; the system does not invent additional dates. The admin table shows a compact requested-date summary and links each request to `/app/bookings/{id}`, where a System Administrator can review per-day times and operational schedule state.

Booking and chat labels use the event type and show requested dates where available. The admin table also shows the contact person. Private package edit history names the administrator when their display name is available and shows **Unknown administrator** otherwise.

On `/app/bookings/{id}`, requested-date rows appear in the Event days section, including dates still waiting for customer times. Acceptance and saved times alone create no operational schedule. After accepting a request, the System Administrator can schedule ready requested days with `POST /admin/event-days/schedule-requested-days` and `{ bookingRequestId, expectedUpdatedAt }`. The API creates and links operational days for requested entries that have both times and no existing day; a stale request revision rejects the batch. Requested dates without times remain unscheduled until the customer provides them. Older requests without a requested-day list retain manual event-day creation. An admin can move or cancel an operational day; a moved day links to a replacement and retains the original record. Requested dates, saved times, acceptance, or schedules do not reserve a date or confirm a booking. `preferredVenueLocation` records the customer's preferred physical event location; it is not a catalog selection. The API also accepts an optional guest count.

Requests may have a null `package_id`; catalog name, price, and maximum guests are null until a catalog package is selected. A missing current proposal shows **Package to be prepared** and **Amount to be discussed**, without a zero price. Later catalog edits appear on requests that reference that package. A supplied stale `packageUpdatedAt` returns `409`. Requests start as `under_review`; other statuses are `needs_details`, `accepted`, `declined`, and `cancelled`. Acceptance is for processing only. Customers can cancel their own open requests. Only System Administrators can update review status. `preferredVenueLocation` is a customer-entered physical location preference.

With Realtime configured, newly saved messages appear immediately in open signed-in conversations. The existing thread API reconciles messages every 15 seconds while the thread is visible and refreshes when the tab returns to focus or rejoins the channel. Opening a conversation marks incoming messages as read, and messages displayed from Realtime are acknowledged through the session-aware API. Inbox lists and anonymous conversations refresh every five seconds. Messages allow up to 4,000 characters. Scrolling to the bottom of either inbox automatically appends older conversations. Scrolling up through a conversation automatically loads earlier messages while keeping the visible message in place. Thread refreshes retain loaded history and follow new messages when the reader is near the bottom. A detected gap resets the thread to its newest boundary with a notice. Loading failures pause automatic pagination until retried.

On mobile, an open customer conversation hides the workspace tabs to make room for messages. **Back** returns to the inbox and restores the tabs, including when the customer has only one conversation.

Guest chat and customer/admin Messages render ordinary message bodies as sanitized Markdown using the shared `Markdown` component from `@event-management/ui`, also used by catalogs. Conversation styling preserves typed line breaks, inherits bubble colors, and contains wide code blocks and tables. Markdown images show their alt text without fetching sender-supplied URLs; catalog images retain their existing rendering. Quotation cards and exact-version links remain separate. Stored message text and the existing quotation controls remain separate from image processing.

Chat shows one animated three-dot assistant bubble while an eligible customer or guest AI reply is pending. AI off, admin sends, takeover, handoff, completed replies and terminal failures do not show it; switching AI back on does not revive an invalidated turn. The indicator has an accessible status label and static dots for reduced motion. Text requests track waiting locally until their send result settles; this state is not restored across reloads or shared across tabs. Image-job eligibility comes from the API's conversation-wide `aiReplyPending` projection, independent of message pagination, with `processing.replyPending` bridging send and retry acknowledgements. Pending attachments keep an available sender-local thumbnail or a neutral attachment slot, without processing-phase text. Original image access remains gated by validation; delivery/processing errors and authorized retries remain visible.

Customer, guest, and admin messages can include up to four JPEG, PNG, or WebP images, with an optional caption. Each image is limited to 10 MiB and 16 megapixels. The API checks size and file signatures, uploads bytes privately, and commits the message, pending attachment metadata and a durable job together. The Node worker fully decodes and validates each image before it can be served, automatically executes the `interpretMessageImage` tool using `VISION_MODEL`, and saves bounded observations. Interpretation remains mandatory for images, including admin sends and conversations with AI disabled; it is not selected by the chat model. Originals remain in private Storage under `messages/<conversation-id>/`; reads enforce current conversation access, including guest expiry and claim revocation. Later assistant turns receive saved observations from both human senders without image bytes, URLs, or Storage keys. Failed or incomplete observations are explicitly unavailable. Observations do not establish customer requirements, prices, or availability.

Image-message acceptance does not wait for vision or the conversational model. Existing `background_jobs` rows provide image-processing state; message reads derive queued, interpreting, replying, completed, failed and suppressed outcomes from the job and saved observations/reply. There is no separate processing table or image-status column. The chat offers **Retry processing** for eligible image-job failures, using saved uploads and the original job rather than resending the message. Only image-containing customer and guest messages use the worker for an automatic reply; text-only customer and guest replies remain synchronous in the send request. Before calling the model, a text-only send waits, with a bounded abortable wait, for earlier image jobs. If the five-second wait times out, the message stays saved and the send returns an assistant error without queuing the text turn. Admin image jobs only interpret, and accepted admin messages retain human takeover. Each trigger has at most one committed assistant reply, including handoff acknowledgements. Image jobs retry bounded transient failures and resume saved observations; stale leases and changed AI versions cannot publish. Terminal image-job failures release later image jobs; retrying an older failed image message after a later image job starts, or after any later reply is saved, repairs observations without publishing an obsolete answer. This does not cover an inline text turn that is still in flight. Invalid images cannot be retried. Provider execution is at least once, so a crash before saving an observation may repeat a vision call. Upload/message rollback cleanup remains best effort. Apply the image migrations through `20261119110919_durable_message_processing`, then apply `20261119112935_image_message_jobs_only` before deploying the matching API and worker. Stop the old worker during the job-type rename. The migration renames jobs only when their saved message has image rows, retires and revokes pending/running text jobs, and keeps completed text-job history under its retired type. Configure the separately supervised worker with the same database, Storage, `AI_GATEWAY_API_KEY`, `VISION_MODEL` and `TEXT_MODEL` before enabling this flow.

Both linked conversation headers share icon-only buttons for Details, Current package, and Quotation. Each button has an accessible name. Details shows event and contact information in a drawer, with a link to My events for customers or the booking workspace for admins; eligible scheduling changes remain in those workspaces. Current package opens the existing full package preview, including the booking’s private custom package, or explains that a package is still to be prepared. Quotation opens the latest delivered version, which stays current while the admin prepares a replacement. Quotation messages continue to open their exact linked versions. Active customer general conversations offer **Create booking request**. Submission locks and binds the owned conversation in the same transaction as the request and status history; repeated or conflicting submissions cannot create another request for that thread. Messages, conversation ID, and AI preference are preserved. Requests submitted separately still create a new linked conversation. Drafts are retained per conversation while Messages remains mounted. Customer and admin Messages share a compact composer with the camera, message field, and send button in one row. Both roles use Enter to send and Shift+Enter for a new line.

Anonymous and signed-in customer sends immediately display a local message bubble. Sending a draft clears and refocuses the composer, which stays usable while replies arrive. Selecting a suggested reply sends its exact label through the same customer send flow and keeps any draft text and attachments in the composer. Unconfirmed delivery has a retry action beside that message. Quota and expiry rejections explicitly say the message was not sent. Local bubbles are reconciled with server history by message ID. The outbox is in memory, so a full page reload discards unconfirmed local drafts and bubbles. Saved messages remain in server history.

Signed-in general and booking-linked conversations have no automatic expiry, regardless of age, parent end time, or message activity. Conversations have no stored open/closed state. Previously closed signed-in threads are available with their history and AI preference preserved. Customer messages receive a saved text-model reply while AI is enabled; admin messages do not trigger generation.

The home page's **Chat with us** action opens an anonymous bookingless inquiry. The public header retains Sign in and removes Get started. Guest messages are saved on the server from the first send. An opaque `em_guest` cookie identifies the browser; only its hash is stored in `guest_chat_identities`. The cookie has a separate 30-day browser lifetime. Each browser identity has one unexpired guest conversation, reused on subsequent openings. Its deadline is derived from the latest saved customer, admin, or assistant message plus 24 hours; reads, polling, and AI toggles do not reset that deadline. An empty thread starts its window at creation. Once expired, opening chat creates a new thread with a fresh allowance. Expiry blocks guest access without deleting history or storing a closed state. Clearing cookies or switching browsers creates a different identity; this is not physical-device tracking.

Each guest thread permits five saved customer messages; admin and assistant replies do not consume the allowance. The fifth reply remains visible, and **Sign in to continue** replaces sending once the saved-message limit is known. In-flight and uncertain guest sends reserve local allowance slots until reconciled, while the API enforces saved-message counts. Guest requests carry a unique request ID; matching sends reuse the saved message/job. New guest message IDs equal their request IDs; historical reservations retain their original IDs. Provider failure leaves the message saved and counted. Durable jobs recover interrupted attempts; processing retries do not consume another allowance slot. Existing guest jobs keep their original restricted capability after account claim and never gain private customer tools. The `/v1/guest` routes enforce bootstrap, reads, sends, processing retries and authenticated claim.

After local or Firebase sign-in or registration, the explicit guest continuation verifies both the customer session and guest cookie. Claiming transfers the same conversation and history to that customer, revokes guest reads and writes, and removes the anonymous deadline. Claim alone leaves the conversation bookingless. A guest who selects **Create booking request** resumes intake only after successful claim, then explicitly reviews and submits the request. Another account cannot claim it; retrying with the same customer and guest proof is idempotent. Claim failure keeps the customer signed in with a retry option. Signing out does not restore guest access. Signed-in customers entering Chat with us open their general Messages thread; administrators are directed to their inbox. See the [message policy](messages.md#anonymous-inquiries-and-account-claim).

### In-app notifications

The notification bell appears in both signed-in workspace headers. Each current System Administrator receives a separate alert when a customer submits a booking request or a conversation needs human review. Customers receive alerts for admin changes to their own request status and for sent quotations or revisions. The bell shows the signed-in user's unread count. ### Private packages and quotations

Service widgets inside a package are included in its fixed total. Each can store package-local included hours and excess hourly rate in its canvas JSONB, edited through the three-dot settings dialog. Selecting a service copies its catalog defaults; editing or explicitly resetting those terms affects that package only. Legacy widgets without terms remain readable with unspecified coverage and rates. Service-page references retain their neutral catalog-preview behavior.

Add-on services belong to the booking request, separate from the package. A requested service without an admin offer remains a request; saved offers carry the booking-specific pricing and hours. Historical package audit snapshots and sent quotations retain their original terms.

System Administrators can prepare packages and quotations while a request is `under_review`, `needs_details`, or `accepted`; acceptance is not a prerequisite. Declined and cancelled requests retain readable records while package and quotation controls are read-only. An open editor closes when a refreshed status becomes ineligible, and a conflicting write requires booking refresh before retry. The [eligibility specification](../../docs/specs/booking-proposal-status-eligibility.md) records the implemented behavior and local verification.

The inquiry keeps its selected catalog `package_id`, if any, and reads its current name, price, and guest limit from that record. Its current proposal is the private package identified by `custom_for_booking_request_id`, falling back to the catalog record when no custom package exists; both may initially be absent. System Administrators can assign an available catalog package to a request with no current package through `POST /admin/booking-requests/{id}/package`, using the expected booking revision. This does not overwrite an existing catalog choice or private proposal. Admins can also build a private package from scratch, or copy a catalog base and its uploads independently, then edit that booking’s custom package. Private packages are excluded from public catalogs, public slugs and new inquiry selection. Catalog title/address behavior is preserved; private copies may retain the same title.

System Administrators prepare quotations from the booking's current proposal. The editor opens with the package base price and the booking's offered add-ons. Admins manage add-ons and total whole hours on the booking request. The quotation uses those saved terms. Sending requires the linked booking conversation. If delivery fails, the admin can retry without creating a saved draft.

A revision uses the current proposal and requires a reason. The previous offer stays active until its replacement is sent. Customers can read sent versions from the booking or linked conversation and respond through chat. Later package changes leave earlier prices and messages intact. Legacy unsent records are retained outside the quotation workflow. Quotations have no automatic expiry and do not confirm a booking, reserve dates, or create event days.

### Operational event days

Accepted booking requests can have multiple event days, each with a date, full start/end timestamps, and the booking's timezone. Older requests without a requested-day list retain manual event-day creation. An administrator can create, move, or cancel operational days; a moved day links to its replacement and keeps the original history. Scheduling does not reserve a date or confirm a booking.

Image-containing customer and guest messages follow `saved message and durable image job → image validation/interpretation → current context → model-chosen answer or tool calls → saved assistant reply`. Text-only customer and guest messages use the synchronous send flow and wait, with a bounded abortable wait, for earlier image jobs before calling the model; a wait failure returns the saved message with `assistantError` and does not queue the text turn. This wait does not promise serialization with concurrent text sends or later image messages. The flow uses Vercel AI Gateway and the configured `TEXT_MODEL`. Image sends return the saved human message and processing state, with null `assistantMessage` and `assistantError`; Realtime or the thread refresh delivers the eventual reply. Assistant messages have no human sender ID and count as unread for the customer.

## Catalogs and media

Catalog packages and services are flat records with ordered canvas sections stored in `packages.canvas` and `services.canvas` as JSONB arrays. The document is a plain sections array with no schema-version field. A canvas save replaces the owner's full canvas and uses the owner's `expectedUpdatedAt` concurrency check; there are no independently versioned section or widget rows. A System Administrator catalog save publishes a complete record immediately. Packages feature services and other packages through linked canvas widgets. Package service widgets represent inclusions. Add-ons are stored with the booking request. Every new quotation uses its current offered add-ons and prices. Physical event locations are recorded on booking requests through `preferredVenueLocation`. Booking-owned custom packages are private and have a separate edit/audit flow. Updates require `expectedUpdatedAt`; stale or archived edits return `409`. Archive hides a record from public selection. A package referenced by a booking request cannot be deleted.

| Catalog | Required save data                                                                                                                                  |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Package | Name, positive `maxGuests`, fixed total PHP price, and canvas sections; the catalog description is separate from Markdown widgets.                  |
| Service | Name, description, positive whole-peso `hourlyRatePesos`, optional paired `fixedPricePesos` and positive whole `includedHours`, and a canvas photo. |

Package prices are stored as whole pesos; the API uses `{ kind: "fixed", currency: "PHP", amountMinor }` in centavos divisible by 100. Booking responses derive `packageName`, `packagePrice`, and `packageMaxGuests` from the referenced catalog package, or return null for these fields when none is selected. The current private proposal is read separately. Service saves require a positive whole-peso `hourlyRatePesos`; send both `fixedPricePesos` and `includedHours` as null for hourly-only pricing, or provide a positive fixed price and positive whole number of included hours together. A legacy service rate may be null on reads. Omitted service canvas sections preserve saved content.

Creating a catalog package or service opens a details modal before the canvas editor. Required fields are marked and validated before continuing; the modal does not save a record. Package descriptions remain optional. Services collect their description and pricing first, then require a photo in the editor before saving. The same details remain editable in a modal inside the editor. Toolbar actions use labelled icons.

Card thumbnails are optional and independent of canvas photos. An administrator-set thumbnail overrides the shared AMAC default; removing it restores the default. Public, customer, and admin cards, linked listing widgets, and reference pickers use the same default when no thumbnail is set or its image fails to load. API `imageUrl` contains only the dedicated thumbnail URL, or null; canvas photos never supply a card thumbnail automatically. The default is bundled presentation and creates no media record. Deploy the matching API and frontend together.

Package and service details preview the card image and offer **Add image**, **Change image**, or **Use default**. Replacing an image keeps the current selection until the upload succeeds. **Done** returns to the editor, where saving the package or service applies the thumbnail change. Creating a private package from a catalog package copies its thumbnail unless the administrator chooses a different image or the default.

The package and service editors share a 24-column canvas. Drag a photo, Markdown, video, or service icon from the left sidebar to a section. Clicking a sidebar icon adds a widget to the first section by default. Creating a section or dropping a widget into a section makes that section the destination for subsequent clicks. Widget controls provide move, settings, and remove actions, with a separate corner grip for resizing. Narrow canvases stack widgets and provide a reorder action. Existing package reference widgets also remain editable.

Saves retain widget positions and spans, including intentional gaps. Sections with `columns: 24` use the finer grid. Sections saved before this change use 12-column coordinates. The editor doubles their horizontal units and records the column count when saving. This needs no database migration. Deploy the matching API and web app together.

The editor, customer preview, and public detail page scale widget dimensions with the available canvas width. Photos and videos fit without cropping. Select a Markdown widget to edit its source in place. The formatted text returns when the widget loses focus. Text overflow is clipped in the rendered view. A widget can span at most 100 rows. Shared schemas validate the canvas in the editor, API, stored reads and writes, and seeds. Invalid canvas saves identify the affected section and widget. Pending file selections are validated before upload and require a saved media ID afterward.

Media uploads go through `POST /v1/admin/catalog-media`, remain pending until a catalog save references them, and stream through `/v1/catalog-media/{id}`. JPEG/PNG/WebP images allow up to 10 MiB; MP4/WebM videos allow up to 25 MiB. Photo/video widgets accept uploads only, with built-in sample photos retained for legacy catalog records; external URLs and hosted-player embeds are rejected. Video autoplay is opt-in and uses muted inline playback on customer previews and public pages.

The editor offers Photo, Markdown, Video, and Service widgets. Adding new Package widgets is temporarily hidden in catalog package, service, and private proposal editors. Existing package widgets remain visible, editable, and saveable; their stored references and public navigation are preserved. This editor-only change needs no migration or API change.

Service widgets in packages indicate inclusions covered by the package base price. Package widgets and service-page references link to catalog listings. In edit mode, clicking the widget body opens active choices of that kind directly, with search, photos, descriptions, pagination, an optional caption, and keyboard dismissal/focus restoration. Private custom packages are excluded. In public pages and previews, the whole card links to the selected listing's detail page. Inside `/app`, the whole card instead opens a detail preview overlay while preserving the current route and underlying preview or editor. Following another service or package replaces the overlay content; closing it returns focus to the original card. Workspace navigation closes the overlay and restores page scrolling. Saved widgets store a service or package ID; reads resolve its current name, description, photo, and public link without pricing or nested canvases. Archived targets show an unavailable placeholder; existing references remain editable, but new unavailable references cannot be saved. A listing referenced by a package or service canvas cannot be deleted. Knowledge ingestion indexes the widget caption only, so renames do not leave copied listing details in another listing. No database migration is needed; deploy the matching shared contracts, API, and frontend together.

├── packages/<package-id>/images/<media-id>.<ext>

Saving a listing promotes its new pending uploads by copying bytes into the owner folder, switching the stored key, then removing the pending copy. A failed copy leaves the saved listing using its readable pending file; a later save retries promotion. Dedicated thumbnails use the same owner folders. API media URLs and access checks remain unchanged; folder names do not grant access. Original filenames are not retained.

**Development scope:** Clemora has not reached production. Existing documents and uploaded files do not need migration or preservation for this redesign. There is no storage backfill command or move-tracking table, and this change does not delete existing bucket objects. The folder structure applies to new uploads and their subsequent saves. Interrupted promotion can leave an unreferenced object; this development implementation does not add a durable recovery queue. See [catalog media](../areas/api/references/external-image-urls.md) for lifecycle details.

Public media streaming requires a reference from a published, non-archived catalog record. System Administrators can preview pending uploads and saved private media under the API access rules. See [catalog media](../areas/api/references/external-image-urls.md) for storage, cleanup, and migration details, and [shared limits](../areas/contracts/SKILL.md) for validation ownership.
