# Private proposals and quotations

The original inquiry retains its selected catalog identity and stored name, price and maximum-guest snapshots. Its current proposal resolves a booking-owned custom package when present, otherwise the current original catalog package. These are separate presentations. Only System Administrators prepare packages and quotations; customers review their own private proposal and sent offers.

Custom packages use the existing packages table and belong to one booking. Their content, uploads, services, guest limit and price can change without editing the public catalog. Package service links are ordered included/optional descriptions; they do not calculate a quotation or verify availability.

A quotation retains the offered package ID, base amount, ordered manual integer-centavo additions/deductions and computed total. A base-only offer is valid. The server owns totals. Package content, services and event details remain on the booking and current proposal; quotations do not snapshot or compare them. Later edits do not alter saved quotation amounts or automatically block sending/acceptance. Starting an explicit revision uses the current proposal price and copies prior adjustments for review. Sent financial history remains readable independently of later library edits. Quotation acceptance never confirms a booking, reserves dates or creates schedules.

Approved policies: quotations have no automatic expiry; any System Administrator can edit/revise/send with audit attribution. Starting a revision immediately supersedes the old active agreement and requires fresh approval after adjustments are reviewed. Customers requesting revision receive an acknowledgment, not the internal new draft. Sending records a version-linked message in the same booking conversation atomically; closed or expired conversations block sending and are never reopened by that action.

Keep requested-day preferences and effective operational schedules distinct. Staffing assignments, response deadlines and attaching an unchanged schedule are not commercial changes. Administrators must discuss relevant delivery or scope changes with the customer and explicitly revise the offer when a new agreement is needed; the API does not detect these changes or automatically invalidate acceptance.
