# Design IT capstones

Research, screen, rank, and develop practical IT capstone ideas, titles, scopes, architectures, integrations, and evaluation plans for student teams and Philippine clients. Use for ideation or proposal design; preserve an already approved project.

Use the [documentation agent](../../../agents/documentation.md). Identify whether the user needs a new idea, a comparison, or refinement of an existing proposal. Read the actual client evidence and approved constraints before shaping the system.

## Shape a practical system

- Start with a recurring task and a real user or business: their current workflow, bottleneck, workaround, and measurable burden. Separate verified problems from hypotheses that need interviews or observation.
- For new ideas, favor immediate net convenience and voluntary adoption. Prefer systems that can deliver value without payments, network effects, private partnerships, institutional approval, or business-document-dependent publishing. For an approved project with such dependencies, assess actual access and fallbacks rather than silently changing its scope.
- Research existing products, research, and capstones before claiming differentiation. Use primary or official evidence for current capabilities and access requirements; distinguish absence of discovered evidence from proof that no alternative exists.
- Define a coherent workflow with useful technical depth. CRUD screens, a generic chatbot, or an integration label alone do not explain the engineering contribution. Connect each proposed technical component to a concrete user task and constraint.
- Match the scope to the team's time, skills, budget, available data, deployment context, and maintainable dependencies. Preserve the approved client, topic, and boundaries when refining Clemora.

## Develop the proposal

For the selected idea, provide the following to the extent the request needs them:

- A precise title, target users/client, evidenced problem, current workaround, and proposed improvement.
- The end-to-end journey, MVP capabilities, explicit exclusions, and likely failure or exception paths.
- A workable architecture, data sources and permissions, integration responsibilities, deployment assumptions, and fallback paths.
- The engineering contribution and defensible differences from relevant alternatives, with sources and limits.
- Feasibility risks and the evidence or prototype needed to resolve each material uncertainty.
- An evaluation plan linking objectives to measures, baseline/comparison, collection method, and explicit proposed success criteria. Never present targets as measured improvements.

For a shortlist, compare candidates using shared criteria and explain why the recommendation fits the user's constraints. Do not force a fixed number of ideas or enlarge an already adequate MVP.

## Validate before drafting the paper

Run [validate-it-capstones](validate-it-capstones.md) as a distinct critical pass after shaping or materially revising the proposal. Address supported weaknesses or expose unresolved conditions; do not self-certify based on persuasive wording.

Use [docs](../../documentation/references/docs.md) to turn the selected, bounded design into the requested proposal or chapters. Use [research-desk](research-desk.md) for source-grounded related work. Keep planned functionality, implemented behavior, and measured outcomes distinguishable throughout the paper.
