# Service catalog and package assignments

Services are reusable offerings such as a coffee bar, grazing table, magazine booth, photo booth, or tattoo booth. These are examples, not approved catalog records or prices. An administrator creates a service draft and publishes it before assigning it to a package. The same service can be included in one package and offered as a paid add-on in another.

## Records and pricing

- `services` holds a stable service ID and archive timestamp. `service_versions` holds the name, Markdown description, optional uploaded image ID, hourly rate in whole PHP pesos, publication state, and immutable published history. A draft may omit the hourly rate and image, but publication requires a positive rate and uploaded image. A published service retains its rate and image for that version. Service categories are no longer stored.
- `package_services` links a specific `package_versions` row to a specific `service_versions` row. Every link has its own UUID `id`. A package version cannot link the same service version twice.
- An `included` link has a positive `included_quantity` and no separate price. Its cost is covered by the package's fixed PHP total.
- An `add_on` link has a positive `add_on_unit_price_amount_minor` and `add_on_max_quantity`, with no included quantity. The amount is a fixed PHP price per unit in centavos. This package-specific add-on price remains separate from the service's hourly rate; package pricing behavior has not been changed.
- Existing free-text package `inclusions` remain available for non-service inclusions. A package can publish with a textual inclusion or an included structured service. The editor should avoid listing the same benefit in both places.

Publishing a revised service creates a new version. Existing published packages continue to reference the service version they were issued with. To offer the revised service in a package, an administrator edits and republishes that package. Service archival is rejected while a current published package uses it; revise or archive the affected package first. Historical versions and links are retained.

## API and screens

Public `GET /v1/services` and `GET /v1/services/:id` expose current published, non-archived services. The list supports optional `limit` (1–15) and `offset` and returns `nextOffset` for paging; omitting `limit` retains the full-list response. `GET /v1/services/:id/packages` returns current published packages with an included assignment to that service, including an assignment to an older service version. Admin service routes under `/v1/admin/services` support list, detail, draft creation and edit, publish, archive, and deletion of eligible never-published drafts. Admin writes and reads require the database `admin` role and a valid session. Draft edits and publication use `expectedUpdatedAt` to reject stale changes.

Service image input accepts a JPEG, PNG, or WebP upload up to 10 MiB. Admin multipart `POST /v1/admin/service-uploads` and `PATCH /v1/admin/service-uploads/:id` send JSON service content in `content` and the file in `image`. Uploaded bytes are stored in Cloudflare R2 and fetched through `GET /v1/service-images/:id`. Service responses provide the uploaded image's UUID as `imageId`; JSON create/edit requests cannot set it. JSON draft edits may use `removeImage: true` to remove the current upload. Configure the R2 variables named in `apps/api/.env.example` for actual uploads. The migration rejects existing service image URL data instead of converting it.
Replacing or removing a draft's uploaded image, or deleting a never-published service, removes its R2 object only after no service version references it. If R2 deletion fails after the database change, the edit remains saved and the unused object needs later cleanup.

Package create and draft edit requests may include `services`, an array of assignments with `serviceVersionId`, `role`, `includedQuantity`, `addOnPrice`, and `addOnMaxQuantity`. Package responses include each assignment's UUID `id` and the selected service version's details. Only current published, non-archived service versions can be assigned to a new package draft or published package revision. Existing package requests without `services` remain supported.

The admin workspace has a Services sidebar item for creating, editing, and publishing services. Its three-step editor places service name and Markdown description first, image upload second, and whole-peso hourly rate third. Checking “Preview description markdown” shows rendered Markdown below the editor. The final step offers Preview, Save draft, and Save and publish; the preview shows unsaved values in a full-screen overlay whose only action is the X close button. Admin service cards open the same preview for a saved version. Once published, a service can appear among the first three cards on `/`; View more opens the paged catalog in a full-screen overlay. The public service preview still lists packages that include the service. The Packages editor assigns published services in its Experience step. Public and customer package previews separate included services from optional priced add-ons. Package and public description rendering have not yet been redesigned for Markdown. Catalog selection and add-on display do not check availability, submit an inquiry, create a quote, hold a date, or confirm a booking. Staff must confirm capacity and delivery terms before quoting; the availability and quotation workflows remain separate roadmap work.

## Business details to confirm

Before publishing real services, approve each offered configuration and describe its scope clearly, decide which packages include it, set the PHP add-on price per package, and choose the maximum purchasable quantity. Capacity, provider scheduling, and date conflicts still need operating rules before automated availability can be promised. Keep different sellable configurations as separate services until variant rules are defined.
