# Styled by AMAC

**Styled by AMAC** is the website's visible brand, replacing the previous Clemora identity. The supplied AMAC logo guides its charcoal, off-white, and taupe theme across public pages, login, and workspaces. This pnpm event-management workspace contains an Astro/React frontend, Hono OpenAPI backend, and shared UI, theme, and contract packages. PostgreSQL stores application records; Prisma owns schema changes and migrations, and Kysely handles runtime SQL. Original client research for **Prevail Events Management** is preserved in the interview records; the visual rebrand does not change product scope or establish a legal ownership change.

The original logo is owned by `packages/ui/src/assets/`; shared colors and typography remain in `packages/theme/src/theme.css`. Existing package names, API routes, and browser storage keys retain their technical identifiers.

This README owns product scope, current implementation status, and development setup. The [interview summary](docs/PREVAIL_INTERVIEW_SUMMARY.md) records client evidence and distinguishes it from later scope decisions. The [seed guide](docs/SEED.md) covers development fixtures and repeat runs.

**Outside scope:** all payment responsibilities, including gateways, proof uploads, verification, payment records/status, balances, fee calculation or crediting, and receipts; equipment/inventory management; and supplier management or coordination. Existing demo screens do not establish requirements.

**Later work:** menus, additional policy/term configuration, broader AI knowledge maintenance, reports, and the managed past-events showcase.

Before implementing dependent work, confirm intake fields and real catalog content/prices; any further quotation format or approval policy changes; confirmation, date holds, cancellation and event-change rules; assistant sources and any automatic handoff rules; and report/showcase definitions. Meta and other channel integrations require separate decisions.

## Current implementation

Catalog embedding ingestion uses the server-only `catalog_knowledge` table from migration `20261116103220_add_catalog_knowledge`. Each non-archived catalog package or service produces one combined `text` entry containing listing facts, all original Markdown across sections in reading order, and linked-listing captions. Text is neither split by widget nor sliced by length; listing/section context is retained and linked listing details are not copied. Only photo widgets produce separate chunks with listing/section context, alt text, and captions. Uploaded and checked-in sample photos send their actual bytes with that context to `google/gemini-embedding-2`; WebP converts to PNG for embedding, and videos are skipped. Vectors have 768 dimensions and are normalized. Catalog saves reconcile derived rows and enqueue an owner embedding job in the same transaction when eligible chunks exist. A separate worker refreshes embeddings without delaying the save for provider calls. Unchanged inputs retain their vectors, and guarded writes reject results superseded by catalog edits. Admin semantic search is available in the Knowledge Catalog. Customer and guest assistant turns can use the separate public `searchPublicCatalog` tool with structured filters and optional semantic retrieval. Migration deployment is a separate operational step. See the [combined-text decision](context-factory/history/decisions/2026-11-19_combined-catalog-text.md), [ingestion decision](context-factory/history/decisions/2026-11-16_catalog-embedding-ingestion.md), and [storage decision](context-factory/history/decisions/2026-11-16_catalog-knowledge-storage.md).

Existing overview, per-widget Markdown, and linked-caption rows become withdrawn and are excluded from semantic search. **Index pending**, a catalog save, or the provider-backed `catalog:embed` command replaces them with the combined text entry; unchanged photo embeddings are retained. This source-format change needs no schema migration. The application preserves and submits the full combined text, but Gemini Embedding 2 has an [8,192-token input limit](https://deepmind.google/models/gemini/embedding/); preparation does not guarantee that an oversized listing is fully represented by the provider.

### Admin knowledge catalog

System Administrators open **AI → Knowledge Catalog** at `/app/ai/knowledge`. The dashboard shows separate package and service indexing coverage, listings needing attention, and searchable, cursor-paged listings. Coverage uses all eligible non-archived catalog packages and services, including unpublished listings and owners with no knowledge rows. A listing counts as indexed only when every expected chunk matches its current source identity, pipeline, model, and recorded input digest, with no withdrawn rows remaining. Empty eligibility shows no percentage. Table filters do not change the global coverage totals.

The admin-only `GET /admin/ai/knowledge` and `GET /admin/ai/knowledge/{kind}/{id}` read a consistent database snapshot without reconciling rows or calling an embedding provider. The detail drawer previews stored text and authorized photos; missing rows show expected pending content, and withdrawn chunks are labeled and excluded from coverage. **Open listing** opens the exact package/service preview. Pending does not distinguish failed work from work awaiting execution. Photo freshness assumes immutable upload identity; these reads do not download image bytes again or verify current Storage availability. **Refresh** reloads dashboard data and does not retry embeddings. Customer assistant retrieval uses a separate public adapter described below.

**Search knowledge** embeds an explicitly submitted query with the configured `google/gemini-embedding-2` model and returns up to five unique listings ordered by their best matching chunk's cosine similarity. The admin-only `POST /admin/ai/knowledge/search` accepts `{ query }` (1–500 characters after trimming). It searches current indexed chunks from non-archived services and packages of type `catalog`, including unpublished listings; custom packages, pending, incompatible, stale, and withdrawn chunks are excluded. Matches are grouped by listing kind and package/service ID before the five-result limit, retaining the highest-scoring eligible text or photo chunk for each listing. Results appear as compact rows with only the source package/service title and an optional left thumbnail. Clicking anywhere on a row opens that listing's preview overlay immediately, with loading and retry states, while the Knowledge Catalog stays open behind it. The API retains similarity scores; there is no relevance cutoff. Provider/configuration failures return a sanitized 503. Search makes one embedding request per submission without changing knowledge rows. This admin endpoint remains separate from the customer assistant tool. The existing table search continues to filter listing names.

**Index pending** discovers all eligible listings with missing, pending, outdated, or withdrawn knowledge, independent of table filters, then ensures each package or service is scheduled through the existing background queue. The admin-only `POST /admin/ai/knowledge/index` accepts `{}` and returns `202` with `pendingListings`, `submittedListings`, `skippedListings`, and `failedListings`. Submitted counts include only newly inserted jobs; skipped listings already have pending/running work or became up to date or ineligible after discovery. For each listing, a short transaction locks the owner, rechecks current freshness, and atomically checks active jobs before inserting. Existing jobs, payloads, leases, retry attempts and backoff remain untouched by manual clicks. One listing job covers its text and photos. Actual catalog saves retain their separate enqueue behavior, including a follow-up for edits made while indexing runs. The request does not wait for indexing or call the embedding provider or Storage. After submission, the page reloads coverage once and you can leave it; **Refresh** checks actual coverage later. Partial enqueue failures and interrupted committed prefixes remain retryable. A listing whose earlier job exhausted retries can be submitted again if it still needs indexing; expired running jobs stay with worker lease recovery. Submission retains a 75-second request budget and bounded database waits. The worker must be running to process accepted jobs and can incur provider usage charges. The CLI backfill remains available for full reconciliation, including image-byte changes that metadata-only discovery cannot detect.

See the [background indexing specification](docs/specs/knowledge-catalog-background-indexing.md) for the submission contract, recovery behavior, and verification boundaries.

### Booking requests and messages

Customers follow their requests at **My events** (`/app/events`) in a timeline grouped into Today, Upcoming, Dates to arrange, Past dates, and Closed requests. Empty groups stay hidden except Upcoming. Grouping uses requested dates in each request’s timezone; a multi-day request uses its next requested date, or its most recent date once all have passed. These groups do not describe operational progress or confirm bookings. Cards show status, requested dates and times, and details/chat actions. Details retain time editing, operational schedules, status history, and cancellation. Earlier requests load into the same timeline; while more pages remain, counts describe loaded requests, and additional upcoming dates may still be on an earlier page.

The current intake requires a customer session and allows an optional published catalog package. In an active general conversation, **Create booking request** lets the customer choose a catalog package or discuss a custom package, then submit into that same thread. It collects event type (Birthday, Wedding, Corporate, or a custom choice), one date or Multi-day dates, contact name and phone, and optional notes. Multi-day requests need at least two distinct dates; dates may be nonconsecutive and are saved chronologically. The booking timezone comes from the browser and determines whether a date is today or in the future. A signed-out visitor's catalog draft retains the duration mode, date rows, other fields, and timezone through sign-in, then requires explicit review before submission.

New requests store the complete date list in `requested_days`; `preferred_date` remains the earliest selected date for compatibility. Each requested-day entry starts with no times. Customers can later save start and end times for each unscheduled day from My events or the booking-details modal opened from a linked customer conversation. Both times are required, interpreted in the booking timezone, and may end on the following date for an overnight event. The chosen dates stay fixed. Customers can edit times while a request is `under_review`, `needs_details`, or `accepted`, until an operational schedule is created for that day. Declined and cancelled requests, and already scheduled days, are read-only. Views show “Time to be confirmed” until both times are saved.

The admin Bookings calendar counts a request once on every requested date and applies the same status filter as its results. Selecting any requested date finds the request once in the cursor-paged table; the `preferredDate` API filter matches any requested day for new requests. Legacy rows with SQL `NULL` in `requested_days` keep their recorded preferred date and estimate; the system does not invent additional dates. The admin table shows a compact requested-date summary and links each request to `/app/bookings/{id}`, where a System Administrator can review per-day times and operational schedule state.

On `/app/bookings/{id}`, requested-date rows appear in the Event days section, including dates still waiting for customer times. Acceptance and saved times alone create no operational schedule. After accepting a request, the System Administrator can schedule ready requested days with `POST /admin/event-days/schedule-requested-days` and `{ bookingRequestId, expectedUpdatedAt }`. The API creates and links operational days for requested entries that have both times and no existing day; a stale request revision rejects the batch. Requested dates without times remain unscheduled until the customer provides them. Older requests without a requested-day list retain manual event-day creation. An admin can move or cancel an operational day; a moved day links to a replacement and retains the original record. Requested dates, saved times, acceptance, or schedules do not reserve a date or confirm a booking. `preferredVenueLocation` records the customer's preferred physical event location; it is not a catalog selection. The API also accepts an optional guest count.

Requests may have a null `package_id`; catalog name, price, and maximum guests are null until a catalog package is selected. A missing current proposal shows **Package to be prepared** and **Amount to be discussed**, without a zero price. Later catalog edits appear on requests that reference that package. A supplied stale `packageUpdatedAt` returns `409`. Requests start as `under_review`; other statuses are `needs_details`, `accepted`, `declined`, and `cancelled`. Acceptance is for processing only. Customers can cancel their own open requests. Only System Administrators can update review status. `preferredVenueLocation` is a customer-entered physical location preference.

Both message workspaces refresh every five seconds. Opening a conversation marks the other side's messages as read; messages allow up to 4,000 characters. Scrolling to the bottom of either inbox automatically appends older conversations. Scrolling up through a conversation automatically loads earlier messages while keeping the visible message in place. Regular polling retains loaded history and follows new messages when the reader is already near the bottom; a detected gap resets the thread to its newest boundary with a notice. Loading failures pause automatic pagination until retried.

Guest chat and customer/admin Messages render ordinary message bodies as sanitized Markdown using the shared `Markdown` component from `@event-management/ui`, also used by catalogs. Conversation styling preserves typed line breaks, inherits bubble colors, and contains wide code blocks and tables. Markdown images show their alt text without fetching sender-supplied URLs; catalog images retain their existing rendering. Quotation cards and exact-version links remain separate. Stored message text and the existing quotation controls remain separate from image processing.

Chat shows one animated three-dot assistant bubble while an eligible customer or guest AI reply is pending. AI off, admin sends, takeover, handoff, completed replies and terminal failures do not show it; switching AI back on does not revive an invalidated turn. The indicator has an accessible status label and static dots for reduced motion. Text requests track waiting locally until their send result settles; this state is not restored across reloads or shared across tabs. Image-job eligibility comes from the API's conversation-wide `aiReplyPending` projection, independent of message pagination, with `processing.replyPending` bridging send and retry acknowledgements. Pending attachments keep an available sender-local thumbnail or a neutral attachment slot, without processing-phase text. Original image access remains gated by validation; delivery/processing errors and authorized retries remain visible.

Customer, guest, and admin messages can include up to four JPEG, PNG, or WebP images, with an optional caption. Each image is limited to 10 MiB and 16 megapixels. The API checks size and file signatures, uploads bytes privately, and commits the message, pending attachment metadata and a durable job together. The Node worker fully decodes and validates each image before it can be served, automatically executes the `interpretMessageImage` tool using `VISION_MODEL`, and saves bounded observations. Interpretation remains mandatory for images, including admin sends and conversations with AI disabled; it is not selected by the chat model. Originals remain in private Storage under `messages/<conversation-id>/`; reads enforce current conversation access, including guest expiry and claim revocation. Later assistant turns receive saved observations from both human senders without image bytes, URLs, or Storage keys. Failed or incomplete observations are explicitly unavailable. Observations do not establish customer requirements, prices, or availability.

Image-message acceptance does not wait for vision or the conversational model. Existing `background_jobs` rows provide image-processing state; message reads derive queued, interpreting, replying, completed, failed and suppressed outcomes from the job and saved observations/reply. There is no separate processing table or image-status column. The chat offers **Retry processing** for eligible image-job failures, using saved uploads and the original job rather than resending the message. Only image-containing customer and guest messages use the worker for an automatic reply; text-only customer and guest replies remain synchronous in the send request. Before calling the model, a text-only send waits, with a bounded abortable wait, for earlier image jobs. If the five-second wait times out, the message stays saved and the send returns an assistant error without queuing the text turn. Admin image jobs only interpret, and accepted admin messages retain human takeover. Each trigger has at most one committed assistant reply, including handoff acknowledgements. Image jobs retry bounded transient failures and resume saved observations; stale leases and changed AI versions cannot publish. Terminal image-job failures release later image jobs; retrying an older failed image message after a later image job starts, or after any later reply is saved, repairs observations without publishing an obsolete answer. This does not cover an inline text turn that is still in flight. Invalid images cannot be retried. Provider execution is at least once, so a crash before saving an observation may repeat a vision call. Upload/message rollback cleanup remains best effort. Apply the image migrations through `20261119110919_durable_message_processing`, then apply `20261119112935_image_message_jobs_only` before deploying the matching API and worker. Stop the old worker during the job-type rename. The migration renames jobs only when their saved message has image rows, retires and revokes pending/running text jobs, and keeps completed text-job history under its retired type. Configure the separately supervised worker with the same database, Storage, `AI_GATEWAY_API_KEY`, `VISION_MODEL` and `TEXT_MODEL` before enabling this flow.

Both linked conversation headers provide separate Details, Current package, and Quotation controls. Details shows event and contact information in a drawer, with a link to My events for customers or the booking workspace for admins; eligible scheduling changes remain in those workspaces. Current package opens the existing full package preview, including the booking’s private custom package, or explains that a package is still to be prepared. Quotation opens the latest version that was actually sent, including a superseded offer while a newer draft is being prepared; unsent drafts are excluded. Quotation messages continue to open their exact linked versions. Active customer general conversations offer **Create booking request**. Submission locks and binds the owned conversation in the same transaction as the request and status history; repeated or conflicting submissions cannot create another request for that thread. Messages, conversation ID, and AI preference are preserved. Requests submitted separately still create a new linked conversation. Drafts are retained per conversation while Messages remains mounted. Customer composers use Enter to send and Shift+Enter for a new line; the admin composer retains Ctrl/Cmd+Enter to send.

Anonymous and signed-in customer sends immediately display a local message bubble, clear and refocus the composer, and leave it usable while replies arrive. The send arrow stays unchanged. Unconfirmed delivery has a retry action beside that message; quota and expiry rejections explicitly say the message was not sent. Local bubbles are reconciled with server history by message ID. The outbox is in memory, so a full page reload discards unconfirmed local drafts and bubbles; saved messages remain in server history.

Signed-in general and booking-linked conversations have no automatic expiry, regardless of age, parent end time, or message activity. Conversations have no stored open/closed state. Previously closed signed-in threads are available with their history and AI preference preserved. Customer messages receive a saved text-model reply while AI is enabled; admin messages do not trigger generation.

The home page's **Chat with us** action opens an anonymous bookingless inquiry. The public header retains Sign in and removes Get started. Guest messages are saved on the server from the first send. An opaque `em_guest` cookie identifies the browser; only its hash is stored in `guest_chat_identities`. The cookie has a separate 30-day browser lifetime. Each browser identity has one unexpired guest conversation, reused on subsequent openings. Its deadline is derived from the latest saved customer, admin, or assistant message plus 24 hours; reads, polling, and AI toggles do not reset that deadline. An empty thread starts its window at creation. Once expired, opening chat creates a new thread with a fresh allowance. Expiry blocks guest access without deleting history or storing a closed state. Clearing cookies or switching browsers creates a different identity; this is not physical-device tracking.

Each guest thread permits five saved customer messages; admin and assistant replies do not consume the allowance. The fifth reply remains visible, and **Sign in to continue** replaces sending once the saved-message limit is known. In-flight and uncertain guest sends reserve local allowance slots until reconciled, while the API enforces saved-message counts. Guest requests carry a unique request ID; matching sends reuse the saved message/job. New guest message IDs equal their request IDs; historical reservations retain their original IDs. Provider failure leaves the message saved and counted. Durable jobs recover interrupted attempts; processing retries do not consume another allowance slot. Existing guest jobs keep their original restricted capability after account claim and never gain private customer tools. The `/v1/guest` routes enforce bootstrap, reads, sends, processing retries and authenticated claim.

After local or Firebase sign-in or registration, the explicit guest continuation verifies both the customer session and guest cookie. Claiming transfers the same conversation and history to that customer, revokes guest reads and writes, and removes the anonymous deadline. Claim alone leaves the conversation bookingless. A guest who selects **Create booking request** resumes intake only after successful claim, then explicitly reviews and submits the request. Another account cannot claim it; retrying with the same customer and guest proof is idempotent. Claim failure keeps the customer signed in with a retry option. Signing out does not restore guest access. Signed-in customers entering Chat with us open their general Messages thread; administrators are directed to their inbox. See the [message policy](context-factory/business/messages.md#anonymous-inquiries-and-account-claim).

### Private packages and quotations

Service widgets inside a package are included in its fixed total. Each can store package-local included hours and excess hourly rate in its canvas JSONB, edited through the three-dot settings dialog. Selecting a service copies its catalog defaults; editing or explicitly resetting those terms affects that package only. Legacy widgets without terms remain readable with unspecified coverage and rates. Service-page references retain their neutral catalog-preview behavior.

Private custom packages alone can store an `addonServices` JSONB list with service references and local pricing, including fixed price, covered hours and excess rate or hourly-only pricing. Add-on overrides live in the same entry. Neither list changes the base package total. Automatic quotation charging, extension calculations, partial-hour rounding and structured quote-term snapshots remain deferred; existing quotations retain their manual adjustment flow. See the [decision](context-factory/history/decisions/2026-11-20_package-service-terms.md) and [verification run](context-factory/runs/2026-11-20_23-03-00_package-service-terms.md).

System Administrators can prepare packages and quotations while a request is `under_review`, `needs_details`, or `accepted`; acceptance is not a prerequisite. Declined and cancelled requests retain readable records while package and quotation controls are read-only. An open editor closes when a refreshed status becomes ineligible, and a conflicting write requires booking refresh before retry. The [eligibility specification](docs/specs/booking-proposal-status-eligibility.md) records the implemented behavior and local verification.

The inquiry keeps its selected catalog `package_id`, if any, and reads its current name, price, and guest limit from that record. Its current proposal is the private package identified by `custom_for_booking_request_id`, falling back to the catalog record when no custom package exists; both may initially be absent. System Administrators can assign an available catalog package to a request with no current package through `POST /admin/booking-requests/{id}/package`, using the expected booking revision. This does not overwrite an existing catalog choice or private proposal. Admins can also build a private package from scratch, or copy a catalog base and its uploads independently, then edit that booking’s custom package. Private packages are excluded from public catalogs, public slugs and new inquiry selection. Catalog title/address behavior is preserved; private copies may retain the same title.

From the admin booking page, System Administrators create a quotation draft from the current proposal, save ordered manual additions/deductions, and send the saved version. A prepared catalog or private package is required before quotation creation. Empty adjustment lists are valid. The server validates every item and optional service reference and atomically saves JSONB items with the computed integer-centavo total. Each version retains its package ID, base amount, adjustments and computed total. Package content, services and event details remain on the booking and current proposal; quotations do not copy or automatically compare them. Later edits do not change saved quotation amounts or block sending. An administrator explicitly starts a revision when a new offer is needed; the revision uses the current proposal price and copies prior adjustments for review.

Sending atomically records the quotation, audit event and a version-linked conversation message. Sending requires the linked booking conversation; conversation age and prior closure do not block delivery. Quotations have no automatic expiry. Any System Administrator can edit, revise or send, with audit attribution. Starting a revision immediately supersedes the prior offer and creates an internal draft for adjustment review. Quotation statuses are `draft`, `sent`, and `superseded`. Customers see sent history and discuss agreement, concerns, or requests for a new quotation through chat; their replies do not change quotation status or create drafts. Internal drafts remain hidden. Admin revisions preserve prior versions, their financial values, revision links and reasons, adjustments, messages, and audit history. Quotations and chat replies do not confirm a booking, reserve dates, or create event days.

### Operational event days

Accepted booking requests can have multiple event days, each with a date, full start/end timestamps, and the booking's timezone. The customer supplies requested dates and times; acceptance and saved times alone do not create operational schedules. A System Administrator schedules ready requested days with `POST /admin/event-days/schedule-requested-days`, sending `bookingRequestId` and `expectedUpdatedAt`. The API creates and links days for requested entries that have both times and no existing day, and rejects stale request revisions. Older requests without a requested-day list retain manual event-day creation. An administrator can create, move, or cancel operational days; a moved day links to its replacement and keeps the original history. Scheduling does not reserve a date or confirm a booking.

Image-containing customer and guest messages follow `saved message and durable image job → image validation/interpretation → current context → model-chosen answer or tool calls → saved assistant reply`. Text-only customer and guest messages use the synchronous send flow and wait, with a bounded abortable wait, for earlier image jobs before calling the model; a wait failure returns the saved message with `assistantError` and does not queue the text turn. This wait does not promise serialization with concurrent text sends or later image messages. The flow uses Vercel AI Gateway and the configured `TEXT_MODEL`. Image sends return the saved human message and processing state, with null `assistantMessage` and `assistantError`; polling delivers the eventual reply. Signed-in sends support an optional UUID `requestId`, used as the saved message ID. Matching image-send retries preserve the saved message/job and conflicting body or image hashes return 409. Provider failures leave the human message saved and counted. Reply identity is enforced through a unique `reply_to_message_id`; image-reply writes recheck the job lease, conversation ownership/activity and captured AI version. Assistant messages have no human sender ID and count as unread for the customer.

Tools are available from the first model step, with no mandatory evidence-selection call or tool-use publication gate. The model chooses proposal and public catalog reads when needed; booking fields already arrive in the fresh server context. Greetings, drafting, and questions about the conversation can receive a direct answer in one generation without record reads or tool-call records. Earlier assistant replies are labeled historical claims; they help resolve the conversation but do not establish current saved facts. The prompt requires current context or successful current-turn reads for those facts and permits claims of tool execution only for completed calls. Code validates and audits actual calls, enforces access and budgets, and blocks replies on tracking failure. Source selection and interpretation remain model decisions; representative live-model evaluation remains separate from synthetic orchestration tests.

`searchPublicCatalog` accepts `catalogType` (`package` or `service`), optional `query` (1–500 trimmed characters), inclusive whole-peso price bounds, package-only `pax`, service-only `pricingType` (`fixed` or `hourly`), and an optional cursor. Service price bounds require a pricing type. Package capacity must accommodate `pax`; fixed service filtering compares the base amount, excluding excess-hour charges. Each call returns at most five unique listings with current PHP pricing terms, capacity, bounded descriptions/evidence, and public links. Public eligibility excludes archived listings, custom packages, and unpublished packages. Queryless searches do not require embedding configuration. Queries use fresh, compatible indexed chunks after exact eligibility/filter checks; pending or unavailable evidence is not a successful semantic match, and provider failures remain distinct from empty results. Cursors are bound to type, query, and filters. Only the last successful search associated with an earlier saved assistant reply in this conversation supplies continuation input/cursor to later turns; old catalog prices are not copied into context.

`getPublicCatalogItem` accepts `catalogType`, a catalog UUID `id`, and an optional cursor. It reads current public records directly, without embeddings or an extra model call. The SDK returns Markdown through `toModelOutput`. The audit result retains `{ markdown, nextCursor }`. Facts include current pricing terms, package capacity, description, and source identity/update time; canvas sections preserve authored Markdown in visual reading order, photo/video captions and alt text with media references, and visible linked-listing references. Service widgets in packages expose their included status and saved package-local hours/excess rates. Service-page references remain neutral, no widget applies price adjustments, and related canvases are not expanded recursively. Private add-ons remain excluded from public catalog reads. Pages contain up to 4,000 source Unicode code points plus continuation metadata and remain below a 32 KiB serialized-output limit. Cursors bind the item and rendered content; edits invalidate continuation. Later turns receive only validated selectors and the cursor from an earlier delivered same-conversation detail call, without replaying saved Markdown or prices. Missing/private/archived items and invalid continuations have sanitized failures. This tool adds no endpoint, migration, or chat rendering change.

`getMyProposal` takes no model-supplied arguments. Only signed-in customer turns receive it; guest turns remain ineligible even if claimed while running. The server binds the current conversation/customer, verifies conversation and linked-request ownership, and reuses the booking-package service to prefer the private custom package over the original catalog choice. Its JSON result is `{ status: "found", proposal }`, `{ status: "no_linked_request", proposal: null }`, or `{ status: "proposal_not_prepared", proposal: null }`. The proposal contains its type, name, description, capacity, current fixed PHP package price, update timestamp, and complete `sections[].widgets[]`; each Markdown string and hydrated media/linked widget remains intact. Content is not flattened, summarized, paginated, or recursively expanded. The model receives the full JSON; audit output stores status, result hash/character count, package type/update time, and section/widget counts without copying private text. Proposal results cumulatively consume the remaining 200,000-character context/history budget; oversized results fail explicitly without partial content. Access, tracking, and read failures remain errors rather than normal empty states. Existing activity, takeover, shared-call, and reply-link guards apply. Package facts are not quotation amounts or booking confirmation. This tool adds no endpoint, migration, or UI change.

Migration `20261118000000_ai_tool_calls` adds the server-only `ai_tool_calls` audit table. Each executed validated call has its own UUID, server-generated `turn_id`, invocation `tool_call_id`, `tool_name`, bounded JSON input/output, status, sanitized error code, and start/completion timestamps. Model-selected chat tools bind a required triggering `customer_message_id` and an optional resulting `assistant_message_id`; their reply links commit with the assistant message. Automatic `interpretMessageImage` calls bind the saved human `source_message_id`; its conversation is derived through that message. They run only after message acceptance, with separate attempt IDs and compact metadata/result hashes rather than image bytes, Storage keys or observation text. Saved observations are reused on retry; a crash before observation persistence can repeat a vision call. The additive `20261119110919_durable_message_processing` migration removes the earlier redundant audit conversation column; historical unsaved attempts can remain without a source, while new image attempts require one. Only `(turn_id, tool_call_id)` is unique; multiple calls can belong to one message. Provider failures and takeover can leave completed chat calls without a reply; a process stop may leave a `started` record. These rows are audit records, not durable retry jobs, and are not replayed as conversation messages. RLS and revoked client grants prevent direct browser access; there is no tool-trace UI or read API in this slice. Apply the matching migrations and API together. The [decision](context-factory/history/decisions/2026-11-18_catalog-search-and-tool-calls.md) records the original chat-tool ownership and scope.

System Administrators control an **AI on / AI off (Human)** toggle in each available conversation’s header, including general chats. New and existing conversations default to AI on. Successfully sending an admin message or quotation switches that conversation to human handling in the same transaction; failed sends do not. AI stays off until an admin explicitly re-enables it, across later customer messages. While off, customer messages save without a conversational AI reply; attached images still require the vision interpretation tool. Re-enabling affects future customer messages and does not generate a catch-up reply. Expired guest threads cannot be toggled.

`requestHumanHandoff` is available to active guest and customer turns. The model supplies only a validated reason (`customer_requested`, `needs_admin_review`, or `cannot_answer`) and a short admin summary; conversation, identity, triggering message, and AI version are server-bound. A conversation-locked transaction saves the latest `{ reason, summary, pending: true }` in nullable `conversations.ai_handoff`, switches AI off, advances `aiVersion`, and saves a fixed customer acknowledgement with the completed tool-call audit. Repeated calls for the same triggering message reuse that acknowledgement. The turn stops after success; later provider cancellation cannot undo the committed handoff. This requests review in the admin inbox without an external notification, assigned responder, or response-time promise.

Admin conversation lists, threads, send results, and AI-toggle results expose `aiHandoff`; customer and guest responses omit it. Pending handoffs show **Needs attention** in the inbox and header. The shared information control shows the reason on hover/focus and persistent reason, AI summary, and state on click/keyboard activation. Escape and outside interaction dismiss details. The first successfully saved admin message or quotation clears `pending` and advances the version even when AI was already off. Reading, failed sends, and manually resuming AI do not clear it. The reason remains available; a later handoff replaces the object. There are no takeover timestamps or separate handoff history table. Migration `20261118164653_conversation_ai_handoff` adds only the nullable JSONB column; deploy it before the matching API.

The admin-only `PATCH /admin/conversations/{id}/ai` accepts `aiEnabled` and `expectedAiVersion`; stale changes return 409. Conversation responses and admin send responses carry `aiEnabled` and `aiVersion`. Each turn captures the version atomically with its customer message and checks it under the conversation lock before saving an assistant reply. Takeover discards an unfinished reply even if AI is switched back on before it completes; a reply already committed before takeover remains in history. Browser polling cannot overwrite a newer confirmed AI preference.

Each generation also receives a fresh server-built JSON context from [assistant-context.ts](apps/api/src/services/ai/assistant-context.ts): the current ISO timestamp, the linked request's timezone (or `Asia/Manila` for general chats), and the selected conversation's customer-owned booking request or `null`. The request projection includes its reference, status, event type, guest count, requested dates/times, linked operational schedules, location preference, and special requests. Legacy requests without a complete requested-day list retain their saved preferred date and start/end times. The projection excludes package details, contact details, and internal IDs; it does not load another conversation's request. Context is labeled as current server data and placed immediately before the latest customer message; it is not saved as a chat message.

Each generation receives the full ordered history through its triggering customer message, without UI pagination. A combined 200,000-character context/history budget fails explicitly rather than silently truncating; the model/tool loop has a shared 30-second deadline, up to four model steps, an 800-token output budget per step, and no automatic retries. The model chooses tools during the first three steps; the fourth step requires a text answer, unless a successful handoff has already saved its acknowledgement and stopped the turn. At most six domain operations execute across all tools and at most twelve tool calls may be recorded, including rejected calls within that record limit. Oversized provider call batches are rejected before execution. Concurrent tabs can generate overlapping turns; replies append when completed, without strict turn serialization or durable retry/idempotency guarantees. AI text alone cannot change quotations, reserve dates, or confirm bookings.

## Authentication

New registrations create local customer accounts with Argon2id password hashes; passwords must contain 8–128 characters. Password hashing uses WebAssembly through `hash-wasm` in both Node and the Edge Function, with 19 MiB of memory, two passes, and parallelism one. Existing Argon2id hashes remain valid; no password reset or database migration is needed. Google sign-in and existing Firebase email/password accounts are optional identity methods. Application roles always come from PostgreSQL.

Run `pnpm --filter @event-management/api test:password` for password compatibility checks. With the current Edge bundle served by `pnpm dev` or `pnpm dev:edge`, run `pnpm --filter @event-management/api test:edge` to check session rejection, unknown-account password verification, route matching, and OpenAPI loading in the local runtime. After changing API code, rebuild with `pnpm build:edge` and restart the function server before running those runtime checks.

All methods use the `em_session` cookie and hashed sessions in PostgreSQL. The frontend restores the account with `GET /v1/me`. While the workspace remains open, it rechecks `/me` when the page regains focus or visibility and after a non-authentication data request returns `401`. A successful check refreshes the profile; a `401` clears it and returns the user to login with the local workspace URL saved for sign-in. Same-origin `/app` navigation uses browser history and does not remount the authentication provider. Sessions expire after `SESSION_TTL_DAYS` (default 7), rotate on successful sign-in/linking, and are deleted on logout. Cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` in production.

Account settings → Sign-in methods supports connecting Firebase to a local account after proving the current local password, or adding a local password after proving the connected Firebase identity. Firebase proof requires a verified email and a sign-in within five minutes. Matching emails never merge accounts automatically; linking preserves the database identity and role. Profile editing, local password reset, and local email-verification delivery are not implemented.

The only account roles are `customer` and `admin`. Admin access belongs to designated System Administrators; public registration creates customers, and the browser cannot assign or promote a role. Reload after an authorized role change so the frontend refreshes its profile.

Password attempts are limited in memory per account; multiple API processes require a shared limiter. Browser writes must pass the configured `WEB_ORIGIN` check. See the [authentication reference](context-factory/areas/api/references/auth-and-sessions.md) and running OpenAPI contract for route details.

2. Fill in the `PUBLIC_FIREBASE_*` fields in `apps/web/.env` using the web app configuration.
3. Configure `FIREBASE_PROJECT_ID` on the API and either `GOOGLE_APPLICATION_CREDENTIALS` pointing to a gitignored service-account JSON or `FIREBASE_CLIENT_EMAIL` plus `FIREBASE_PRIVATE_KEY`. Relative credential paths resolve from `apps/api`.

## Catalogs and media

Catalog packages and services are flat records with ordered canvas sections stored in `packages.canvas` and `services.canvas` as JSONB arrays. The document is a plain sections array with no schema-version field. A canvas save replaces the owner's full canvas and uses the owner's `expectedUpdatedAt` concurrency check; there are no independently versioned section or widget rows. A System Administrator catalog save publishes a complete record immediately. Packages feature services and other packages through linked canvas widgets. There is no separate included/optional service assignment list. Service pricing is catalog information and does not automatically calculate quotation amounts. Physical event locations are recorded on booking requests through `preferredVenueLocation`. Booking-owned custom packages are private and have a separate edit/audit flow. Updates require `expectedUpdatedAt`; stale or archived edits return `409`. Archive hides a record from public selection. A package referenced by a booking request cannot be deleted.

| Catalog | Required save data                                                                                                                                  |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Package | Name, positive `maxGuests`, fixed total PHP price, and canvas sections; the catalog description is separate from Markdown widgets.                  |
| Service | Name, description, positive whole-peso `hourlyRatePesos`, optional paired `fixedPricePesos` and positive whole `includedHours`, and a canvas photo. |

Package prices are stored as whole pesos; the API uses `{ kind: "fixed", currency: "PHP", amountMinor }` in centavos divisible by 100. Booking responses derive `packageName`, `packagePrice`, and `packageMaxGuests` from the referenced catalog package, or return null for these fields when none is selected. The current private proposal is read separately. Service saves require a positive whole-peso `hourlyRatePesos`; send both `fixedPricePesos` and `includedHours` as null for hourly-only pricing, or provide a positive fixed price and positive whole number of included hours together. A legacy service rate may be null on reads. Omitted service canvas sections preserve saved content.

Creating a catalog package or service opens a details modal before the canvas editor. Required fields are marked and validated before continuing; the modal does not save a record. Package descriptions remain optional. Services collect their description and pricing first, then require a photo in the editor before saving. The same details remain editable inside the editor.

Card thumbnails are optional and independent of canvas photos. An administrator-set thumbnail overrides the shared AMAC default; removing it restores the default. Public, customer, and admin cards, linked listing widgets, and reference pickers use the same default when no thumbnail is set or its image fails to load. API `imageUrl` contains only the dedicated thumbnail URL, or null; canvas photos never supply a card thumbnail automatically. The default is bundled presentation and creates no media record. Deploy the matching API and frontend together.

The shared editor uses photo, Markdown, video, and linked service/package widgets on a 12-column canvas. The editor, customer preview, and public detail page use the full available width with the same widget dimensions at the same screen width. Photos and videos fit inside their widgets without cropping; rendered text outside a widget is clipped without internal scrollbars. Markdown editing opens in a separate dialog so the canvas shows the rendered result. Editor guides and numbered columns use the actual snap geometry; each section shows its automatically growing row count from the lowest widget edge. Saves retain widget positions and spans, including intentional gaps. A widget can span at most 100 rows; sections have no separate fixed row count. Shared application schemas validate the canvas before browser uploads/saves and again in API requests, stored-document reads/writes, and seeds. Invalid canvas saves identify the affected section/widget in the editor. Pending file selections are validated before upload and require a saved media ID afterward. Editor previews, saved catalog overlays, booking package views, and server-rendered public details reuse the same app composition and shared canvas/widget renderer; embedded booking views adapt to their containing area. Media uploads go through `POST /v1/admin/catalog-media`, remain pending until a catalog save references them, and stream through `/v1/catalog-media/{id}`. JPEG/PNG/WebP images allow up to 10 MiB; MP4/WebM videos allow up to 25 MiB. Photo/video widgets accept uploads only, with built-in sample photos retained for seeded packages; external URLs and hosted-player embeds are rejected. Video autoplay is opt-in and uses muted inline playback on customer previews and public pages.

The editor offers Photo, Markdown, Video, and Service widgets. Adding new Package widgets is temporarily hidden in catalog package, service, and private proposal editors. Existing package widgets remain visible, editable, and saveable; their stored references and public navigation are preserved. This editor-only change needs no migration or API change.

Service and package widgets feature an existing catalog listing without creating a package inclusion or changing package/quotation prices. In edit mode, clicking the widget body opens active choices of that kind directly, with search, photos, descriptions, pagination, an optional caption, and keyboard dismissal/focus restoration. Private custom packages are excluded. In public pages and previews, the whole card links to the selected listing's detail page. Inside `/app`, the whole card instead opens a detail preview overlay while preserving the current route and underlying preview or editor. Following another service or package replaces the overlay content; closing it returns focus to the original card. Workspace navigation closes the overlay and restores page scrolling. Saved widgets store a service or package ID; reads resolve its current name, description, photo, and public link without pricing or nested canvases. Archived targets show an unavailable placeholder; existing references remain editable, but new unavailable references cannot be saved. A listing referenced by a package or service canvas cannot be deleted. Knowledge ingestion indexes the widget caption only, so renames do not leave copied listing details in another listing. No database migration is needed; deploy the matching shared contracts, API, and frontend together.

The private bucket uses this filing structure (IDs remain stable when names change):

```text
event-management/
├── packages/<package-id>/images/<media-id>.<ext>
├── packages/<package-id>/videos/<media-id>.<ext>
├── services/<service-id>/images/<media-id>.<ext>
├── services/<service-id>/videos/<media-id>.<ext>
├── bookings/<booking-id>/custom-package/images/<media-id>.<ext>
├── bookings/<booking-id>/custom-package/videos/<media-id>.<ext>
└── pending/<admin-id>/<media-id>.<ext>
```

Saving a listing promotes its new pending uploads by copying bytes into the owner folder, switching the stored key, then removing the pending copy. A failed copy leaves the saved listing using its readable pending file; a later save retries promotion. Dedicated thumbnails use the same owner folders. API media URLs and access checks remain unchanged; folder names do not grant access. Original filenames are not retained.

**Development scope:** Clemora has not reached production. Existing documents and uploaded files do not need migration or preservation for this redesign. There is no storage backfill command or move-tracking table, and this change does not delete existing bucket objects. The folder structure applies to new uploads and their subsequent saves. Interrupted promotion can leave an unreferenced object; this development implementation does not add a durable recovery queue. See [catalog media](context-factory/areas/api/references/external-image-urls.md) for lifecycle details.

Public media streaming requires a reference from a published, non-archived catalog record. System Administrators can preview pending uploads and saved private media under the API access rules. Owners can preview media currently referenced by their private package; private responses use no-store caching. Quotations do not retain historical media or grant media access. Removing uploaded media triggers cleanup only when no current canvas or thumbnail references it; storage failures can leave unreferenced assets for retry. See [catalog media](context-factory/areas/api/references/external-image-urls.md) for storage, cleanup, and migration details, and [shared limits](context-factory/areas/contracts/SKILL.md) for validation ownership.

## Database workflow

For schema changes, edit `apps/api/prisma/schema.prisma`, create and review the migration, then regenerate Kysely types:

```sh
pnpm db:migrate
pnpm db:generate
pnpm check
```

`pnpm db:deploy` applies committed migrations; it does not create migrations. Never hand-edit generated `apps/api/src/db/types.ts`. Inspect both Prisma and SQL migrations because some database constraints extend beyond the Prisma model.

The type generator includes application tables in `public` only, excluding Supabase's internal schemas. Migration `20261110141853_event_day_staffing` is historical: it introduced operational event days along with availability and assignment tables. Later additive migrations remove those tables and response fields while keeping admin event-day scheduling.

Migration `20261109140000_enable_application_rls` enables row-level security on application tables and Prisma's migration history. It removes table grants from `PUBLIC` and, when present, Supabase's `anon` and `authenticated` roles. Clients access records through Clemora's session-aware API; there are no direct-client RLS policies. The server database role must own the tables or have `BYPASSRLS`. Future table-creation migrations must explicitly enable RLS and remove unused client grants too; this migration does not install an automatic trigger. These SQL-only access settings do not change Prisma models or generated Kysely types.

Migration `20261111150000_simplify_quotation_offers` deliberately discards quotation package timestamps and full package/event-term snapshots. It preserves quotation IDs, package references, amounts/items, status and acceptance timestamps, revision links, audit events, and quotation messages. It does not delete Storage objects; normal cleanup can remove uploads that no current widget references. Deploy the matching API and web changes together with this migration.

Migration `20261120124456_derive_conversation_activity` removes conversation `status`, `closed_at`, and `guest_expires_at`, preserving conversations, messages, quotation links, ownership, and AI preferences. Previously closed signed-in conversations become available. Anonymous expiry is derived from the latest saved message or creation time. Deploy the matching API, frontend, and background worker together; older runtimes query removed columns. The migration replaces the guest ownership check and active-thread unique index with ownership validation and a guest-history lookup index. Bootstrap serializes on the guest identity to reuse one unexpired thread without deleting expired history.

Migration `20261120121409_remove_quotation_acceptance` removes `quotations.accepted_at`, the `accepted` quotation status, and its partial unique index. It does not transform quotation rows or support retired statuses. Acceptance timestamps are deliberately discarded, while supported quotation versions, prices, adjustments, revision links, delivery messages, and audit history remain. Booking-request acceptance is unchanged. Deploy the matching API and web code with this migration and regenerate database types.

Migration `20261111120000_booking_requested_days` adds nullable JSONB `booking_requests.requested_days` with a check that non-NULL values are nonempty arrays. SQL `NULL` identifies requests created before customers selected a complete date list. The migration does not backfill dates or rewrite the legacy estimate, timestamps, snapshots, conversations, or operational event days.

Migration `20261114000000_drop_venues` removes the venue catalog and its package link; `20261114010000_drop_staff_tables` removes availability and assignment tables plus event-day staffing fields. The additive `20261114151517_complete_catalog_staff_removal` migration revokes sessions for former staff and admins without the System Administrator designation, converts those accounts to customers, and drops `users.staff_role`. At that stage, it also deletes catalog pages left without an owner, restores the temporary package/service page-owner constraint, and removes coordinator/checklist delivery metadata. Migration `20261116072801_embed_catalog_canvas` later embeds the remaining canvases and drops the page hierarchy. Follow-up migration `20261114154206_remove_event_checklists` drops the event-checklist table and its content validator, removing stored task definitions and progress. The migrations keep shared media assets and Storage objects; `pnpm --filter @event-management/api media:cleanup` removes stale unreferenced media through the existing cleanup path.

Migration `20261116063852_derive_booking_package_details` drops `booking_requests.package_name`, `package_price`, and `package_max_guests`, including their stored values and column checks. Existing requests keep their package references, dates, statuses, conversations, and schedules; package details use the current catalog record, including archived records. Private proposals and saved quotation amounts retain their separate ownership. Deploy this migration with the matching API; old API code requires the removed columns.

Migration `20261116072801_embed_catalog_canvas` adds `packages.canvas` and `services.canvas`, backfills the ordered section/widget arrays while preserving their IDs and content/media references, then drops `catalog_widgets`, `catalog_sections`, and `catalog_pages`. At that stage, package/service owner timestamps, `media_assets`, uploaded Storage objects, and relational `package_services` links were preserved; the later assignment-removal migration below drops the link table. Follow-up migration `20261116090100_validate_catalog_canvas_in_app` removes the SQL canvas validator and its two check constraints without changing canvas data, owner timestamps, defaults, NOT NULL constraints, or GIN indexes. Canvas document validation belongs to the shared browser/API application schemas; direct SQL writes bypass those rules. Deploy the matching application validators with this migration; see the [catalog canvas decision](context-factory/history/decisions/2026-11-16_catalog-canvas-jsonb.md) and [database guidance](context-factory/areas/api/references/database-and-migrations.md).

Migration `20261118121512_remove_package_services` drops `package_services` and its included/optional assignments. It preserves package/service records and canvases, prices, bookings, quotations, audit history, and media. It removes only derived overview chunks for packages that had assignments, preventing old inclusion text from remaining searchable; those overviews remain pending until the ordinary catalog save or `pnpm --filter @event-management/api catalog:embed` workflow recreates them. The latter command calls the configured embedding provider. Package request/response contracts no longer contain `services`; old payloads are rejected. Deploy the matching API and frontend with this migration. Historical migrations still create the table before its removal and must remain unchanged. See the [removal decision](context-factory/history/decisions/2026-11-18_remove-package-service-assignments.md).

Migration `20261116090000_service_fixed_pricing` adds nullable `services.fixed_price_pesos` and `services.included_hours`. The constraint permits hourly-only rows with both fields null or fixed pricing with both positive and a non-null hourly rate. Existing service rates, including legacy null rates, are preserved. The migration does not change quotation data or calculations.

Migration `20261116103220_add_catalog_knowledge` enables pgvector and creates the empty `catalog_knowledge` table without changing catalog records or Storage objects. The PostgreSQL server must provide the `vector` extension; plain `postgres:17` images do not include it. The migration reuses an existing extension in its current schema. Each row has exactly one package/service owner, a unique chunk key within that owner, and either an entirely pending or entirely populated embedding state. Owner and media deletion cascade to their derived rows. RLS and revoked client grants preserve server-only access. The ingestion services enforce catalog-only, non-archived eligibility, input invalidation, and stale-result protection; these behaviors are not supplied by foreign keys or this migration. Admin search enforces current-source and model/preprocessing compatibility. Any future customer retrieval must additionally enforce its customer visibility policy before exposing evidence.

Migration `20261116083246_conversation_ai_control` adds `conversations.ai_enabled` (default true) and `ai_version` (default zero). It preserves messages and existing conversation status, and does not infer historical takeover from old admin messages. Apply it before the matching API; deploy the updated API and browser contracts together.

Migration `20261116155140_anonymous_guest_chat` adds server-only guest identities and message-request deduplication, guest conversation ownership/deadlines/counts, and explicit anonymous message provenance. Existing account-owned conversations and messages remain intact. Exclusive ownership and sender constraints, a unique active guest conversation per identity, RLS, and revoked direct client grants protect the new state. Apply the migration before the matching API and deploy the browser contract changes together; the generated Kysely types include the new tables and nullable customer ownership. Claimed anonymous messages retain their original provenance.

Migration `20261116061207_add_ai_message_replies` makes the message sender nullable only for the new `assistant` role; human sender IDs remain required. It preserves existing messages and conversation lifecycle. Deploy the matching API and browser contracts together.

**`pnpm db:reset` deletes data without a confirmation prompt.** Its script forces a Prisma reset, reapplies migrations, and seeds the configured database. Check the target and use it only for a database whose contents may be discarded.

### Migration impact

Migration `20261120120000_package_service_terms` adds `packages.addon_services` with an empty-array default, an array constraint, a custom-package-only constraint and a GIN reference index. It preserves existing prices, canvases, booking/quotation records and audits; existing widgets retain unspecified terms. Deploy the migration with matching API/web code. This work does not apply the migration to hosted or configured application databases.

Review all pending migrations before upgrading a populated database:

- `20261102130000_package_canvas` removes existing packages, package versions and service assignments, booking requests and status history, and booking-linked conversations/messages. General conversations and messages remain.
- `20261102180000_flat_services_venues` retains selected current content, or archives the latest content when none was published. It removes version tables and unselected canvas pages; uploaded storage objects are not deleted.
- `20261102190000_cleanup_catalog_fields` renames guest limits to `maxGuests` / `max_guests` and snapshots to `packageMaxGuests` / `package_max_guests`. It discards package event types, venue categories/photo URLs, and legacy service-image references. Existing canvas content and inquiry snapshots remain. Legacy storage objects are not removed remotely.
- `20261109140000_enable_application_rls` preserves records and blocks direct table access for Supabase client roles. Apply it as the table owner and verify the API database role before deployment. `pnpm db:deploy` targets the database configured for the API; creating this migration does not apply it to the separate local Supabase stack.
- `20261111120000_booking_requested_days` adds the nullable requested-date JSONB column and array constraint without fabricating missing dates or rewriting existing booking data.
- `20261114000000_drop_venues` removes venue listings, package/venue links, and the venue catalog-page owner column. Any ownerless pages are deleted by the follow-up cleanup migration.
- `20261114010000_drop_staff_tables` removes event availability and assignment tables and the event-day response fields.
- `20261114151517_complete_catalog_staff_removal` revokes sessions and converts staff and non-designated admin accounts to customers, leaving designated System Administrators as admins. It drops the remaining staff-role and coordinator/checklist-delivery fields, deletes ownerless catalog pages, restores the temporary package/service owner check, and preserves media assets and Storage objects; the later embed migration drops the remaining page hierarchy.
- `20261114154206_remove_event_checklists` drops `event_checklists` and `clemora_checklist_content_valid(jsonb)`, removing saved checklist tasks and progress. Earlier migration files remain unchanged as historical evidence.
- `20261116072801_embed_catalog_canvas` moves package/service canvas content into owner JSONB arrays, preserving section/widget IDs, order, content, and media IDs before dropping the former page/section/widget tables. It does not change media assets or uploaded objects.
- `20261116090000_service_fixed_pricing` adds paired nullable fixed-price and included-hours fields to services, requiring both to be positive together and requiring an hourly rate when fixed pricing is set. Existing hourly rates remain unchanged.
- `20261117000000_optional_booking_package` permits a null catalog package on booking requests and updates the existing catalog-only trigger to accept that state. Existing package associations, requests, messages, permissions, and private proposals remain intact. Deploy the matching API and browser code together: package fields are nullable, and a missing proposal is a valid read state.

Back up affected records before deployment. Apply coordinated API/frontend contract changes with their migrations; do not edit applied migrations or reset a database to resolve drift. ## Source formatting

Run `pnpm format` to format source and configuration files with Prettier, then fix
blank-line spacing with ESLint. Run `pnpm format:check` to check both without
writing changes. Prettier covers JavaScript, TypeScript, React JSX/TSX, CSS, JSON,
and YAML; `prettier-plugin-astro` adds Astro files. It uses two-space indentation
and an 80-character wrapping target.

The [ESLint configuration](eslint.config.mjs) adds blank lines after import groups,
between top-level declarations, around callback declarations and control flow,
and before returns in JavaScript, TypeScript, TSX, and Astro scripts. Consecutive
simple scalar declarations stay together. Existing intentional blank lines
are preserved; logical grouping still needs judgment. Run `pnpm lint` to check
spacing alone or `pnpm lint:fix` to fix it. `pnpm check` also runs the spacing check.

In VS Code or Cursor, install the recommended Prettier and ESLint extensions to
format and fix spacing on an explicit save. The Astro extension is also recommended.
Generated files, lockfiles, migrations, assets, local data, imported agent tooling,
and historical documentation are excluded through `.prettierignore` and the matching
ESLint ignores. The root README remains included so these instructions can be
checked with the source.
