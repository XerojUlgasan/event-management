# Styled by AMAC

**Styled by AMAC** is the website's visible brand, replacing the previous Clemora identity. The supplied AMAC logo guides its charcoal, off-white, and taupe theme across public pages, login, and workspaces. This pnpm event-management workspace contains an Astro/React frontend, Hono OpenAPI backend, and shared UI, theme, and contract packages. PostgreSQL stores application records; Prisma owns schema changes and migrations, and Kysely handles runtime SQL. Original client research for **Prevail Events Management** is preserved in the interview records; the visual rebrand does not change product scope or establish a legal ownership change.

The original logo is owned by `packages/ui/src/assets/`; shared colors and typography remain in `packages/theme/src/theme.css`. Existing package names, API routes, and browser storage keys retain their technical identifiers.

This README owns product scope, current implementation status, and development setup. The [interview summary](docs/PREVAIL_INTERVIEW_SUMMARY.md) records client evidence and distinguishes it from later scope decisions. The [seed guide](docs/SEED.md) covers development fixtures and repeat runs.

The [identity reference](context-factory/business/identity.md) defines these intended responsibilities. The only account roles are customer and admin; admin access is reserved for designated System Administrators.

The [messages reference](context-factory/business/messages.md) describes intended booking-linked communication. Quotations are the implemented booking-related transaction; other transaction types remain undefined within the scope boundaries below.

A request does not reserve a date, establish a final price, or confirm a booking. Confirmation rules remain to be agreed and must not be inferred from payment.

**Outside scope:** all payment responsibilities, including gateways, proof uploads, verification, payment records/status, balances, fee calculation or crediting, and receipts; equipment/inventory management; and supplier management or coordination. Existing demo screens do not establish requirements.

**Later work:** menus, additional policy/term configuration, broader AI knowledge maintenance, reports, and the managed past-events showcase.

Before implementing dependent work, confirm intake fields and real catalog content/prices; any further quotation format or approval policy changes; confirmation, date holds, cancellation and event-change rules; assistant sources and any automatic handoff rules; and report/showcase definitions. Meta and other channel integrations require separate decisions.

## Current implementation

Catalog embedding ingestion uses the server-only `catalog_knowledge` table from migration `20261116103220_add_catalog_knowledge`. Non-archived catalog packages and services produce overview text, original Markdown chunks, and individual photo chunks with listing/section context, alt text, and captions. Uploaded and checked-in sample photos send their actual bytes with that context to `google/gemini-embedding-2`; WebP converts to PNG for embedding, and videos are skipped. Vectors have 768 dimensions and are normalized. Catalog saves reconcile derived rows in their existing transactions, then refresh embeddings after commit; service renames and archives also refresh dependent package overviews. Unchanged inputs retain their vectors, and guarded writes reject results superseded by catalog edits. Admin semantic search is available in the Knowledge Catalog; AI knowledge tools and assistant retrieval remain unimplemented. Migration deployment is a separate operational step. See the [ingestion decision](context-factory/history/decisions/2026-11-16_catalog-embedding-ingestion.md) and [storage decision](context-factory/history/decisions/2026-11-16_catalog-knowledge-storage.md).

Customers browse **Catalogs** at `/app/catalogs`, with Packages and Services tabs. Older customer `/app/packages` links open the same catalog. Filters start collapsed and open from the filter icon beside the results count; closing the panel preserves entered values and active filters. Package filters use inclusive total-price ranges in whole PHP pesos and a guest count. Service filters select fixed-price or hourly-only listings, then apply inclusive ranges to the fixed base price or hourly rate, respectively; excess-hour charges are not part of the fixed-price range. An hourly-only price range excludes services without a known rate. Package guest counts match listings with enough capacity. Applying or clearing filters starts at page 1, and Next/Previous returns focus and scroll to the catalog top. Browsing and package inquiries do not confirm a booking or final price.

### Admin knowledge catalog

System Administrators open **AI → Knowledge Catalog** at `/app/ai/knowledge`. The dashboard shows separate package and service indexing coverage, listings needing attention, and searchable, cursor-paged listings. Coverage uses all eligible non-archived catalog packages and services, including unpublished listings and owners with no knowledge rows. A listing counts as indexed only when every expected chunk matches its current source identity, pipeline, model, and recorded input digest, with no withdrawn rows remaining. Empty eligibility shows no percentage. Table filters do not change the global coverage totals.

The admin-only `GET /admin/ai/knowledge` and `GET /admin/ai/knowledge/{kind}/{id}` read a consistent database snapshot without reconciling rows or calling an embedding provider. The detail drawer previews stored text and authorized photos; missing rows show expected pending content, and withdrawn chunks are labeled and excluded from coverage. **Open listing** opens the exact package/service preview. Pending does not distinguish failed work from work awaiting execution. Photo freshness assumes immutable upload identity; these reads do not download image bytes again or verify current Storage availability. **Refresh** reloads dashboard data and does not retry embeddings. Assistant catalog retrieval remains unimplemented.

**Search knowledge** embeds an explicitly submitted query with the configured `google/gemini-embedding-2` model and returns up to five text/photo matches ordered by cosine similarity. The admin-only `POST /admin/ai/knowledge/search` accepts `{ query }` (1–500 characters after trimming). It searches current indexed chunks from non-archived services and packages of type `catalog`, including unpublished listings; custom packages, pending, incompatible, stale, and withdrawn chunks are excluded. Results appear as compact rows with only the source package/service title and an optional left thumbnail. Clicking anywhere on a row opens that listing's preview overlay immediately, with loading and retry states, while the Knowledge Catalog stays open behind it. The API retains similarity scores; there is no relevance cutoff. Provider/configuration failures return a sanitized 503. Search makes one embedding request per submission without changing knowledge rows or connecting the customer assistant. The existing table search continues to filter listing names.

### Booking requests and messages

Customers follow their requests at **My events** (`/app/events`) in a timeline grouped into Today, Upcoming, Dates to arrange, Past dates, and Closed requests. Empty groups stay hidden except Upcoming. Grouping uses requested dates in each request’s timezone; a multi-day request uses its next requested date, or its most recent date once all have passed. These groups do not describe operational progress or confirm bookings. Cards show status, requested dates and times, and details/chat actions. Details retain time editing, operational schedules, status history, and cancellation. Earlier requests load into the same timeline; while more pages remain, counts describe loaded requests, and additional upcoming dates may still be on an earlier page.

The current intake requires a customer session and a published package. It collects event type (Birthday, Wedding, Corporate, or a custom choice), one date or Multi-day dates, contact name and phone, and optional notes. Multi-day requests need at least two distinct dates; dates may be nonconsecutive and are saved chronologically. The booking timezone comes from the browser and determines whether a date is today or in the future. A signed-out visitor's current-tab draft retains the duration mode, date rows, other fields, and timezone through sign-in, then requires explicit review before submission.

New requests store the complete date list in `requested_days`; `preferred_date` remains the earliest selected date for compatibility. Each requested-day entry starts with no times. Customers can later save start and end times for each unscheduled day from My events or the booking-details modal opened from a linked customer conversation. Both times are required, interpreted in the booking timezone, and may end on the following date for an overnight event. The chosen dates stay fixed. Customers can edit times while a request is `under_review`, `needs_details`, or `accepted`, until an operational schedule is created for that day. Declined and cancelled requests, and already scheduled days, are read-only. Views show “Time to be confirmed” until both times are saved.

The admin Bookings calendar counts a request once on every requested date and applies the same status filter as its results. Selecting any requested date finds the request once in the cursor-paged table; the `preferredDate` API filter matches any requested day for new requests. Legacy rows with SQL `NULL` in `requested_days` keep their recorded preferred date and estimate; the system does not invent additional dates. The admin table shows a compact requested-date summary and links each request to `/app/bookings/{id}`, where a System Administrator can review per-day times and operational schedule state.

On `/app/bookings/{id}`, requested-date rows appear in the Event days section, including dates still waiting for customer times. Acceptance and saved times alone create no operational schedule. After accepting a request, the System Administrator can schedule ready requested days with `POST /admin/event-days/schedule-requested-days` and `{ bookingRequestId, expectedUpdatedAt }`. The API creates and links operational days for requested entries that have both times and no existing day; a stale request revision rejects the batch. Requested dates without times remain unscheduled until the customer provides them. Older requests without a requested-day list retain manual event-day creation. An admin can move or cancel an operational day; a moved day links to a replacement and retains the original record. Requested dates, saved times, acceptance, or schedules do not reserve a date or confirm a booking. `preferredVenueLocation` records the customer's preferred physical event location; it is not a catalog selection. The API also accepts an optional guest count.

Requests retain `package_id`; their name, price, and maximum guests are read from that package. Later catalog edits appear on existing requests, conversation headers, and event-day lists. A supplied stale `packageUpdatedAt` returns `409`. Requests start as `under_review`; other statuses are `needs_details`, `accepted`, `declined`, and `cancelled`. Acceptance is for processing only. Customers can cancel their own open requests. Only System Administrators can update review status. `preferredVenueLocation` is a customer-entered physical location preference.

Both message workspaces refresh every five seconds. Opening a conversation marks the other side's messages as read; messages allow up to 4,000 characters. Scrolling to the bottom of either inbox automatically appends older conversations. Scrolling up through a conversation automatically loads earlier messages while keeping the visible message in place. Regular polling retains loaded history and follows new messages when the reader is already near the bottom; a detected gap resets the thread to its newest boundary with a notice. Loading failures pause automatic pagination until retried.

Both linked conversation headers provide separate Details, Current package, and Quotation controls. Details shows event and contact information in a drawer, with a link to My events for customers or the booking workspace for admins; eligible scheduling changes remain in those workspaces. Current package opens the existing full package preview, including the booking’s private custom package, without a new booking action. Quotation opens the latest version that was actually sent, including a superseded offer while a newer draft is being prepared; unsent drafts are excluded. Quotation messages continue to open their exact linked versions. General conversations have no booking-context controls. The composer supports multiline drafts retained per conversation while Messages remains mounted, with Ctrl/Cmd+Enter to send.

Conversations have no automatic expiry. Booking-linked threads stay active regardless of their age, parent end time, or message activity. An expiry policy is deferred for future bookingless conversations; the existing general-chat routes also have no timer. Existing closed threads retain their status; a customer message can reopen a general conversation, while a closed booking-linked thread remains read-only. Closed history is retained. There is no public guest chat. The signed-in customer Messages flow automatically saves a text-model reply after each accepted customer message; admin messages do not trigger generation.

### Private packages and quotations

The inquiry retains its original catalog `package_id` and reads its current name, price, and guest limit from that record. Its current proposal is the private package identified by `custom_for_booking_request_id`, falling back to the original catalog record when no custom package exists. Admins select a catalog base, copy its content and uploads independently, and edit that booking’s custom package thereafter. Private packages are excluded from public catalogs, public slugs and new inquiry selection. Catalog title/address behavior is preserved; private copies may retain the same title.

From the admin booking page, System Administrators create a quotation draft from the current proposal, save ordered manual additions/deductions, and send the saved version. Empty adjustment lists are valid. The server validates every item and optional service reference and atomically saves JSONB items with the computed integer-centavo total. Each version retains its package ID, base amount, adjustments and computed total. Package content, services and event details remain on the booking and current proposal; quotations do not copy or automatically compare them. Later edits do not change saved quotation amounts or block sending. An administrator explicitly starts a revision when a new offer is needed; the revision uses the current proposal price and copies prior adjustments for review.

Sending atomically records the quotation, audit event and a version-linked conversation message. A closed linked conversation blocks sending; sending does not reopen it. Quotations have no automatic expiry. Any System Administrator can edit, revise or send, with audit attribution. Starting a revision immediately supersedes the prior offer and creates an internal draft for adjustment review. Customers see sent history and discuss agreement, concerns, or requests for a new quotation through chat. Customer replies do not change quotation status or create drafts. Internal drafts remain hidden. Existing accepted quotations and their timestamps remain readable as historical records and can still be revised by an administrator; there is no customer quotation acceptance or revision endpoint. Quotations and chat replies do not confirm a booking, reserve dates, or create event days.

The additive `20261111130000_private_packages_quotations` migration creates service links, JSONB quotations and audit events, adds private ownership and message references, and applies constraints, RLS and restricted grants. It does not replay err12’s booking simplification or remove inquiry snapshots/timezones. The follow-up `20261111150000_simplify_quotation_offers` migration removes the package timestamp and full terms snapshot from quotations while retaining financial values, version/status history, audit events and message links. Apply pending migrations to the intended database before using these screens; generating types or passing tests against disposable databases does not migrate an application database.

### Operational event days

Accepted booking requests can have multiple event days, each with a date, full start/end timestamps, and the booking's timezone. The customer supplies requested dates and times; acceptance and saved times alone do not create operational schedules. A System Administrator schedules ready requested days with `POST /admin/event-days/schedule-requested-days`, sending `bookingRequestId` and `expectedUpdatedAt`. The API creates and links days for requested entries that have both times and no existing day, and rejects stale request revisions. Older requests without a requested-day list retain manual event-day creation. An administrator can create, move, or cancel operational days; a moved day links to its replacement and keeps the original history. Scheduling does not reserve a date or confirm a booking.

The initial AI pipeline is `customer message → saved conversation history and current context → text-model reply → saved assistant message`. It uses Vercel AI Gateway and the configured `TEXT_MODEL`; there are no tools, retrieval, or decision-model calls in this slice. The send response includes the saved customer message plus `assistantMessage` or a sanitized `assistantError`. Provider failure leaves the customer message saved and clears the composer instead of inviting a duplicate resend. Assistant messages have no human sender ID and count as unread for the customer.

System Administrators control an **AI on / AI off (Human)** toggle in each active conversation’s header, including general chats. New and existing conversations default to AI on. Successfully sending an admin message or quotation switches that conversation to human handling in the same transaction; failed sends do not. AI stays off until an admin explicitly re-enables it, including when a general conversation reopens. While off, customer messages save normally without a provider call or an AI error. Re-enabling affects future customer messages and does not generate a catch-up reply. Closed threads keep their existing lifecycle and cannot be toggled.

The admin-only `PATCH /admin/conversations/{id}/ai` accepts `aiEnabled` and `expectedAiVersion`; stale changes return 409. Conversation responses and admin send responses carry `aiEnabled` and `aiVersion`. Each turn captures the version atomically with its customer message and checks it under the conversation lock before saving an assistant reply. Takeover discards an unfinished reply even if AI is switched back on before it completes; a reply already committed before takeover remains in history. Browser polling cannot overwrite a newer confirmed AI preference.

Each generation also receives a fresh server-built JSON context from [assistant-context.ts](apps/api/src/services/ai/assistant-context.ts): the current ISO timestamp, the linked request's timezone (or `Asia/Manila` for general chats), and the selected conversation's customer-owned booking request or `null`. The request projection includes its reference, status, event type, guest count, requested dates/times, linked operational schedules, location preference, and special requests. Legacy requests without a complete requested-day list retain their saved preferred date and start/end times. The projection excludes package details, contact details, and internal IDs; it does not load another conversation's request. Context is supplied as data before history and is not saved as a chat message.

Each generation receives the full ordered history through its triggering customer message, without UI pagination. A combined 200,000-character context/history budget fails explicitly rather than silently truncating; generation has a 30-second timeout, an 800-token output budget, and no automatic retries. Concurrent tabs can generate overlapping turns; replies append when completed, without strict turn serialization or durable retry/idempotency guarantees. AI text alone cannot change quotations, reserve dates, or confirm bookings.

## Local development

Requires Node.js 22.22+, pnpm (the version is pinned in `package.json`), and Docker with Docker Compose.

```sh
pnpm install
pnpm dev
```

`pnpm dev` starts the local Supabase stack, serves the edge function, and starts the website at <http://localhost:4321/>. `pnpm all` remains the Compose PostgreSQL path: it creates `apps/api/.env` from its example if missing, starts PostgreSQL and waits for its healthcheck, applies committed migrations, then starts the Node API and web servers. Local email/password sign-in works without Firebase configuration. Catalog uploads use the private Supabase Storage bucket `event-management`; object keys stay `catalog-media/<id>`. The edge runtime supplies its own Storage URL and service role. The Node API needs `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from the API example.

**Existing databases:** review pending migrations and back up affected data before `pnpm all`, `pnpm dev:prepare`, or `pnpm db:deploy`; these commands apply migrations. See [migration impact](README.md#migration-impact).

`pnpm agents:sync` runs once and copies missing entries from any of the four folders into the others, including hidden files, subfolders, and symbolic links. It creates missing folders and preserves existing files. Conflicting contents or entry types at the same relative path are reported and skipped, including descendants of conflicting paths; the command exits with status 1 after syncing unambiguous additions. It does not propagate edits or deletions: a file removed from one folder is restored from another on the next run. Rerun it after adding files to any folder.

`Ctrl+C` in `pnpm all` stops the Node API and website; Compose PostgreSQL stays running until `pnpm db:down`. The seed is separate from startup and does not overwrite catalog edits or archives. See [database seed](docs/SEED.md) for coverage, collisions, and verification. Sample content and prices are not business-approved offers.

### Local Supabase

`apps/supabase` is the local Supabase CLI project, pinned to CLI 3.0.0. `pnpm supabase:start` requires Docker and starts its own Postgres 17, Studio, and Storage. Postgres listens on `127.0.0.1:54322`, the API gateway on `54321`, and Studio on `54323`. This stack can run beside `pnpm db:up`. Local Storage declares the private `event-management` bucket in `apps/supabase/config.toml`. Restart the stack after pulling that bucket so Storage creates it. New catalog objects use the key `catalog-media/<id>`; this change does not copy objects already stored elsewhere.

The Node API, Prisma, seeds, and integration tests still use Compose PostgreSQL from `apps/api/compose.yaml` on port 5432. Do not point that API's `DB_HOST` at the Supabase database until that cutover is explicit. Supabase Auth is not the application sign-in.

`pnpm dev` starts this stack when it is not already running, bundles the Hono routers into one Edge Function at `apps/supabase/functions/api`, and serves that function with the website. A request loads only the matching route family. The browser calls the website origin at `/v1`. The Astro dev server proxies that path to `http://127.0.0.1:54321/functions/v1/api`. The Supabase gateway sends `Access-Control-Allow-Origin: *` and answers preflight itself; browsers reject that header when a request includes the session cookie, so the page does not call the gateway directly. Direct checks, such as the health URL in the service table, can still use the gateway. The function reads `apps/supabase/.env.functions`, which `pnpm dev` creates when missing. Inside the function container the database host is `db` on port `5432`. That host is the Supabase database, not Compose. The local edge runtime uses `oneshot` mode so a bundle rebuild does not hot-reload the container. Restart `pnpm dev` after `pnpm build:edge` to load a new bundle. If the function server exits, `pnpm dev` starts it again and leaves the website running. `Ctrl+C` stops both; the Supabase stack stays up until `pnpm supabase:stop`.

### Configuration

Environment access, parsing, and defaults are centralized per app:

- API, including the Edge bundle and API commands: [`apps/api/src/utils/env.ts`](apps/api/src/utils/env.ts). Getters preserve on-demand reads; importing the utility does not require database, Firebase, or Storage configuration. Existing entry points still load dotenv.
- Browser: [`apps/web/src/lib/env/env.ts`](apps/web/src/lib/env/env.ts). Only explicit `PUBLIC_*` settings enter this module; they are captured at build time. Firebase setup stays optional.
- Web server and Astro config: [`apps/web/src/lib/server/config/env.ts`](apps/web/src/lib/server/config/env.ts). Server getters read the runtime environment. Astro config reads shell-provided variables before Astro loads `.env` files.

Use these utilities instead of reading `process.env` or `import.meta.env` in consumers. `pnpm check:env` enforces the source boundary and runs in `pnpm check`; tests and generated Edge bundles are excluded. Compose and Supabase configuration still use their native environment loading. The standalone cleanup script uses the API utility with Node's built-in TypeScript support, keeping its own dotenv path and local-only guards.

Use the checked-in [API environment example](apps/api/.env.example) and [web environment example](apps/web/.env.example) for variable names. Keep `.env`, `.secrets/`, database values, session tokens, and service-account contents out of chat and commits.

- Database: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, and `DB_PASSWORD` configure the API, Prisma, and type generator. A separate `DATABASE_URL` is unnecessary. Compose reads `apps/api/.env`; its project name remains `event_management_v2` to reuse the existing volume.
- API listener: `API_PORT` defaults to `3000`. Browser/server API URLs remain separately configured; changing the listener port does not rewrite them.
- Web proxy: optional `API_PROXY_TARGET` points to the Supabase gateway. `pnpm dev` sets it for both Astro config and request-time proxying. The catalog server loader prefers this proxy; otherwise it uses an absolute `PUBLIC_API_URL`, with `http://127.0.0.1:3000/v1` as its server fallback.
- Browser API: `PUBLIC_API_URL` points to the API including `/v1`. `pnpm dev` sets it to `/v1` on the website origin. `pnpm all` uses the web environment value, which defaults to `http://localhost:3000/v1`.
- AI replies: set server-only `AI_GATEWAY_API_KEY` and `TEXT_MODEL` (selected: `deepseek/deepseek-v4.1-flash-1017`) in `apps/api/.env` for Node or `apps/supabase/.env.functions` for local Edge. The files are separate; restart the function server after changing Edge settings. Configuration is checked on use; decision and embedding settings are not required for text replies.
- Catalog embeddings: set server-only `AI_GATEWAY_API_KEY` and `EMBEDDING_MODEL=google/gemini-embedding-2` in the matching Node or Edge environment above. Apply the catalog knowledge migration separately, then run `pnpm --filter @event-management/api catalog:embed` from the repository root to reconcile eligible sources and backfill or retry embeddings. This command makes paid provider calls and reads uploaded images through configured Storage. Background refresh runs at most two owners per process, with a 120-second owner budget and 30-second Storage/provider call limits. Edge uses `EdgeRuntime.waitUntil`; shutdown, timeouts, and provider failures can leave pending rows. There are no durable scheduled retries: rerun the command to recover. The sequential CLI backfill has no background owner budget.
- The local Edge runtime uses the `oneshot` policy, which ends work after the response. Set `CATALOG_EMBEDDING_AWAIT=true` in `apps/supabase/.env.functions` for that policy; catalog mutations then wait for refresh with a 110-second batch budget. Provider failures still preserve the successful catalog save and leave pending rows. Restart the local function server after changing this setting. Node and deployed workers that support background tasks can leave this setting false.
- Catalog media: set the Supabase Storage variables in the API example before testing Node API uploads. Built-in package sample photos do not require uploads. Existing stored files are left in place.
- Database clients such as DBeaver: use PostgreSQL on `localhost:5432` with the configured database name/user/password. The local defaults use no SSL. A containerized client may require `host.docker.internal` instead of `localhost`.

## Authentication

New registrations create local customer accounts with Argon2id password hashes; passwords must contain 8–128 characters. Password hashing uses WebAssembly through `hash-wasm` in both Node and the Edge Function, with 19 MiB of memory, two passes, and parallelism one. Existing Argon2id hashes remain valid; no password reset or database migration is needed. Google sign-in and existing Firebase email/password accounts are optional identity methods. Application roles always come from PostgreSQL.

Run `pnpm --filter @event-management/api test:password` for password compatibility checks. With the current Edge bundle served by `pnpm dev` or `pnpm dev:edge`, run `pnpm --filter @event-management/api test:edge` to check session rejection, unknown-account password verification, route matching, and OpenAPI loading in the local runtime. After changing API code, rebuild with `pnpm build:edge` and restart the function server before running those runtime checks.

All methods use the `em_session` cookie and hashed sessions in PostgreSQL. The frontend restores the account with `GET /v1/me`. While the workspace remains open, it rechecks `/me` when the page regains focus or visibility and after a non-authentication data request returns `401`. A successful check refreshes the profile; a `401` clears it and returns the user to login with the local workspace URL saved for sign-in. Same-origin `/app` navigation uses browser history and does not remount the authentication provider. Sessions expire after `SESSION_TTL_DAYS` (default 7), rotate on successful sign-in/linking, and are deleted on logout. Cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` in production.

Account settings → Sign-in methods supports connecting Firebase to a local account after proving the current local password, or adding a local password after proving the connected Firebase identity. Firebase proof requires a verified email and a sign-in within five minutes. Matching emails never merge accounts automatically; linking preserves the database identity and role. Profile editing, local password reset, and local email-verification delivery are not implemented.

The only account roles are `customer` and `admin`. Admin access belongs to designated System Administrators; public registration creates customers, and the browser cannot assign or promote a role. Reload after an authorized role change so the frontend refreshes its profile.

Password attempts are limited in memory per account; multiple API processes require a shared limiter. Browser writes must pass the configured `WEB_ORIGIN` check. See the [authentication reference](context-factory/areas/api/references/auth-and-sessions.md) and running OpenAPI contract for route details.

### Optional Firebase setup

1. Enable Google and retain Email/Password for existing accounts in Firebase Authentication. Add `localhost` to authorized domains for local development.
2. Fill in the `PUBLIC_FIREBASE_*` fields in `apps/web/.env` using the web app configuration.
3. Configure `FIREBASE_PROJECT_ID` on the API and either `GOOGLE_APPLICATION_CREDENTIALS` pointing to a gitignored service-account JSON or `FIREBASE_CLIENT_EMAIL` plus `FIREBASE_PRIVATE_KEY`. Relative credential paths resolve from `apps/api`.
4. For a Firebase-backed admin, run `pnpm db:seed-admin admin@example.com` after configuring Firebase. The command finds the Firebase user or creates one when `ADMIN_PASSWORD` is supplied, then assigns the database System Administrator role. For local-only fixtures, use `pnpm db:seed` instead.

The API verifies Firebase ID tokens, including revocation/disabled-user checks, before identity exchange or linking. A Firebase token alone does not grant catalog administration.

## Catalogs and media

Catalog packages and services are flat records with ordered canvas sections stored in `packages.canvas` and `services.canvas` as JSONB arrays. The document is a plain sections array with no schema-version field. A canvas save replaces the owner's full canvas and uses the owner's `expectedUpdatedAt` concurrency check; there are no independently versioned section or widget rows. A System Administrator catalog save publishes a complete record immediately. Packages can include ordered service links marked included or optional; these links remain relational and do not calculate package prices or establish availability. Service pricing is catalog information and does not automatically calculate quotation amounts. Physical event locations are recorded on booking requests through `preferredVenueLocation`. Booking-owned custom packages are private and have a separate edit/audit flow. Updates require `expectedUpdatedAt`; stale or archived edits return `409`. Archive hides a record from public selection. A package referenced by a booking request cannot be deleted.

| Catalog | Required save data                                                                                                                                  |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Package | Name, positive `maxGuests`, fixed total PHP price, and canvas sections; the catalog description is separate from Markdown widgets.                  |
| Service | Name, description, positive whole-peso `hourlyRatePesos`, optional paired `fixedPricePesos` and positive whole `includedHours`, and a canvas photo. |

Package prices are stored as whole pesos; the API uses `{ kind: "fixed", currency: "PHP", amountMinor }` in centavos divisible by 100. Booking responses derive `packageName`, `packagePrice`, and `packageMaxGuests` from the referenced package. Service saves require a positive whole-peso `hourlyRatePesos`; send both `fixedPricePesos` and `includedHours` as null for hourly-only pricing, or provide a positive fixed price and positive whole number of included hours together. A legacy service rate may be null on reads. Omitted service canvas sections preserve saved content.

Creating a catalog package or service opens a details modal before the canvas editor. Required fields are marked and validated before continuing; the modal does not save a record. Package descriptions remain optional. Services collect their description and pricing first, then require a photo in the editor before saving. The same details remain editable inside the editor. The catalog package editor hides the package-services picker and preserves existing service assignments on save; private booking-package editing retains its service controls.

The shared editor uses photo, Markdown, and video widgets on a 12-column canvas. The editor, customer preview, and public detail page use the full available width with the same widget dimensions at the same screen width. Photos and videos fit inside their widgets without cropping; rendered text outside a widget is clipped without internal scrollbars. Markdown editing opens in a separate dialog so the canvas shows the rendered result. Editor guides and numbered columns use the actual snap geometry; each section shows its automatically growing row count from the lowest widget edge. Saves retain widget positions and spans, including intentional gaps. A widget can span at most 100 rows; sections have no separate fixed row count. Shared application schemas validate the canvas before browser uploads/saves and again in API requests, stored-document reads/writes, and seeds. Invalid canvas saves identify the affected section/widget in the editor. Pending file selections are validated before upload and require a saved media ID afterward. Editor previews, saved catalog overlays, booking package views, and server-rendered public details reuse the same app composition and shared canvas/widget renderer; embedded booking views adapt to their containing area. Media uploads go through `POST /v1/admin/catalog-media`, remain pending until a catalog save references them, and stream through `/v1/catalog-media/{id}`. JPEG/PNG/WebP images allow up to 10 MiB; MP4/WebM videos allow up to 25 MiB. Photo/video widgets accept uploads only, with built-in sample photos retained for seeded packages; external URLs and hosted-player embeds are rejected. Video autoplay is opt-in and uses muted inline playback on customer previews and public pages.

Public media streaming requires a reference from a published, non-archived catalog record. System Administrators can preview pending uploads and saved private media under the API access rules. Owners can preview media currently referenced by their private package; private responses use no-store caching. Quotations do not retain historical media or grant media access. Removing uploaded media triggers cleanup only when no current widget references it; storage failures can leave unreferenced assets for retry. See [catalog media](context-factory/areas/api/references/external-image-urls.md) for storage, cleanup, and migration details, and [shared limits](context-factory/areas/contracts/SKILL.md) for validation ownership.

## Database workflow

For schema changes, edit `apps/api/prisma/schema.prisma`, create and review the migration, then regenerate Kysely types:

```sh
pnpm db:migrate
pnpm db:generate
pnpm check
```

`pnpm db:deploy` applies committed migrations; it does not create migrations. Never hand-edit generated `apps/api/src/db/types.ts`. Inspect both Prisma and SQL migrations because some database constraints extend beyond the Prisma model.

The type generator includes application tables in `public` only, excluding Supabase's internal schemas. Migration `20261110141853_event_day_staffing` is historical: it introduced operational event days along with availability and assignment tables. Later additive migrations remove those tables and response fields while keeping admin event-day scheduling.

Migration `20261109140000_enable_application_rls` enables row-level security on application tables and Prisma's migration history. It removes table grants from `PUBLIC` and, when present, Supabase's `anon` and `authenticated` roles. Clients access records through Clemora's session-aware API; there are no direct-client RLS policies. The server database role must own the tables or have `BYPASSRLS`. Future table-creation migrations must explicitly enable RLS and remove unused client grants too; this migration does not install an automatic trigger. These SQL-only access settings do not change Prisma models or generated Kysely types.

Migration `20261111150000_simplify_quotation_offers` deliberately discards quotation package timestamps and full package/event-term snapshots. It preserves quotation IDs, package references, amounts/items, status and acceptance timestamps, revision links, audit events, and quotation messages. It does not delete Storage objects; normal cleanup can remove uploads that no current widget references. Deploy the matching API and web changes together with this migration.

Migration `20261111120000_booking_requested_days` adds nullable JSONB `booking_requests.requested_days` with a check that non-NULL values are nonempty arrays. SQL `NULL` identifies requests created before customers selected a complete date list. The migration does not backfill dates or rewrite the legacy estimate, timestamps, snapshots, conversations, or operational event days.

Migration `20261114000000_drop_venues` removes the venue catalog and its package link; `20261114010000_drop_staff_tables` removes availability and assignment tables plus event-day staffing fields. The additive `20261114151517_complete_catalog_staff_removal` migration revokes sessions for former staff and admins without the System Administrator designation, converts those accounts to customers, and drops `users.staff_role`. At that stage, it also deletes catalog pages left without an owner, restores the temporary package/service page-owner constraint, and removes coordinator/checklist delivery metadata. Migration `20261116072801_embed_catalog_canvas` later embeds the remaining canvases and drops the page hierarchy. Follow-up migration `20261114154206_remove_event_checklists` drops the event-checklist table and its content validator, removing stored task definitions and progress. The migrations keep shared media assets and Storage objects; `pnpm --filter @event-management/api media:cleanup` removes stale unreferenced media through the existing cleanup path.

Migration `20261116063852_derive_booking_package_details` drops `booking_requests.package_name`, `package_price`, and `package_max_guests`, including their stored values and column checks. Existing requests keep their package references, dates, statuses, conversations, and schedules; package details use the current catalog record, including archived records. Private proposals and saved quotation amounts retain their separate ownership. Deploy this migration with the matching API; old API code requires the removed columns.

Migration `20261116072801_embed_catalog_canvas` adds `packages.canvas` and `services.canvas`, backfills the ordered section/widget arrays while preserving their IDs and content/media references, then drops `catalog_widgets`, `catalog_sections`, and `catalog_pages`. Package/service owner timestamps, `media_assets`, uploaded Storage objects, and relational `package_services` links remain separate and unchanged. Follow-up migration `20261116090100_validate_catalog_canvas_in_app` removes the SQL canvas validator and its two check constraints without changing canvas data, owner timestamps, defaults, NOT NULL constraints, or GIN indexes. Canvas document validation belongs to the shared browser/API application schemas; direct SQL writes bypass those rules. Deploy the matching application validators with this migration; see the [catalog canvas decision](context-factory/history/decisions/2026-11-16_catalog-canvas-jsonb.md) and [database guidance](context-factory/areas/api/references/database-and-migrations.md).

Migration `20261116090000_service_fixed_pricing` adds nullable `services.fixed_price_pesos` and `services.included_hours`. The constraint permits hourly-only rows with both fields null or fixed pricing with both positive and a non-null hourly rate. Existing service rates, including legacy null rates, are preserved. The migration does not change quotation data or calculations.

Migration `20261116103220_add_catalog_knowledge` enables pgvector and creates the empty `catalog_knowledge` table without changing catalog records or Storage objects. The PostgreSQL server must provide the `vector` extension; plain `postgres:17` images do not include it. The migration reuses an existing extension in its current schema. Each row has exactly one package/service owner, a unique chunk key within that owner, and either an entirely pending or entirely populated embedding state. Owner and media deletion cascade to their derived rows. RLS and revoked client grants preserve server-only access. The ingestion services enforce catalog-only, non-archived eligibility, input invalidation, and stale-result protection; these behaviors are not supplied by foreign keys or this migration. Admin search enforces current-source and model/preprocessing compatibility. Any future customer retrieval must additionally enforce its customer visibility policy before exposing evidence.

Migration `20261116083246_conversation_ai_control` adds `conversations.ai_enabled` (default true) and `ai_version` (default zero). It preserves messages and existing conversation status, and does not infer historical takeover from old admin messages. Apply it before the matching API; deploy the updated API and browser contracts together.

Migration `20261116061207_add_ai_message_replies` makes the message sender nullable only for the new `assistant` role; human sender IDs remain required. It preserves existing messages and conversation lifecycle. Deploy the matching API and browser contracts together.

**`pnpm db:reset` deletes data without a confirmation prompt.** Its script forces a Prisma reset, reapplies migrations, and seeds the configured database. Check the target and use it only for a database whose contents may be discarded.

### Migration impact

Review all pending migrations before upgrading a populated database:

- `20261102130000_package_canvas` removes existing packages, package versions and service assignments, booking requests and status history, and booking-linked conversations/messages. General conversations and messages remain.
- `20261102180000_flat_services_venues` retains selected current content, or archives the latest content when none was published. It removes version tables and unselected canvas pages; uploaded storage objects are not deleted.
- `20261102190000_cleanup_catalog_fields` renames guest limits to `maxGuests` / `max_guests` and snapshots to `packageMaxGuests` / `package_max_guests`. It discards package event types, venue categories/photo URLs, and legacy service-image references. Existing canvas content and inquiry snapshots remain. Legacy storage objects are not removed remotely.
- `20261109140000_enable_application_rls` preserves records and blocks direct table access for Supabase client roles. Apply it as the table owner and verify the API database role before deployment. `pnpm db:deploy` targets the database configured for the API; creating this migration does not apply it to the separate local Supabase stack.
- `20261111120000_booking_requested_days` adds the nullable requested-date JSONB column and array constraint without fabricating missing dates or rewriting existing booking data.
- `20261114000000_drop_venues` removes venue listings, package/venue links, and the venue catalog-page owner column. Any ownerless pages are deleted by the follow-up cleanup migration.
- `20261114010000_drop_staff_tables` removes event availability and assignment tables and the event-day response fields.
- `20261114151517_complete_catalog_staff_removal` revokes sessions and converts staff and non-designated admin accounts to customers, leaving designated System Administrators as admins. It drops the remaining staff-role and coordinator/checklist-delivery fields, deletes ownerless catalog pages, restores the temporary package/service owner check, and preserves media assets and Storage objects; the later embed migration drops the remaining page hierarchy.
- `20261114154206_remove_event_checklists` drops `event_checklists` and `clemora_checklist_content_valid(jsonb)`, removing saved checklist tasks and progress. Earlier migration files remain unchanged as historical evidence.
- `20261116072801_embed_catalog_canvas` moves package/service canvas content into owner JSONB arrays, preserving section/widget IDs, order, content, and media IDs before dropping the former page/section/widget tables. It does not change media assets or uploaded objects.
- `20261116090000_service_fixed_pricing` adds paired nullable fixed-price and included-hours fields to services, requiring both to be positive together and requiring an hourly rate when fixed pricing is set. Existing hourly rates remain unchanged.

Back up affected records before deployment. Apply coordinated API/frontend contract changes with their migrations; do not edit applied migrations or reset a database to resolve drift. The [database guidance](context-factory/areas/api/references/database-and-migrations.md), [catalog media reference](context-factory/areas/api/references/external-image-urls.md), and [seed guide](docs/SEED.md) provide the related procedures.
